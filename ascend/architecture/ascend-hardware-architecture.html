昇腾硬件架构：达芬奇架构、910C/A3 与 950 ​

本文先介绍达芬奇架构的计算、存储和数据流，再分析 Ascend 910C 与 Atlas A3、910C-128 超节点的现场配置，最后讨论 Ascend 950。CANN 软件栈、部署检查和性能验证方法列在附录。

参数分为官方产品规格、CloudMatrix384 论文配置和现场采样三类，正文分别标注。比较时应先确认芯片、Die、加速卡、服务器或超节点层级，再核对数据格式、带宽方向及理论或实测口径。

1. 达芬奇架构：计算、存储与数据流 ​

1.1 Host 与 Device 的分工 ​

昇腾程序通常由 Host CPU 和 Device NPU 协同执行。Host 侧运行应用、框架和 CANN Runtime，负责设备管理、内存分配、任务提交及运行时控制；Device 侧执行 Kernel，完成矩阵、向量和数据搬运等操作。[1][2]

Host 与 Device 通常拥有各自的内存空间。常规路径下，Host 数据需要通过运行时或框架提供的接口传入 Device；Host 指针不能因为数值相同就被当作 Device 指针使用。部分平台支持统一编址或共享访存，但地址映射、访问权限、同步和一致性规则仍由具体平台及软件接口决定。

1.2 AI Core：Cube、Vector 与 Scalar ​

AI Core 是执行 AI Kernel 的主要计算资源。Ascend C 将其抽象为 Cube、Vector、Scalar 三类计算单元，以及内部存储、数据搬运和控制单元。[1][2]

单元主要职责常见工作
Cube矩阵乘加和张量计算GEMM、卷积的矩阵化计算、注意力中的 QKᵀ 与 PV
Vector对一组数据执行向量运算逐元素运算、归约、Softmax、GELU、量化和反量化
Scalar标量运算、地址计算、流程控制和指令发射循环、分支、参数准备和流水控制

Cube 的左右输入矩阵分别进入 L0A、L0B，计算结果及中间累加值写入 L0C。Vector 的输入、输出和中间数据通常放在 Unified Buffer（UB）中。Scalar 负责控制与调度，不宜承担大规模通用数据计算；若 Kernel 中存在大量标量操作或复杂分支，可能影响计算流水效率。

耦合模式与分离模式 ​

Cube、Vector 是否部署在同一个核内，决定了 AI Core 的两种组织方式。[1]

  • 耦合模式：Cube 和 Vector 共用一个 Scalar 调度单元，部署在同一个 AI Core 内。
  • 分离模式：Cube Core 和 Vector Core 各自拥有 Scalar 调度单元。两者按硬件设定的比例组合成逻辑 AI Core；该模式下，AI Core 数量按 Cube Core 数量统计。

分离模式下，AIC 通常指 Cube Core，AIV 指 Vector Core。昇腾社区当前 Ascend C 文档列出的产品模式包括：Atlas A2/A3 训练和推理系列采用分离模式；Atlas 350 采用分离模式；较早的 Atlas 训练、推理系列采用耦合模式。Atlas 200I/500 A2 的硬件支持两种模式，但 Ascend C 编程场景使用耦合模式。具体核数、AIC/AIV 配比及接口支持情况，应以目标设备的硬件信息和对应 CANN 版本文档为准。[1][2]

NPU 还可能集成 AI CPU。AI CPU 位于 Device 侧，承担部分控制、标量、通用 CPU 算子及调度相关工作；Host CPU 运行主机操作系统、应用和主机侧软件栈。两者的职责不能混为一谈。[3]

1.3 存储层次 ​

昇腾的存储体系不是一条所有数据都必须依次经过的缓存链。硬件管理的 Cache、软件显式规划的 Local Memory，以及 Device 全局内存，各自承担不同任务。

存储主要作用使用时需要注意
GM（Global Memory）算子编程中的设备全局内存视角，保存 Kernel 输入、输出及中间数据GM 是软件层的逻辑视角；物理介质通常是 HBM 或其他设备内存，不能把 GM 与某一种物理内存直接画等号
L2 Cache服务设备全局访存的共享缓存，可缓存代码和数据主要由硬件管理，不等同于软件显式分配的 L1、L0 或 UB
L1 BufferAI Core 内部的局部存储，为矩阵计算暂存和复用数据不是 Vector 专用缓存；具体容量、连接和用途随架构而变
L0A / L0B保存 Cube 的左右输入矩阵数据排布、分块和对齐需要满足 Cube 通路要求
L0C保存 Cube 计算结果及中间累加结果输出可经 FixPipe 等路径处理后写入支持的目标存储
UB（Unified Buffer）Vector/Scalar 运算的输入、输出和中间数据存储属于 AI Core 内部 Local Memory，不宜简单类比为 GPU 寄存器
BiasTable / Fixpipe Buffer 等为偏置、量化和结果处理等专用路径提供存储是否具备及容量取决于具体产品架构

GM、L2 和 AI Core 内部 Local Memory 的角色不同。优化算子时，通常需要把频繁复用的数据留在片上局部存储，减少不必要的 GM 读写；但分块大小必须服从目标平台的存储容量、数据排布和访问粒度。

1.4 数据搬运：MTE 与 FixPipe ​

MTE（Memory Transfer Engine）负责不同存储空间之间的数据搬运；部分路径支持在搬运过程中完成数据格式或数值类型转换。常见路径如下。[1][2]

单元常见路径说明
MTE2GM → L1、GM → UB；部分架构也支持 GM → L0A/L0B从全局内存向 AI Core 内部存储搬入数据
MTE1L1 → L0A/L0B；部分架构还涉及 BiasTable Buffer为 Cube 准备矩阵输入
MTE3UB → GM将 Vector 路径的结果写回全局内存
FixPipeL0C → GM/L1；部分架构支持随路格式转换处理 Cube 结果及量化、排布转换等操作

图中展示的是典型数据流，不代表每个 MTE 只能访问固定的一对地址空间。不同芯片的存储大小、访问粒度和搬运路径可能不同，应查询目标产品的架构文档或通过开发接口获取实际容量。[1]

算子优化中的 Tiling、数据复用、对齐和双缓冲，都是围绕局部存储与搬运通路展开的。分块过大可能挤占 UB/L1 等资源；分块过小则可能增加搬运、调度和同步开销。

1.5 指令队列与同步 ​

Host 提交 Kernel 后，运行时创建并管理 Device Task 和 Stream。Device 调度单元再将任务分配给可用计算资源。一个 Kernel 通常由多个 AI Core 处理不同的数据分块，形成 SPMD（Single Program, Multiple Data）式并行执行。[2]

在 AI Core 内部，Scalar 发射指令：标量指令直接执行，Vector、Cube 和 MTE 指令进入相应执行流水或队列。不同流水可以并行工作，但指令被发射或进入队列，并不代表其数据读写已经完成。

Ascend C 常用以下机制表达流水依赖：[1]

  • PipeBarrier：约束相关流水的先后关系，使后续操作不会越过需要等待的前序操作。
  • SetFlag / WaitFlag：在不同流水或任务之间建立事件依赖；前一侧完成约定操作后设置标志，等待方在标志满足前不能继续执行依赖操作。

例如 GM → UB → Vector → UB → GM 这一流程中，数据搬入完成后才能进行计算，计算完成后才能搬出。若循环复用同一块 UB，还要确保新数据不会覆盖尚未被消费的旧数据。Ascend C 的高层编程范式可以处理常见同步关系；手动同步应建立在明确理解目标流水与缓冲区生命周期的基础上。

1.6 以 FlashAttention 观察计算与搬运的配合 ​

注意力计算同时包含矩阵乘、非线性处理和大量数据移动，可以用来理解 Cube、Vector 与 MTE 的协作。

实际 FlashAttention 实现还要维护在线 Softmax 的归一化状态，并对 Head、序列长度和矩阵维度进行分块。图中是逻辑阶段，不代表每一步都要把完整注意力矩阵写回 GM。优化目标是让中间数据尽可能在局部存储中复用，同时利用异步搬运和双缓冲，使数据准备与计算重叠。

2. Ascend 910C 与 Atlas A3：从芯片到超节点 ​

2.1 先区分产品层级 ​

“Ascend 910C”“Atlas 800T A3”“一张 NPU 卡”和“一个训练 rank”不是同一层级。芯片、加速模块、服务器、超节点和软件可见设备之间存在映射关系，不能只凭商品名称推断计算 Die 数、Runtime device 数或 rank 数。

层级示例核对重点

设备编译目标应以运行环境查询为准。昇腾产品形态文档提供 soc_series、soc_version 等信息的查询说明；Atlas A3 开发环境常见 NPU_ARCH=2201，soc_version 可能采用 Ascend910_93xx 系列命名。不要仅凭产品名称手工补全具体后缀。[4]

2.2 910C：双计算 Die 封装 ​

CloudMatrix384 论文将其所用处理器称为 Ascend 910；华为后续发布材料将 Atlas A3 所用处理器称为昇腾 910C。引用论文中的芯片结构时，本文保留论文的命名，并把相关数量限定为论文所描述的配置。[5][18]

论文描述的 Ascend 910 采用双计算 Die 合封：两个计算 Die 共用封装内的 8 个高带宽内存堆栈，并通过封装内高速互联通信。每个 Die 配置 24 个 AIC 和 48 个 AIV；整颗封装合计 48 个 AIC、96 个 AIV。论文列出的计算数据类型包括 FP16、BF16 和 INT8。[5]

论文还描述了每个计算 Die 分别接入 UB 和 RDMA 网络平面。图中按 Die 粒度呈现，是对论文拓扑的概括。AIC/AIV 数量、内存堆栈数量及网络连接方式都应视为论文配置，不能在没有对应产品资料的情况下套用到所有 910C SKU。

Atlas A3 产品页给出的设备内存配置为每颗 NPU 128 GB，最高内存带宽 3.2 TB/s。[6][7] 这里的 128 GB 是 NPU 设备内存，不是服务器 Host DDR；3.2 TB/s 是设备内存带宽，不是设备间互联带宽。910C 的 FP8、MXFP8 或 MXFP4 能力也不能从 Ascend 950 的规格反推。

2.3 Atlas A3：服务器与超节点配置 ​

Atlas A3 的训练、推理服务器以及超节点采用不同配置。以下数据来自对应产品页，表示公开规格上限或标称配置，不应与实际项目交付清单混为一谈。[6][7][8]

产品公开硬件配置官方公开算力定位与散热
Atlas 800T A310U；8 颗昇腾 910；4 颗鲲鹏 920；32 个 DDR5 插槽6.0 PFLOPS FP16；12.0 POPS INT8预训练、后训练；风冷
Atlas 800I A310U；8 颗昇腾 910；4 颗鲲鹏 920；32 个 DDR5 插槽4.48 PFLOPS FP16；8.96 POPS INT8大模型推理；风冷
Atlas 900 A3 SuperPoD最大 384 颗昇腾 910；192 颗鲲鹏 920；12 个计算柜、4 个总线设备柜307.2 / 288.7 PFLOPS FP16（产品页列示两档）大规模训练与推理；计算柜液冷、总线设备柜风冷

Atlas 800T A3、800I A3 产品页均列出每台 8 × 128 GB 设备内存，内存带宽最高 3.2 TB/s。[6][7] Atlas 900 A3 SuperPoD 产品页列出 48 TB 片上内存统一编址，以及双向 784 GB/s 的 D2D 互联带宽。[8]

统一编址表示软件可在相应地址空间中寻址远端资源，不代表全部物理内存集中在一处，也不意味着远端访问具备本地 HBM 的时延和带宽。

带宽术语需要带上层级。 “D2D”在不同材料中可能指封装内 Die-to-Die，也可能指设备间 Device-to-Device。比较时要同时注明互联层级、单向或双向，以及理论值或实测值。

2.4 CloudMatrix384：超节点内的三个网络平面 ​

CloudMatrix384 论文描述的系统由 48 台计算节点组成，共 384 颗 NPU、192 颗鲲鹏 CPU。每个计算节点配置 8 颗 NPU、4 颗 CPU 和 7 颗板载 UB 交换芯片；系统跨 16 个机柜，其中 12 个为计算柜、4 个为通信柜。[5]

论文将网络分为三个平面：

  1. UB 平面（Scale-Up）：连接超节点内的 CPU 与 NPU，承载细粒度通信、设备间访问和远端内存访问。二级 UB 交换网络分为 7 个独立子平面，论文将其设计为无带宽收敛。
  2. RDMA 平面（Scale-Out）：基于 RoCE，连接不同超节点或兼容 RDMA 的外部系统。论文说明该平面由 NPU 参与，可用于跨超节点训练、推理及 Prefill/Decode 之间的 KV Cache 传输。
  3. VPC 平面：由擎天 DPU 接入标准以太网/IP 网络，承载部署、监控、业务访问和持久化存储流量，与 NPU 的 RDMA 平面分开。

三个平面解决的问题不同：UB 是超节点内部的高带宽互联；RoCE/RDMA 负责跨超节点通信；VPC 连接数据中心业务网络和存储系统。统一编址使资源具备可寻址性，实际访问仍需要软件栈、权限和通信机制配合。[5]

论文明确注明其网络图中的带宽数字采用单向口径。[5] 因此，不能把论文的单向 UB 数值与产品页中的双向 D2D 数字直接相加或比较。“无收敛”也只描述拓扑的带宽配置，不意味着任意通信模式在任意并发负载下都能独占标称带宽。

4. Ascend 950：第三代达芬奇与灵衢 2.0 ​

4.1 多 Die 封装与第三代达芬奇 ​

Ascend 950PR 和 950DT 采用第三代达芬奇架构。两者的基本封装结构相近，但 AI Die 数量、IO Die 数量和高速内存配置需要结合白皮书的具体型号规格阅读。[10]

完整封装包含 2 个 AI Die、2 个 IO Die，以及高速片上内存模块：950PR 配置 8 个内存模块，950DT 配置 4 个。AI Die、IO Die 与内存模块通过 D2D Clink 和 Memory Interface 互联，构成统一内存访问（UMA）体系。

每个 AI 子系统包含 1 个 Cube Core 和 2 个 Vector Core。白皮书的系列概述使用 36 组 AI 子系统描述完整架构；详细规格表进一步区分型号和衍生版本：950PR 为 32/28 组，950DT 为 36/32/28 组。因此，“36 组”是系列规格中的上限，不能写成所有 950PR 的固定配置。[10]

完整架构还包括 AI CPU Cluster、共享 L2 Cache、STARS 2.0 调度系统、DVPP 和专用安全引擎。白皮书列出的 DVPP 配置为 4 个 VPC Core、4 个 JPEGE Core 和 8 个 JPEGD Core；IO 接口包括 UB 2.0、UBoE 和 PCIe 5.0。[10]

每个 AI CPU Cluster 包含 2 个基于 ARMv8-A 的 Linx816 CPU Core 和 4 MB L3 Cache；Linx816 支持物理双线程。AI CPU 负责 NPU 侧操作系统、页表管理、性能监控、算子编译和设备调度，也能执行部分控制、标量与向量类 CPU 算子。[10]

4.2 计算格式与数据通路变化 ​

950 的 Cube Core 支持 TF32、FP16、BF16、FP8、MXFP8、HiF8、INT8 和 MXFP4 等格式。低精度格式有助于提高理论吞吐并降低存储、搬运开销，但实际收益取决于模型精度要求、量化策略、算子实现及软件版本。[10]

第三代架构在向量计算和数据通路方面的主要变化包括：[10]

  • 基于寄存器的 SIMD/SIMT 混合编程：Vector Core 采用基于寄存器的 SIMD 架构，SIMD 是规则向量计算的主要路径；SIMT 用于补充 Gather/Scatter 和复杂分支等不规则任务。相关编程抽象使用 Vector Function（VF）。
  • Cube–Vector 融合：支持 Cube L1 Buffer 与 Vector UB 之间更直接的数据传输，并可在通路中进行精度和排布转换，减少中间结果经 L2 或 GM 往返。
  • NDDMA：可对 GM 中最多 5 个维度的数据进行重排，再写入 Vector Core 的 UB；内置缓存可利用数据局部性，并把多个小粒度读操作聚合为 128 Byte 读取。具体布局和访问限制以编程文档为准。
  • BufferID 同步：通过缓冲区获取、释放和生命周期表达流水依赖，减少单纯依赖固定屏障的同步开销。

这些功能依赖 Ascend 950 硬件及适配的软件版本，不能直接套用到 910C。NDDMA 也不意味着所有不规则访存都能自动获得高性能；数据布局和访存局部性仍然重要。

4.3 950PR 与 950DT：内存配置对应不同负载 ​

白皮书中的“高速片上内存”是保存全局数据的 DRAM，不是 AI Core 内部的 L1、L0 或 UB。不同文档对内存的称呼略有差异；Atlas 350 产品页使用 HBM 一词。下表的容量和带宽按白皮书详细规格表列示，HiBL 1.0 与 HiZQ 2.0 的方案名称按华为发布资料列示。[10][18]

L2 Cache128 / 112 MB128 MB

PR 与 DT 不是简单的高低配关系。Prefill 通常对输入序列进行并行计算，矩阵计算密度较高；Decode 按 Token 逐步生成，对权重和 KV Cache 的反复访问更敏感。不同内存配置对应不同负载侧重点，实际选型还要结合模型结构、批量、上下文长度和软件支持情况。

950 的 L2 Cache 由两个 AI Die 共享并统一编址；白皮书描述了跨 AI Die 的硬件一致性支持，以及 Cache Hint、按 Way 驻留和 128 Byte Sector 等管理特性。AI CPU 具有自己的 L1/L2/L3 Cache，并通过一致性机制与 AI Core 和共享 L2 子系统交换数据。[10]

STARS 2.0 用于调度 AIC、AIV、CPU、DVPP、SDMA、UB 和 CCU 等引擎，支持任务流下沉、资源分组和性能轨迹记录。DVPP 负责图像/视频相关处理，可减少这类任务对 AI Core 与 AI CPU 的占用。[10]

语义工作方式白皮书/产品资料列出的操作

URMA 适合与计算流水重叠的异步通信；UB Memory 提供同步 Load/Store 访存路径。两者都需要软件处理地址和权限、内存一致性、完成通知及错误状态。华为云 A5 文档给出的适用范围不同：URMA 支持 8K 超节点范围内存语义，UB Memory 最大支持 1K 超节点范围。不能把一种语义的规模限制套用到另一种语义上。[13]

CCU（Collective Communication Unit）是昇腾 950 中用于加速集合通信的硬件单元。系统调度器可向 CCU 下发集合通信任务，由其按软件预置算法执行搬运、同步和 Reduce 等操作。白皮书列出的算法包括 Broadcast、ReduceScatter、AllGather、AllReduce、All2All 和 All2Allv。CCU 提供通信卸载能力，实际性能仍受 HCCL 软件路径、消息大小、拓扑和负载均衡影响。[10][17]

4.6 超节点规模：架构能力与具体组网方案 ​

950 架构白皮书给出最大 8192 卡超节点及超过 128K 卡集群的架构支持能力；Atlas 950 SuperPoD 产品页列出的配置为 64 卡或 1024 卡。[10][12] 8192 卡属于白皮书描述的架构能力上限，64/1024 卡属于产品页当前列出的配置，不是同一层级的数字。

机柜数量应按具体产品资料记录。昇腾社区 Atlas 950 SuperPoD 产品页列出 16 个计算柜和 4 个灵衢互联柜；华为云 1024 NPU 组网说明则给出 16 个计算柜、2 个灵衢互联柜，并描述 8 个超平面和两级灵衢交换。[12][14]

这两组数据不能合并成一个“标准机柜配置”。华为云页面中的 2 个互联柜是其 1024 模组组网示例的计算结果；产品页的 4 个互联柜是产品规格页列示的整机柜形态。工程实施时应以采购 SKU、设备 BOM、合同配置和现场布线图为准，并记录文档版本。

6.1 CANN 软件栈 ​

CANN（Compute Architecture for Neural Networks）为框架和应用提供访问昇腾设备的运行环境。模型开发者通常使用框架、算子库或 AscendCL 接口，不需要直接编写硬件指令。[15]

组件主要职责使用边界
驱动与固件设备初始化、资源管理、设备通信和硬件控制必须与硬件、操作系统和 CANN 版本配套
Runtime管理 Device、Context、Stream、Event、设备内存和任务职责与 CUDA Runtime 有部分相似之处，但接口与实现不同
GE（Graph Engine）在支持的执行模式下处理计算图、编译优化和执行控制并非所有 PyTorch Eager 算子都必经 GE
AOE在支持的场景中自动调优算子或计算图功能范围取决于 CANN 版本及目标产品
AscendCL提供设备、Context、Stream、内存、模型和算子等 API框架内部可能使用不同的调用路径
OPP / 内置算子库提供目标产品和版本支持的算子实现需要核对精度、形状、布局及动态形状限制
Ascend C用 C/C++ 风格接口组织计算、搬运和同步用于自定义算子和针对性性能优化
TBE通过 DSL 等方式描述和生成算子按既有实现、版本支持和迁移成本选择
HCCL提供 AllReduce、AllGather、ReduceScatter、Broadcast、All2All 等集合通信底层路径可能涉及 HCCS、RoCE 或其他受支持互联
torch_npuPyTorch 的昇腾设备后端和算子适配不是 CUDA API 或 CUDA Kernel 的自动转换器
MindSpore面向昇腾生态的 AI 框架不依赖 torch_npu
MindSpeed 等套件提供大模型并行、算子和性能优化能力需要核对模型、框架、驱动和 CANN 版本配套

PyTorch Eager、图模式和推理引擎的调用链不同，不应把所有任务描述成固定经过同一组模块。图编译、算子编译和 Runtime 调度也分别解决不同问题。

6.4 部署前检查 ​

  1. 确认设备和 SoC 型号。 记录整机、NPU、设备内存和互联配置。可先运行 npu-smi info；在安装 CANN 且 Python ACL 模块可用时，可执行：

    bash
    python3 -c "import acl; print(acl.get_soc_name())"
    1

  2. 按兼容矩阵安装软件。 驱动、固件、CANN、PyTorch、torch_npu、HCCL、推理引擎和模型框架必须使用兼容组合。Beta 版本适合功能验证，未经充分验证不宜直接用于生产环境。

  3. 分层验证基础能力。 依次检查设备可见性、内存分配、基础矩阵算子、单机多卡通信和跨节点通信，再运行完整模型。

  4. 核对机房与网络条件。 确认机柜功率、供电制式与冗余、风冷或液冷条件、网络布线、光模块和存储配套。

  5. 保存验收材料。 记录硬件清单、软件版本、测试配置、原始日志和监控数据，保证结果能够复现。

6.5 从单卡到业务逐级测量 ​

性能验证建议按以下顺序进行：

  1. 计算映射：确认矩阵计算是否有效落到 Cube；检查 Vector、Scalar 是否成为瓶颈，以及精度和数据布局是否匹配。
  2. 数据路径：检查分块复用、搬运对齐、不必要的 GM 往返及格式转换。
  3. 流水与同步：检查搬入、计算、搬出能否重叠，并定位屏障、缓冲区冲突和事件等待。
  4. 主机与调度：测量小 Kernel 下发、Host–Device 拷贝和主机侧逻辑开销。
  5. 多卡通信：分别测量单机内、同超节点跨机和跨超节点路径；固定通信原语、消息大小、卡数及并发条件。
  6. 业务指标：训练记录稳定步时、吞吐和扩展效率；推理区分 TTFT、TPOT、吞吐以及 P95/P99 尾时延，并固定并发数、输入输出长度和模型精度。
  7. 可靠性：观察长时间负载下的温度、功耗、链路告警、故障隔离和恢复过程。

TTFT 是首 Token 时延；TPOT 是 Decode 阶段平均每个输出 Token 的耗时。MFU 是模型实际执行 FLOPs 与理论可用 FLOPs 的比值，计算时需要统一分子、分母的统计范围。跨平台测试要固定模型、精度、批量、并行策略和软件版本，不能用不同测试条件下的峰值代替业务性能。
