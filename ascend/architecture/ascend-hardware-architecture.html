昇腾AI 硬件技术介绍 ​

——以 Ascend 910C 为主，兼述 Ascend 950 系列

适用读者： AI 基础设施规划人员、系统架构师、算法工程师、平台运维人员及技术管理人员 内容范围： Ascend 910C 芯片及其服务器、超节点系统；Ascend 950PR/950DT 的技术演进与产品形态；昇腾软件栈、互联和部署要点。

1. 概述 ​

昇腾（Ascend）是华为面向人工智能计算推出的处理器及计算平台系列。其硬件产品并非只有单颗 AI 芯片，还包括加速卡、AI 服务器、超节点（SuperPoD）以及更大规模的智算集群。Atlas 是华为基于昇腾处理器和基础软件构建的 AI 计算产品体系，覆盖训练、推理及行业 AI 应用场景。[1]

本文重点介绍 Ascend 910C。910C 是昇腾面向大规模训练和推理的重要一代产品，其关键价值不仅在于单芯片计算能力，更在于与鲲鹏 CPU、高速互联、统一内存编址、服务器和超节点技术协同形成系统级算力。以 Atlas 900 A3 SuperPoD 为例，系统最多支持 384 个 NPU 高速互联，官方公布的 FP16 峰值算力为 307.2/288.7 PFLOPS，并支持 48 TB 片上内存统一编址。[2]

Ascend 950 是后续一代产品系列，包含面向推理 Prefill 和推荐场景的 950PR，以及面向推理 Decode 和训练场景的 950DT。相较 910C，950 系列的重要变化包括：新增 FP8、MXFP8、MXFP4、HiF8 等低精度格式；引入 SIMD/SIMT 双编程模型；提升向量计算能力；并将互联升级至灵衢 Unified Bus 2.0（UB 2.0）。[3][4]

1. 产品层次与基本概念 ​

1.1 从处理器到集群 ​

“昇腾 910C”“Atlas 800T A3”“一张 NPU 卡”和“一个训练 device”不是同一层次的概念。

层次代表内容需要核对的信息

具体 SoC 型号由设备查询得到的 soc_version离线编译目标、算子支持和具体规格
加速模块或加速卡Atlas 200I、300I、350 等板卡内存、功耗、接口和散热条件
服务器或计算节点Atlas 800T A3、800I A3 等NPU 与 CPU 数量、主机内存、PCIe 和网络拓扑
超节点Atlas 900 A3、Atlas 950 SuperPoD 等节点数、交换拓扑、统一编址范围和故障域
云服务实例CloudMatrix384 等底层产品、资源池划分和云服务接口
软件可见设备Runtime 枚举出的 device物理卡、计算 die 与逻辑 device 的映射
分布式训练单元rank、通信组rank 到 device 的绑定及通信算法

官方产品形态说明将 Atlas 训练系列、Atlas 推理系列、Atlas 200I/500 A2、Atlas A2、Atlas A3 和 Ascend 950PR/950DT 系列分别列出，并给出 soc_series 与 soc_version 的查询方式。开发文档对 Atlas A3 给出的标识为 NPU_ARCH=2201、soc_version=Ascend910_93xx，具体后缀应在目标设备上查询，不能仅凭商品名称硬编码。

CloudMatrix384 是华为云基于 Atlas 900 A3 超节点构建的云服务实例，不是另一款芯片。CloudMatrix384 论文将处理器简称为“Ascend 910”，华为发布资料则将 Atlas 900 A3 所用处理器明确称为昇腾 910C。引用论文参数时，应保留这一来源和命名差异。

Host 侧负责应用逻辑、运行时管理和任务提交，Device 侧执行 Kernel 及数据密集计算。在通用编程模型中，两侧内存空间分离，不能假定 Host 指针可以在 Device 上直接使用；输入通常先复制到 Device 全局内存，计算完成后再复制回 Host。特定产品提供的统一内存或灵衢共享访存能力，需要按各自的地址、同步和权限规则理解。

2. 达芬奇架构：计算、存储与异步执行 ​

2.1 AI Core 的三类计算单元 ​

AI Core 是昇腾处理器执行 AI Kernel 的核心计算资源。Ascend C 文档将其抽象为三类计算单元、若干内部存储单元和数据搬运单元。

计算单元主要职责典型工作负载
Cube矩阵乘加和张量计算GEMM、卷积的矩阵化实现、注意力中的 QKT 与 PV
Vector对多个数据执行同类向量操作逐元素运算、归约、Softmax、GELU、量化与反量化
Scalar标量运算、地址与参数计算、流程控制、指令发射循环、分支、描述符和地址准备、流水控制

Cube 的左矩阵进入 L0A Buffer，右矩阵进入 L0B Buffer，矩阵乘结果及中间累加结果进入 L0C Buffer。Vector 的源操作数和结果通常放在 Unified Buffer（UB）中。Scalar 像核内的控制处理器，但不适合承担大量通用计算；复杂分支和过多标量操作可能妨碍主流水运行。

实际算子往往由 Cube、Vector 和搬运单元共同完成，性能取决于三者能否形成均衡的流水线，而不是只取决于 Cube 峰值算力。

2.2 耦合模式与分离模式 ​

不同产品对三类计算资源的物理组织不同。官方 Ascend C 文档区分两种工作模式：

  • 耦合模式：矩阵和向量计算单元共用同一个 Scalar 调度单元，部署在一个 AI Core 上。
  • 分离模式：Cube Core 和 Vector Core 各自拥有 Scalar 调度单元，按一定比例组合为一个逻辑 AI Core；该模式下 AI Core 数量以 Cube Core 数量为准。

在分离模式文档中，AIC 指组合中的 Cube Core，AIV 指组合中的 Vector Core。Atlas A2/A3 训练和推理系列采用分离模式；较早的 Atlas 训练和推理系列采用耦合模式。Atlas 200I/500 A2 的硬件可以支持两种模式，但 Ascend C 编程场景仅使用耦合模式。核数、AIC/AIV 配比和同步接口应通过目标平台接口查询。

2.3 AI CPU 与 Host CPU ​

AI Core 之外，昇腾处理器还可包含 AI CPU，用来执行控制类、标量和部分通用向量算子。它与 Host CPU 的位置和职责不同：Host CPU 运行应用与主机侧软件栈，AI CPU 位于 NPU 侧，补充 AI Core 不擅长的通用处理。

昇腾 950 进一步集成了 4 个 AI CPU Cluster，每个 Cluster 包含 2 个基于 ARMv8-A 的 Linx816 CPU Core 和 4 MB L3 Cache。Linx816 支持物理双线程；AI CPU 还承担 NPU 侧操作系统、页表管理、性能监控、算子编译以及加速器和 IO 调度等任务。该配置属于昇腾 950，不能反推早期产品。

2.4 存储单元与数据搬运 ​

昇腾算子开发中的“内存层次”不是一条所有数据都必须顺序经过的缓存链。硬件自动管理的 Cache、软件显式规划的 Local Memory 和 Device 全局内存具有不同性质。

名称性质与作用理解时的边界
GM（Global Memory）算子编程中的设备全局内存视角，保存 Kernel 输入、输出和中间数据GM 是逻辑视角；HBM 或其他 DRAM 是物理实现，两者不能直接画等号
L2 Cache服务设备全局访存的共享缓存，可缓存代码段和数据段由硬件管理，与软件显式分配的 L1/L0/UB 不同
L1 BufferAI Core 内的重要局部存储，服务矩阵数据准备和部分中间结果不应笼统称为“Vector 的缓存”
L0A / L0B分别保存 Cube 的左、右输入矩阵数据排布和对齐需满足 Cube 通路的约束
L0C保存 Cube 的结果和中间累加结果结果可经后续通路转换并写往支持的目标存储
Unified Buffer（UB）Vector 计算的主要局部存储，也承载大量算子中间数据不是 L0A/L0B/L0C 的统称，也不能简单类比 GPU 寄存器
BiasTable / Fixpipe Buffer 等为偏置、结果处理等专用路径提供存储是否具备及其容量取决于具体架构

MTE（Memory Transfer Engine）负责在不同存储空间之间搬运数据，部分路径还支持随路格式或数值类型转换。按照官方典型数据流：

  • MTE2 常见于 GM 到 L1 或 UB 的搬入路径；
  • MTE1 常见于 L1 到 L0A/L0B 的矩阵输入准备路径；
  • MTE3 常见于 UB 到 GM 的结果搬出路径；
  • FixPipe 位于 Cube 结果处理路径，可配合完成数据排布转换、量化等操作，具体能力依架构而定。

这些描述用于识别典型通路，不是说每个 MTE 只能连接一对固定地址空间。局部存储容量、最小访问粒度、对齐要求和完整连接关系，都应查询目标产品规格。

分块（Tiling）、数据复用、对齐以及双缓冲流水，都是围绕这套存储与搬运体系展开的优化。若数据不能及时进入局部存储，或者搬出、格式转换和同步形成瓶颈，计算单元就会等待。

2.5 指令队列与同步 ​

在 Host–Device 层面，运行时根据 Kernel 的核数和任务类型创建 Task，将其放入 Device Stream 的运行队列，再由调度单元分配给空闲 AI Core。多个核心处理不同的数据块，属于 SPMD（Single Program, Multiple Data）组织方式。

在 AI Core 内部，Scalar 对指令进行分类和发射：Scalar 指令直接执行，Vector、Cube、MTE 等指令进入各自的队列。同一队列中的指令按进入顺序处理，不同队列可以并行；但“顺序处理”不代表后一条指令开始时，前一条指令的所有读写都已结束。

常见同步机制包括：

  • PipeBarrier：约束同一指令序列内的执行顺序，保证前序指令的数据读写完成后，后序指令才开始执行。
  • SetFlag / WaitFlag：在不同指令序列之间建立事件依赖。SetFlag 等待当前序列前序读写完成后置位，WaitFlag 在标志未就绪时阻塞目标序列。

以 GM → UB → Vector → UB → GM 为例，至少需要保证搬入完成后才能计算、计算完成后才能搬出。循环使用同一块 UB 时，还要防止新数据覆盖尚未被消费或搬出的旧数据。Ascend C 的高层编程范式通常会自动插入必要同步；手动同步主要用于标准范式无法表达的特定场景。

3. 昇腾 910C 与 Atlas A3 ​

3.1 双计算 Die 封装 ​

CloudMatrix384 论文描述的处理器采用双计算 Die 合封：两个计算 Die 共享封装内的 8 个高带宽内存堆栈，并通过封装内高速互联通信。论文配置中，每个计算 Die 包含 24 个 AIC 和 48 个 AIV，合计 48 个 AIC 和 96 个 AIV；计算引擎支持 FP16、BF16 和 INT8。上述核心数量属于论文所述配置，不应推定所有商业型号完全一致。

A3 产品公开配置通常按每 NPU 128 GB 设备内存、最高 3.2 TB/s 内存带宽描述。这里的 128 GB 不是服务器 DDR5 容量，3.2 TB/s 也不是设备间网络带宽。910C 的论文配置与 Atlas A3 产品配置应结合阅读，不能用 950 的原生 FP8、MXFP8 或 MXFP4 能力反推 910C。

3.2 算力与互联的口径 ​

Atlas A3 的不同训练和推理产品具有不同峰值，不能把一个“单芯片 800 TFLOPS”数字当作所有 SKU 的通用承诺。

产品NPU 与主机配置官方公开峰值典型用途与散热
Atlas 800T A310U；8 颗昇腾 NPU、4 颗鲲鹏 920；32 个 DDR5 插槽6.0 PFLOPS FP16；12.0 POPS INT8预训练、后训练；风冷
Atlas 800I A310U；8 颗昇腾 NPU、4 颗鲲鹏 920；32 个 DDR5 插槽4.48 PFLOPS FP16；8.96 POPS INT8大模型推理；风冷
Atlas 900 A3 SuperPoD最大 384 颗昇腾 NPU、192 颗鲲鹏 920；12 个计算柜、4 个总线设备柜307.2 / 288.7 PFLOPS FP16 两档规模化训练和推理；计算柜液冷、总线设备柜风冷

800T A3 和 800I A3 的产品页均列出每台 8 × 128 GB 设备内存及 3.2 TB/s 设备内存带宽。Atlas 900 A3 还列出 48 TB 片上内存统一编址和双向 784 GB/s D2D 互联带宽。统一编址不意味着设备共享一块物理 HBM，也不保证远端访问具有本地 HBM 的时延和带宽。

“D2D”在不同资料中可能指封装内 Die-to-Die，也可能指设备间 Device-to-Device。引用带宽时必须注明层级、单向或双向以及理论或实测口径，不能将两类数字直接比较。

3.3 CloudMatrix384 的三个通信平面 ​

CloudMatrix384 的公开实现由 48 台计算节点组成，每节点配置 8 颗 NPU、4 颗 CPU 和 7 颗板载灵衢交换芯片。节点内为第一级互联，通信柜内的第二级交换划分为 7 个独立子平面，按无收敛设计连接各计算节点。整个系统包含 12 个计算柜和 4 个通信柜。

三类通信平面分别承担不同职责：

  • 灵衢 UB（Scale-Up）：连接超节点内的 CPU 与 NPU，为细粒度通信和远端内存访问提供高速路径。统一编址让资源可寻址，但不意味着框架会自动聚合全部内存。
  • RoCE / RDMA（Scale-Out）：在 CloudMatrix384 所述实现中承载超节点间通信，可用于跨域训练、推理以及 Prefill 与 Decode 之间的 KV Cache 传输。
  • VPC（数据中心网络）：由擎天 DPU 接入，承载部署、监控、业务接入和持久化存储访问，与 NPU 的 RoCE 平面分开。

“无收敛”描述交换拓扑的带宽配置，不代表任意两个设备都能在满并发下独占全部标称带宽。论文网络图采用单向口径，不应直接与产品页的双向 D2D 数字比较。

实机核验带来四项边界修正：

  1. brain3 不能按“8 个独立 NPU 封装”描述。 当前工具口径是 4 个 NPU ID、8 个 Chip；软件 device/rank 数量还取决于运行时映射，不能仅凭进程数决定。
  2. 不能用 CloudMatrix384 的节点配置覆盖 brain3。 论文中的 8 NPU、4 CPU 是另一种明确记录的配置；brain3 当前只暴露 4 NPU、2 CPU Socket，是否经过资源隔离以及完整物理节点形态需由平台侧确认。
  3. 不能混用 AICore Count 与论文 AIC/AIV 计数。 本文保留论文的 24 AIC + 48 AIV 和实机工具的 25 AICore Count 两种原始口径，不将二者拼接成推算规格。
  4. 不能把当前节点当作整个超节点。 brain3 的查询结果可以验证本地封装、HBM 和链路关系，但不能单独证明超节点总卡数、完整交换拓扑、统一编址容量或跨节点带宽。

4. 昇腾 950 系列 ​

4.1 第三代达芬奇架构与 Chiplet UMA ​

昇腾 950 系列包括 950PR 和 950DT，两者采用共同的第三代达芬奇架构，通过不同的高速片上内存配置面向不同负载。

一颗完整的昇腾 950 芯片合封 2 个 AI Die、2 个 IO Die，以及 8 个（950PR）或 4 个（950DT）高速片上内存模块。各 Die 与内存模块通过 D2D Clink 和 Memory Interface 连接，整芯片构成统一内存访问（UMA）的整体。

主要整芯片规格包括：

  • 36 个第三代 DaVinci AI 子系统，每个包含 1 个 Cube Core 和 2 个 Vector Core；
  • 4 个 AI CPU Cluster，每个包含 2 个 Linx816 双线程处理器和 4 MB L3 Cache；
  • 最高 128 MB 统一访问 L2 Cache；
  • STARS 2.0 任务与资源调度系统；
  • 4 个 VPC、4 个 JPEGE 和 8 个 JPEGD 组成的 DVPP 图像处理能力；
  • UB 2.0、UBoE 和 PCIe 5.0 等 IO 接口。

4.2 计算、低精度与数据流改进 ​

昇腾 950 的 Cube Core 支持 TF32、FP16、BF16、FP8、MXFP8、HiF8、INT8、MXFP4 等格式。低精度格式的意义不只是提高理论峰值，也包括降低数据存储和搬运开销，但模型精度、量化方法和 Kernel 支持仍需单独验证。

第三代架构的主要数据流改进包括：

  • Vector Register File：在 UB 与 Vector ALU 之间引入寄存器堆，提高数据复用和供给能力。
  • SIMD/SIMT 混合编程：以 SIMD 为主处理规则、连续的向量计算，以 SIMT 为辅处理 Gather/Scatter、复杂分支等不规则任务。基本函数块称为 Vector Function（VF）。
  • Cube–Vector 融合：支持 Cube L1 Buffer 与 Vector UB 之间的直接数据传输，并可随路完成精度和排布转换，减少经过 L2 或全局内存交换中间数据的成本。
  • NDDMA：对 GM 中最多五个维度的数据进行重排，再写入 Vector Core 的 UB；内置缓存可发掘局部性，将细粒度读取聚合为更高效的对齐访问。
  • BufferID 同步：以缓冲区的获取和释放表达依赖，更贴近流水线对缓冲区生命周期的管理。

这些能力依赖目标硬件和 CANN 版本，不能直接套用到 910C 或更早产品。NDDMA 也不意味着任意不规则访存都能被自动优化。

4.3 存储、调度与媒体处理 ​

昇腾 950 的“高速片上内存”在白皮书中属于保存全局数据的 DRAM，不是 AI Core 内部的 L1、L0 或 UB。

昇腾 950 将灵衢（Unified Bus，UB）2.0 作为规模扩展的基础。需要分别理解物理链路、访问语义、集合通信引擎和组网拓扑。

UB 提供两类内存访问语义：

语义工作方式典型操作
URMA通过 Jetty 队列、Doorbell 和完成机制进行异步通信，可执行远端内存搬运与消息操作Read、Write、Send、Notify，以及部分 Atomic 操作

URMA 适合与计算流水重叠的异步通信，UB Memory 提供更直接的同步访存语义。二者都不意味着软件可以忽略地址权限、内存一致性、完成通知和错误处理。华为云 A5 文档还分别给出 URMA 支持 8K 超节点范围、UB Memory 最大支持 1K 超节点范围的口径，不能把两种语义的适用规模混为一谈。

CCU（Collective Communication Unit）接收系统调度器下发的集合通信任务，根据软件预置的通信算法执行节点间搬运、同步和 Reduce 计算。白皮书列出的典型算法包括 Broadcast、ReduceScatter、AllGather、AllReduce、All2All 和 All2Allv。CCU 为卸载集合通信和计算通信并行提供硬件条件，但实际效果仍取决于 HCCL 等软件路径、消息大小、拓扑和负载均衡。

4.6 超节点规模：架构能力与交付配置 ​

950 白皮书给出最大 8192 卡超节点、整体集群超过 128K 卡的架构支持能力；当前 Atlas 950 SuperPoD 产品页给出 64 或 1024 卡配置。前者是协议与架构规模，后者是具体产品配置，不应互相替代。

华为云 A5 组网文档以 1024 个 NPU 模组为例，描述 16 个计算柜、8 个超平面和两级灵衢交换组织。昇腾社区 Atlas 950 产品规格页与云侧 A5 文档在机柜交付形态上可能采用不同口径，实际项目应同时核对产品 SKU、云资源形态和交付设计，而不能只保留一个卡数。

6.1 软件栈分层 ​

硬件指令通常不会由模型开发者直接编写。框架和应用通过 CANN（Compute Architecture for Neural Networks）使用昇腾设备。

6.3 编程与迁移边界 ​

NVIDIA GPU 主要通过线程、线程块与 warp 组织 SIMT 执行，并使用专门的矩阵计算资源。昇腾算子开发则更需要显式考虑矩阵与向量资源、局部缓冲区、数据分块和流水线同步。两者都包含专用计算资源，差别不能简单归结为“GPU 同构、NPU 异构”。

迁移 PyTorch 工作负载时，先检查标准算子在目标后端的支持范围、精度和布局要求。自定义 CUDA 扩展通常需要选择已有 NPU 算子替代，或使用 Ascend C 等方式重新实现，不能假定修改设备字符串即可迁移全部逻辑。

8.2 部署检查 ​

  1. 核对设备与 SoC：记录整机、NPU、HBM 和互联配置。可使用 npu-smi info 查看设备基本信息；安装 CANN 与 Python ACL 后，可用 python3 -c "import acl;print(acl.get_soc_name())" 查询 SoC 型号。
  2. 按兼容矩阵安装软件：驱动、固件、CANN、PyTorch、torch_npu、HCCL、推理引擎和模型框架必须配套。Beta 版本适合验证新特性，不应未经测试直接作为生产默认版本。
  3. 先验证基础能力：依次检查设备可见性、内存分配、基础矩阵算子、单机多卡通信和跨节点通信，再运行完整模型。
  4. 核对机房条件：确认机柜功率、供电制式与冗余、风冷或液冷条件、网络布线、光模块和存储配套。
  5. 保留验收证据：记录测试配置、软件版本、原始日志和监控数据，避免只保留一个无法复现的吞吐数字。

8.3 从单卡到集群逐级测量 ​

硬件优化和性能分析可按以下顺序展开：

  1. 计算映射：矩阵部分是否高效落到 Cube，Vector 和 Scalar 是否成为瓶颈，精度和布局是否匹配。
  2. 数据路径：分块是否提高复用，搬运是否对齐，是否产生不必要的 GM 往返和格式转换。
  3. 流水与同步：搬入、计算、搬出能否重叠，是否存在过度屏障、缓冲区冲突或事件等待。
  4. 主机与调度：小 Kernel 下发、Host–Device 拷贝和主机逻辑是否占据显著时间。
  5. 多卡通信：分别测量单机、同超节点跨机和跨超节点路径，固定通信原语、消息大小、卡数及并发条件。
  6. 业务指标：训练记录稳定步时、吞吐和扩展效率；推理区分 TTFT、TPOT、吞吐与 P95/P99 尾时延，并固定并发数、输入输出长度和模型精度。
  7. 可靠性：观察长时间负载下的温度、功耗、链路告警、故障隔离和恢复过程。

术语或说法正确理解
UB在 Ascend C 中常指 Unified Buffer；在超节点互联中通常指 Unified Bus，必须结合上下文区分

TTFT 与 TPOTTTFT 是首 Token 时延，TPOT 是 Decode 阶段平均每输出 Token 时延
MFU模型实际执行 FLOPs 与理论可用 FLOPs 的比值，计算时应统一分子和分母口径
Scale-Up 与 Scale-Out前者强调紧密互联域内扩展，后者强调通过网络连接更多节点或超节点
峰值算力与最大卡数都不能替代目标模型、软件路径和真实业务约束下的端到端验证

总结 ​

昇腾硬件的主线可以概括为三部分：AI Core 通过 Cube、Vector、Scalar 分工执行计算，局部存储与 MTE 负责把数据及时送到计算单元，异步队列和事件机制维护跨单元流水。进入多芯片系统后，AI CPU、任务调度器、DVPP、互联控制器与集合通信引擎共同决定端到端效率。

910C 的公开技术资料展示了双计算 Die、128 GB 级设备内存和 384 NPU 超节点的系统组织方式。950 则进一步引入第三代 DaVinci Core、低精度格式、SIMD/SIMT 混合编程、CV 融合、NDDMA、灵衢 2.0 和 CCU，并以 950PR、950DT 适配不同训练与推理阶段。

理解这些能力时，应始终保留两个边界：不同产品代际和交付 SKU 不能直接套用参数；官方峰值、架构支持规模和统一编址能力，只有经过具体软件路径与工作负载验证，才能转化为应用性能。
