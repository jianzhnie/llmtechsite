昇腾硬件架构：达芬奇、910C/A3 与 950 ​

本文分三部分介绍昇腾硬件：先讲达芬奇架构如何组织计算、存储和数据搬运，再分析 Ascend 910C 与 Atlas A3 计算系统，最后讨论 Ascend 950 的架构变化。CANN 软件栈和性能验证方法放在附录，供开发和部署时查阅。

文中的芯片、加速卡、服务器和超节点参数分别标注来源。CloudMatrix384 论文、Atlas 产品页和 brain3 实机数据对应不同环境，互不替代；950 白皮书描述系列架构，具体产品仍以交付配置为准。

1. 昇腾达芬奇架构 ​

1.1 Host 与 Device 的分工 ​

昇腾程序通常由 Host CPU 和 Device NPU 协同执行。Host 运行应用、框架和 CANN Runtime，负责设备管理、内存分配与任务提交；Device 执行 Kernel，完成矩阵、向量和数据搬运等操作。[3]

Host 和 Device 有各自的内存空间。普通编程路径需要由程序显式复制数据，或由框架完成两侧传输，Host 指针不能直接在 Device 上使用。特定产品提供统一编址或共享访存能力时，仍须遵守相应的地址、权限和同步规则。

1.2 AI Core：Cube、Vector 与 Scalar ​

AI Core 是执行 AI Kernel 的主要计算资源。Ascend C 将其抽象为三类计算单元、内部存储单元和数据搬运单元。[1][2]

计算单元职责典型计算
Cube矩阵乘加和张量计算GEMM、卷积的矩阵化实现、注意力中的 QKT 与 PV
Vector对一组数据执行向量操作逐元素运算、归约、Softmax、GELU、量化与反量化
Scalar标量运算、地址计算、流程控制和指令发射循环、分支、描述符准备和流水控制

Cube 的左、右输入矩阵分别进入 L0A 和 L0B，结果及中间累加值进入 L0C。Vector 的源操作数和结果通常放在 Unified Buffer（UB）中。Scalar 负责控制，不适合承担大量通用计算；复杂分支和过多标量操作会拖慢主流水。

不同产品对 Cube、Vector 和 Scalar 的物理组织有所区别。Ascend C 文档将其分为耦合和分离两种模式：[1]

  • 耦合模式：矩阵和向量计算单元共用一个 Scalar 调度单元，部署在同一 AI Core 上。
  • 分离模式：Cube Core 和 Vector Core 各自配备 Scalar 调度单元，再按一定比例组成逻辑 AI Core。此模式下，AI Core 数量按 Cube Core 数量统计。

在分离模式中，AIC 指 Cube Core，AIV 指 Vector Core。Atlas A2/A3 训练和推理系列采用分离模式；较早的 Atlas 训练和推理系列采用耦合模式。Atlas 200I/500 A2 的硬件支持两种模式，但 Ascend C 编程场景只使用耦合模式。核数、AIC/AIV 配比和同步接口应以目标平台的查询结果为准。

除 AI Core 外，NPU 还可以集成 AI CPU。AI CPU 位于 Device 侧，用于控制类、标量和部分通用向量算子；Host CPU 则运行应用和主机侧软件栈，两者承担的工作不同。[16]

1.3 存储层次与数据搬运 ​

昇腾的存储层次不是一条所有数据都要依次经过的缓存链。硬件自动管理的 Cache、软件显式规划的 Local Memory，以及 Device 全局内存，各有不同的用途。

名称作用使用时的边界
GM（Global Memory）算子编程中的设备全局内存视角，保存 Kernel 输入、输出和中间数据GM 是逻辑视角，HBM 或其他 DRAM 是物理实现，二者不能直接画等号
L2 Cache服务设备全局访存的共享缓存，可缓存代码和数据由硬件管理，与软件显式分配的 L1/L0/UB 不同
L1 BufferAI Core 内的局部存储，服务矩阵数据准备和部分中间结果不只是 Vector 的缓存
L0A / L0B分别保存 Cube 的左、右输入矩阵数据排布和对齐须满足 Cube 通路要求
L0C保存 Cube 的结果和中间累加结果结果可经后续通路转换并写入支持的目标存储
Unified Buffer（UB）Vector 计算的主要局部存储，也保存算子中间数据不是 L0A/L0B/L0C 的统称，也不能简单类比 GPU 寄存器
BiasTable / Fixpipe Buffer 等为偏置和结果处理等专用路径提供存储是否具备及其容量取决于具体架构

MTE（Memory Transfer Engine）负责在不同存储空间之间搬运数据，部分路径支持随路转换格式或数值类型。官方文档给出的典型通路如下：[1][2]

  • MTE2 常见于 GM 到 L1 或 UB 的搬入路径；
  • MTE1 常见于 L1 到 L0A/L0B 的矩阵输入准备路径；
  • MTE3 常见于 UB 到 GM 的结果搬出路径；
  • FixPipe 位于 Cube 结果处理路径，可配合完成数据排布转换和量化，具体能力依架构而定。

这些通路用于说明数据如何流动，并不表示每个 MTE 只能连接一对固定地址空间。局部存储容量、访问粒度和完整连接关系须查询目标产品规格。算子优化中的分块（Tiling）、数据复用、对齐和双缓冲，都围绕这套存储与搬运体系展开。

1.4 指令队列与同步 ​

Host 提交 Kernel 后，运行时按核数和任务类型创建 Task，将其放入 Device Stream 的运行队列，再由调度单元分配给 AI Core。多个核心处理不同的数据块，属于 SPMD（Single Program, Multiple Data）组织方式。[3]

AI Core 内部的 Scalar 对指令分类并发射：Scalar 指令直接执行，Vector、Cube 和 MTE 指令进入各自队列。同一队列按顺序处理，不同队列可以并行，但后一条指令开始执行，并不代表前一条指令的读写已经全部完成。

Ascend C 使用两类常见机制建立依赖：[1][2]

  • PipeBarrier 约束同一指令序列内的执行顺序，保证前序指令的数据读写完成后，后序指令才开始执行。
  • SetFlag / WaitFlag 在不同指令序列之间建立事件依赖。SetFlag 等待当前序列前序读写完成后置位，WaitFlag 在标志未就绪时阻塞目标序列。

以 GM → UB → Vector → UB → GM 为例，搬入完成后才能计算，计算完成后才能搬出。循环复用同一块 UB 时，还要防止新数据覆盖尚未消费的旧数据。Ascend C 的高层编程范式通常会自动插入必要同步，手动同步主要用于标准范式无法表达的场景。

2. Ascend 910C / Atlas A3：从计算卡到超节点 ​

2.1 先分清产品层次 ​

“昇腾 910C”“Atlas 800T A3”“一张 NPU 卡”和“一个训练 device”处在不同层次。尤其要注意，Atlas 800T/800I A3 是 10U 服务器，Atlas 900 A3 是超节点，不能与单张 PCIe 加速卡混为一谈。

昇腾产品形态文档给出了 soc_series 与 soc_version 的查询方式。Atlas A3 开发资料使用 NPU_ARCH=2201、soc_version=Ascend910_93xx，具体后缀应在目标设备上查询，不能只凭商品名称硬编码。[8]

CloudMatrix384 是基于 Atlas 900 A3 超节点构建的云服务实例。论文将处理器简称为“Ascend 910”，华为发布资料则将 Atlas 900 A3 所用处理器称为昇腾 910C。下文引用论文参数时保留这一命名差异。[4][19]

2.2 910C：双计算 Die 封装 ​

CloudMatrix384 论文描述的处理器采用双计算 Die 合封。两个计算 Die 共享封装内的 8 个高带宽内存堆栈，并通过封装内高速互联通信。论文配置中，每个计算 Die 有 24 个 AIC 和 48 个 AIV，整封装合计 48 个 AIC 和 96 个 AIV；计算引擎支持 FP16、BF16 和 INT8。[4]

这些核心数量属于论文所述配置，不能直接套用到所有商业型号。A3 产品公开配置通常按每 NPU 128 GB 设备内存、最高 3.2 TB/s 内存带宽描述。[5][6] 这里的 128 GB 指 Device HBM，不是服务器 DDR5 容量；3.2 TB/s 指设备内存带宽，也不是设备间网络带宽。950 的原生 FP8、MXFP8 和 MXFP4 能力同样不能反推到 910C。

2.3 Atlas A3：整机配置与公开峰值 ​

Atlas A3 的训练、推理和超节点产品采用不同配置，峰值算力应落到具体 SKU。

产品NPU 与主机配置官方公开峰值用途与散热

Atlas 800T A3 和 800I A3 的产品页均列出每台 8 × 128 GB 设备内存及最高 3.2 TB/s 设备内存带宽。[5][6] Atlas 900 A3 还列出 48 TB 片上内存统一编址和双向 784 GB/s D2D 互联带宽。[7] 统一编址提供跨设备寻址能力，物理内存仍分布在各 NPU 上，远端访问也不具备本地 HBM 的时延和带宽。

“D2D”在不同资料中可能指封装内 Die-to-Die，也可能指设备间 Device-to-Device。比较带宽时，应同时注明互联层级、单向或双向、理论或实测口径。

2.4 CloudMatrix384：超节点内的三个通信平面 ​

CloudMatrix384 的公开实现由 48 台计算节点组成，每节点配置 8 颗 NPU、4 颗 CPU 和 7 颗板载灵衢交换芯片。节点内为第一级互联，通信柜内的第二级交换划分为 7 个独立子平面，按无收敛设计连接各计算节点。系统共有 12 个计算柜和 4 个通信柜。[4]

三类网络承担不同任务：

  • 灵衢 UB（Scale-Up）连接超节点内的 CPU 与 NPU，承载细粒度通信和远端内存访问。统一编址让资源可寻址，框架仍需通过相应的软件和通信路径使用这些资源。
  • RoCE / RDMA（Scale-Out）在 CloudMatrix384 中承载超节点间通信，可用于跨域训练、推理，以及 Prefill 与 Decode 之间的 KV Cache 传输。
  • VPC（数据中心网络）由擎天 DPU 接入，承载部署、监控、业务接入和持久化存储访问，与 NPU 的 RoCE 平面分开。

“无收敛”描述交换拓扑的带宽配置，并不保证任意设备在满并发下都能独占标称带宽。论文网络图采用单向口径，不能直接与产品页的双向 D2D 数字比较。

3. Ascend 950：Chiplet、低精度与灵衢 2.0 ​

3.1 第三代达芬奇架构与多 Die 合封 ​

Ascend 950 系列包括 950PR 和 950DT，两者采用第三代达芬奇架构，通过不同的高速片上内存配置适配不同负载。[10]

一颗完整的昇腾 950 合封 2 个 AI Die、2 个 IO Die，以及 8 个（950PR）或 4 个（950DT）高速片上内存模块。各 Die 与内存模块通过 D2D Clink 和 Memory Interface 连接，整芯片构成统一内存访问（UMA）的整体。

整芯片有 36 个第三代 DaVinci AI 子系统，每个子系统包含 1 个 Cube Core 和 2 个 Vector Core；L2 Cache 最高 128 MB，由两个 AI Die 统一访问。芯片还集成 STARS 2.0 任务与资源调度系统，以及 4 个 VPC、4 个 JPEGE 和 8 个 JPEGD 组成的 DVPP 图像处理能力，IO 接口包括 UB 2.0、UBoE 和 PCIe 5.0。

950 的 4 个 AI CPU Cluster 各有 2 个基于 ARMv8-A 的 Linx816 CPU Core 和 4 MB L3 Cache。Linx816 支持物理双线程。AI CPU 还承担 NPU 侧操作系统、页表管理、性能监控、算子编译，以及加速器和 IO 调度等任务。这组配置属于 950，不能用于推断早期产品。

3.2 计算、低精度与数据流改进 ​

950 的 Cube Core 支持 TF32、FP16、BF16、FP8、MXFP8、HiF8、INT8 和 MXFP4 等格式。低精度格式可以提高理论峰值，也能减少存储和搬运开销；实际收益还取决于模型精度、量化方法和 Kernel 支持。

第三代架构对向量计算和数据通路做了以下调整：[10]

  • Vector Register File 位于 UB 与 Vector ALU 之间，用于提高数据复用和供给能力。
  • SIMD/SIMT 混合编程以 SIMD 处理规则、连续的向量计算，以 SIMT 处理 Gather/Scatter 和复杂分支等不规则任务，基本函数块称为 Vector Function（VF）。
  • Cube–Vector 融合支持 Cube L1 Buffer 与 Vector UB 之间直接传输数据，并可随路完成精度和排布转换，减少中间数据经过 L2 或全局内存的开销。
  • NDDMA 对 GM 中最多五个维度的数据进行重排，再写入 Vector Core 的 UB；内置缓存利用局部性，将细粒度读取聚合为对齐访问。
  • BufferID 同步以缓冲区的获取和释放表达依赖，对应流水线中缓冲区的生命周期。

这些能力依赖 950 硬件和相应 CANN 版本，不能直接套用到 910C。NDDMA 也不意味着任意不规则访存都会被自动优化。

3.3 950PR 与 950DT：存储配置决定负载定位 ​

950 白皮书中的“高速片上内存”属于保存全局数据的 DRAM，与 AI Core 内部的 L1、L0 或 UB 不是同一层存储。

主要目标负载推荐系统、大模型 Prefill、多模态推理训练、后训练，以及包含 Decode 与 Prefill 的推理

950PR 与 950DT 并非简单的高低配。Prefill 并行处理输入提示词，通常有较高的矩阵计算密度；Decode 逐 Token 生成，对权重和 KV Cache 的反复访问更敏感。两种型号通过不同的存储配置适配这些差异。

除高速片上内存外，950 的 L2 Cache 跨 AI Die 统一编址，由硬件维护两个 AI Die 间的一致性，并支持 Cache Hint、按 Way 驻留和 128 Byte Sector 等管理特性。AI CPU 有独立的 L1/L2/L3 Cache，通过全局缓存一致性与 AI Core、共享 L2 子系统交换数据。

STARS 2.0 调度 AIC、AIV、CPU、DVPP、SDMA、UB 和 CCU 等引擎，支持任务流下沉、资源分组和性能轨迹记录。DVPP 承担图像解码、预处理和编码，减少这些任务对 AI Core 与 AI CPU 的占用。

3.4 Atlas 350 与 Atlas 950 SuperPoD 的实际配置 ​

白皮书给出系列能力上限，具体加速卡和超节点可能采用衍生配置。[10][11][12]

产品当前官方公开配置说明
Atlas 350 加速卡950PR；112 GB HBM、1.4 TB/s；425 TFLOPS FP16/BF16、804 TFLOPS MXFP8/HiF8 等、1561 TFLOPS MXFP4；PCIe 5.0 x16；最大功耗不超过 600 W，被动散热面向多模态生成、LLM 推理和推荐；卡间互联随 2 卡或 4 卡拓扑而不同

Atlas 950 SuperPoD 产品页还列出 256 TB 全局内存统一编址能力。这里指地址空间和内存语义，不是本地 HBM 总量；1024 卡配置的设备内存总量应按 1024 × 96 GB 计算。

3.5 灵衢 2.0、URMA 与 CCU ​

昇腾 950 使用灵衢（Unified Bus，UB）2.0 扩展芯片间和超节点互联。评估互联能力时，要把物理链路、内存访问语义、集合通信引擎和组网拓扑分开。[10]

接口或协议950 白皮书规格用途
HiLink SerDes72 Lane，每 Lane 最高 112 Gbps，组成 18 个 x4 PortUB 等高速互联的物理基础
UB架构表列出 2016 GB/s（双向），概述中约为 2 TB/s芯片间及超节点互联
UBoE2 × 400 Gbps，与 UB Link 静态复用部分 SerDes 端口让 UB 的 Scale-Out 协议运行在以太网上
PCIePCIe 5.0 x16，向下兼容，支持 EP/RC 静态选择Host、设备及标准 PCIe 生态连接

UB 提供两类内存访问语义：

语义工作方式典型操作
URMA通过 Jetty 队列、Doorbell 和完成机制进行异步通信，执行远端内存搬运和消息操作Read、Write、Send、Notify，以及部分 Atomic 操作
UB MemoryCore 向 UB 端口发起同步访问，经地址解析、地址翻译和权限校验后访问对端内存Load/Store 语义及 Atomic 操作

URMA 适合与计算流水重叠的异步通信，UB Memory 提供同步 Load/Store 访存。两者都要求软件处理地址权限、内存一致性、完成通知和错误。华为云 A5 文档分别给出 URMA 支持 8K 超节点范围、UB Memory 最大支持 1K 超节点范围的口径，两种语义的适用规模不能混用。[13]

CCU（Collective Communication Unit）接收系统调度器下发的集合通信任务，按软件预置的算法执行节点间搬运、同步和 Reduce 计算。白皮书列出的算法包括 Broadcast、ReduceScatter、AllGather、AllReduce、All2All 和 All2Allv。CCU 为集合通信卸载提供硬件条件，实际效果仍取决于 HCCL 软件路径、消息大小、拓扑和负载均衡。

3.6 超节点规模：架构能力与交付配置 ​

950 白皮书给出最大 8192 卡超节点、整体集群超过 128K 卡的架构支持能力；当前 Atlas 950 SuperPoD 产品页给出 64 或 1024 卡配置。[10][12] 前者说明协议和架构能力，后者是具体交付配置。

华为云 A5 组网文档以 1024 个 NPU 模组为例，描述 16 个计算柜、8 个超平面和两级灵衢交换组织。[14] 昇腾社区产品规格页与云侧 A5 文档可能采用不同的机柜交付口径，项目中应同时核对产品 SKU、云资源形态和交付设计。

总结 ​

达芬奇架构围绕 Cube、Vector 和 Scalar 组织计算，通过 L1/L0/UB、GM 和 MTE 管理数据流动，再用指令队列与事件同步形成流水。理解这套结构，是分析昇腾算力、设备内存和 Kernel 性能的基础。

910C 的公开资料展示了双计算 Die、128 GB 级设备内存和 Atlas A3 超节点组织方式；brain3 实机结果则说明，论文、标准整机和当前可见环境必须分开核对。950 采用第三代达芬奇架构，增加多种低精度格式，并引入 SIMD/SIMT 混合编程、Cube–Vector 融合、NDDMA、灵衢 2.0 和 CCU，以 950PR、950DT 适配不同负载。

软件栈分层 ​

框架和应用通过 CANN（Compute Architecture for Neural Networks）使用昇腾设备，模型开发者通常不需要直接编写硬件指令。[15]

组件职责使用边界
驱动与固件设备初始化、资源管理、设备通信和硬件控制须与操作系统、硬件和 CANN 配套
Runtime管理设备、Context、Stream、Event、设备内存和任务功能可类比 CUDA Runtime 的部分职责，但接口不同
GE（Graph Engine）在支持的场景中处理计算图、编译优化和执行控制不是所有 PyTorch Eager 算子的必经阶段
AOE在支持的场景中自动调优算子或图能力以具体版本为准
AscendCL提供设备管理、模型加载与执行、单算子调用和媒体处理等 API框架内部路径不一定都直接经过同一 API
内置算子与 OPP提供目标产品和版本支持的算子资源先检查精度、形状和布局支持
Ascend C用 C/C++ 风格接口组织计算、搬运和同步用于自定义算子和针对性优化
TBE通过 DSL 等机制描述和生成算子按既有实现、版本支持和迁移成本选择
HCCL提供 AllReduce、AllGather、ReduceScatter、Broadcast、All2All 等集合通信底层可使用 HCCS、RoCE 或其他受支持路径

部署检查 ​

  1. 核对设备与 SoC：记录整机、NPU、HBM 和互联配置。可用 npu-smi info 查看基本信息；安装 CANN 与 Python ACL 后，可用 python3 -c "import acl;print(acl.get_soc_name())" 查询 SoC 型号。
  2. 按兼容矩阵安装软件：驱动、固件、CANN、PyTorch、torch_npu、HCCL、推理引擎和模型框架必须配套。Beta 版本适合验证新特性，不应未经测试直接用于生产。
  3. 先验证基础能力：依次检查设备可见性、内存分配、基础矩阵算子、单机多卡通信和跨节点通信，再运行完整模型。
  4. 核对机房条件：确认机柜功率、供电制式与冗余、风冷或液冷条件、网络布线、光模块和存储配套。
  5. 保留验收证据：记录测试配置、软件版本、原始日志和监控数据，确保结果可复现。

从单卡到集群逐级测量 ​

  1. 计算映射：检查矩阵计算是否高效落到 Cube，Vector 和 Scalar 是否成为瓶颈，精度和布局是否匹配。
  2. 数据路径：检查分块复用、搬运对齐，以及不必要的 GM 往返和格式转换。
  3. 流水与同步：检查搬入、计算、搬出能否重叠，以及屏障、缓冲区冲突和事件等待。
  4. 主机与调度：检查小 Kernel 下发、Host–Device 拷贝和主机逻辑的耗时。
  5. 多卡通信：分别测量单机、同超节点跨机和跨超节点路径，固定通信原语、消息大小、卡数及并发条件。
  6. 业务指标：训练记录稳定步时、吞吐和扩展效率；推理区分 TTFT、TPOT、吞吐与 P95/P99 尾时延，并固定并发数、输入输出长度和模型精度。
  7. 可靠性：观察长时间负载下的温度、功耗、链路告警、故障隔离和恢复过程。

TTFT 是首 Token 时延，TPOT 是 Decode 阶段平均每输出 Token 时延。MFU 是模型实际执行 FLOPs 与理论可用 FLOPs 的比值，计算时要统一分子和分母口径。跨平台比较还应固定模型、精度、批量、并行策略和软件版本，避免用不同条件下的峰值代替应用性能。
