昇腾 910B3 硬件架构与 CANN 软件栈 ​

理解昇腾平台，需要把计算单元、存储与数据搬运、运行时和框架适配连接起来。本文以原稿记录的一台八卡 Ascend 910B3 服务器为线索，先解释硬件如何组织计算，再介绍 CANN 各组件如何支持算子执行与分布式训练。

资料范围：文中的服务器参数与测量值来自原始环境记录，本次整理未连接设备复测，原始命令输出、测试配置和测量日期尚未附全。这些数值不代表所有 910B3 设备的规格或性能，更不能直接套用于 910C。软硬件能力和安装路径应以目标产品、CANN 版本及兼容性文档为准。

相关阅读：昇腾软硬件架构与资料导读。

1. 硬件架构: Ascend 910B3 ​

1.1 概述 ​

Ascend 910B3 是华为昇腾系列 AI 处理器，采用达芬奇（Da Vinci）架构。原始记录中的服务器配备 8 张 910B3 卡，设备间连接类型标记为 HCCS。连接可达性、物理链路和集合通信性能需要分别核对。

1.2 达芬奇 (Da Vinci) 架构核心设计 ​

昇腾的计算资源可按矩阵、向量与标量控制三类职责理解。Cube 执行矩阵乘加，Vector 处理逐元素运算、归约及激活等操作，Scalar 负责地址计算和控制流。

910B 系列的算子编程还需要理解矩阵计算资源 AIC 与向量计算资源 AIV 的分离组织。不能将早期达芬奇架构中“三种单元位于同一核心”的示意图，直接当成所有型号的物理布局；具体核数、资源配比和同步能力应查阅对应产品文档。

资源或职责典型任务与 GPU 的功能类比及边界
Cube / AIC矩阵乘加、GEMM可类比 Tensor Core 的矩阵加速职责，执行模型不等同
Vector / AIV激活、归约、逐元素处理不能简单视为一组 CUDA Core，任务组织与指令接口不同
Scalar控制流、地址和标量计算属于控制与标量处理职责，不对应独立的 CUDA 软件层

架构对性能的直接影响，是算子需要组织好矩阵计算、向量计算和数据搬运之间的依赖与重叠。是否提高利用率或能效，取决于工作负载与实现，不能仅凭资源分工判定优于 GPU。

1.3 内存层次 ​

存储系统应按计算和搬运路径理解，而不是画成所有数据必须逐层经过的单一缓存链：

  • HBM / GM：HBM 是物理高带宽内存，GM 是算子编程中的全局内存视角。原始记录中单卡容量为 64 GB。
  • L2 Cache：服务设备全局访存的共享缓存，其命中行为与软件显式管理的局部缓冲区不同。
  • L1 与 L0A/L0B/L0C：用于矩阵数据准备、输入与累加结果等，具体职责和访问路径由目标架构决定。
  • Unified Buffer（UB）：向量计算使用的重要局部存储，不能从存储图中省略，也不应概括为“Vector 的 L0”。
  • MTE（Memory Transfer Engine）：承担支持路径上的数据搬运；高性能算子通过分块和流水线，将搬运与计算重叠，并显式处理依赖。

原稿记录 ascend-dmi --bw -t d2d 测得约 1538 GB/s，并将其解释为 HBM 带宽。该解释需要补充工具版本、测试说明、数据规模和计时口径后核实：D2D 命名本身不能证明测得的就是 HBM 硬件带宽。因此本文将其保留为待核对的测试记录，不作为产品带宽规格或跨平台对比依据。

注：CANN 的商业版本号和内部版本号需要区分。本服务器上的 CANN 商业版本为 8.0.1（对应 ascend-toolkit 目录名），但 runtime/compiler/hccl 等内部组件版本号均为 7.6.0.2.220（即 7.6 系列）。在查阅版本兼容性矩阵时需注意这个区分。

2. CANN 软件栈 ​

CANN 是连接框架与昇腾硬件的重要软件平台，提供运行时、编译、算子与通信等能力。驱动和固件与 CANN 配套协作，但属于需要单独核对兼容性的组件。下面的层次图用于说明职责，不表示所有任务都严格依次经过每一层。

2.1 栈全貌 ​

CANN (Compute Architecture for Neural Networks) 是华为昇腾的异构计算架构，类似于 NVIDIA 的 CUDA 平台 + 工具链集合。

2.2 各层详解 ​

2.2.1 驱动层 (Driver) ​

最底层，负责：

  • 与固件 (Firmware v7.5.0.5.220) 通信
  • PCIe 设备管理（/dev/davinci0 ~ /dev/davinci7）
  • 内存映射、DMA 传输
  • 通过 npu-smi 工具导出设备状态

当前服务器驱动版本：24.1.0.3

2.2.2 运行时层 (Runtime) ​

可从功能上类比 CUDA Runtime 的部分职责。负责任务分发到 AI Core/AI CPU、设备内存管理、Stream 与 Event 管理。Runtime 下层是任务调度层（Task Scheduler, TSC），负责将计算任务派发到具体 AI Core，通常由上层框架与运行时接口封装，排查性能问题时仍可能需要关注其调度开销。

2.2.3 算子层 (Operator Layer) ​

使用 CANN 算子时，应区分“调用已有算子”和“开发自定义算子”，不要将不同技术按固定的高低等级排列。

方式作用选择依据
内置算子与算子包提供目标产品和版本支持的算子实现优先检查已有实现是否覆盖精度、形状和布局
Ascend C使用 C/C++ 风格接口组织计算、搬运和同步需要自定义逻辑或针对工作负载优化时采用
TBE（Tensor Boost Engine）基于 DSL 等机制描述和生成算子按既有实现、版本支持及迁移成本选择

OPP（Operator Package）提供算子相关资源，安装布局随版本变化。原环境中的路径为 /usr/local/Ascend/ascend-toolkit/latest/opp/，不能假定所有安装均采用相同目录。

CUDA 生态同样包含算子库、编译器与多种编程接口。两者都应按实际调用路径选择工具，不宜概括为“CUDA 只有一种模型、CANN 有三个优化等级”。

2.2.4 图编译与优化层 ​

  • GE（Graph Engine）：提供计算图处理、编译和优化能力；是否使用该路径取决于框架和执行模式。它不属于驱动层，也不是所有 PyTorch eager 算子执行的必经阶段。
  • AOE（Ascend Optimization Engine）：用于支持场景下的自动调优，具体能力以版本文档为准。

图编译、算子编译与运行时调度解决不同问题。GPU 生态也有框架编译器和推理优化工具，不能将两者简化为“一个有图编译，另一个没有”。

2.2.5 AscendCL (Ascend Computing Language) ​

应用开发 API 层，提供 C/Python 接口。功能包括：

  • 设备/Context/Stream 管理
  • 模型加载与推理执行
  • 媒体数据预处理（图像编解码、缩放等，即 DVPP 模块）
  • 单算子调用

框架适配层会使用 CANN 的算子与运行时等接口，不同执行路径不一定经过相同 API。应用开发者则可根据需要直接使用 AscendCL。

2.2.6 HCCL (Huawei Collective Communication Library) ​

集合通信库，对应 NVIDIA 的 NCCL。提供：

  • AllReduce、AllGather、ReduceScatter、Broadcast 等集合操作
  • 利用平台支持的 HCCS、网络等通信路径，具体由部署与版本决定
  • 通信原语和算法实现

本服务器 HCCL 版本：7.6.0.2.220，8 卡之间通过 HCCS 链路全互联。

2.2.7 框架适配层 ​

  • torch_npu：PyTorch 与 CANN 的适配层。为 PyTorch 提供昇腾设备后端及算子适配，不是将任意 CUDA API 或 CUDA kernel 自动转换为 NPU 实现。版本需与 PyTorch 和 CANN 同时兼容。
  • MindSpore：华为自研框架，对 Ascend 有原生支持，不依赖 torch_npu。

5. 编程模型与迁移边界 ​

NVIDIA GPU 主要通过线程、线程块与 warp 组织 SIMT 执行，并使用专门的矩阵计算资源。昇腾算子开发则更需要显式考虑矩阵与向量资源、局部缓冲区、数据分块和流水线同步。两者都包含专用计算资源，差别不能简单归结为“GPU 同构、NPU 异构”。

迁移 PyTorch 工作负载时，先检查标准算子在目标后端的支持范围、精度和布局要求。自定义 CUDA 扩展通常需要选择已有 NPU 算子替代，或使用 Ascend C 等方式重新实现；不能假定改动设备字符串即可迁移全部逻辑。

优化时应分别测量计算、数据搬运、通信和主机调度开销。计算资源可以并行，不代表所有任务天然重叠；依赖、同步和缓冲区容量都可能限制流水线。图模式也只是可选择的执行路径，不能将每个任务都描述为“先由 GE 分析，再分发到计算单元”。
