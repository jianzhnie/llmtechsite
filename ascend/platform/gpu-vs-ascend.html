GPU 与昇腾：大模型训练与推理生态对比 ​

本文比较 NVIDIA GPU 与华为昇腾 NPU 在大模型训练和推理中的实际差异，重点讨论硬件、软件栈、框架支持和迁移成本。资料以厂商文档和开源项目说明为准，核对日期为 2026 年 11 月 24 日。

不同资料的价格、MFU 和 tokens/s 往往采用不同模型、并行策略与测试条件，本文不用这些数字给平台排名。选型时先确认工作负载，再用同一模型和指标做验证。

1. 先看结论 ​

NVIDIA 的优势是成熟的 CUDA 生态、丰富的优化算子和较多可直接复用的研究代码。昇腾可以依托 torch_npu、CANN、MindSpeed 和 vLLM-Ascend 覆盖常见训练与推理流程，但具体模型、算子和版本的支持范围需要逐项核对。

场景优先考虑选择依据
已有大量自定义 CUDA KernelNVIDIA GPU直接复用现有实现，避免重写和精度验证
标准 PyTorch 微调两者都可评估GPU 生态更成熟；昇腾可用 LLaMA-Factory、ms-swift 等框架
大规模预训练按集群和软件路径实测比较有效吞吐、扩展效率和长时间稳定性，不只看单卡峰值
已有昇腾设备或国产化部署要求昇腾 NPU复用现有资源，满足供应和部署约束
vLLM 在线推理两者都可评估先查目标模型在 vLLM 与 vLLM-Ascend 中的支持状态，再比较 SLO
MoE 训练或推理按通信路径选择Scale-Up 互联、专家并行实现和通信算子通常比单卡峰值更关键
追求最低成本实测后决定比较单位有效产出成本，不能只比较卡时价格

两种平台不存在脱离工作负载的固定优劣。对标准模型和成熟框架，迁移通常不难；对自定义算子、复杂并行和极限性能优化，成本会明显增加。

2. 硬件与集群：先统一比较口径 ​

2.1 设备内存和互联 ​

下表列出部分公开规格，便于确定容量和互联的分析起点。不同产品的精度、稀疏条件和带宽方向并不完全一致，因此不在这张表里排列算力高低。

产品设备内存与带宽互联信息
NVIDIA H100 SXM80 GB；3.35 TB/sNVLink 900 GB/s
NVIDIA H200 SXM141 GB；4.8 TB/sNVLink 900 GB/s
NVIDIA B200 SXM180 GB；最高 8 TB/sNVLink 5，GPU 间带宽 1800 GB/s
Atlas A3 所用昇腾 NPU产品页按每 NPU 128 GB、最高 3.2 TB/s 列出Atlas 900 A3 产品页列出双向 784 GB/s D2D 带宽
Atlas 350（950PR）112 GB HBM；1.4 TB/s2 卡互联双向最高 424 GB/s；4 卡全互联双向最高 318 GB/s
Atlas 950 SuperPoD 所用 950DT产品页按每 NPU 96 GB、最高 4.0 TB/s 列出采用灵衢 2.0；具体带宽按产品和组网配置核对

这些数字分别来自 NVIDIA、华为企业业务和昇腾社区产品页。[1][2][3][4][5][6][7] H100/H200 的算力参数还涉及稀疏条件，B200 的内存容量在不同产品资料中也可能采用不同配置。引用时应回到目标 SKU 的原始规格表。

设备内存主要用于容纳权重、激活、梯度、优化器状态和 KV Cache。容量不足时，需要分片、量化或增加设备。内存带宽影响权重和中间数据的供给能力，但不能直接等同于应用吞吐。

2.2 Scale-Up 与 Scale-Out ​

  • Scale-Up 关注服务器或超节点内部的高速互联，适合张量并行、专家并行和远端内存访问等频繁通信。
  • Scale-Out 通过 InfiniBand、RoCE、UBoE 等网络连接更多节点或超节点，用于扩大集群规模。

NVIDIA 常见组合是 NVLink/NVSwitch 加 InfiniBand 或 RoCE。昇腾 A3 使用 HCCS/灵衢 UB 等互联，950 引入灵衢 2.0、URMA、UB Memory 和 CCU。CloudMatrix384 论文还分别描述了 UB、RDMA 和 VPC 三个网络平面，不能把数据中心业务网络与 NPU 通信平面混为一谈。[8]

统一编址只表示资源可以按相应地址体系访问，不表示远端内存与本地 HBM 具有相同的时延和带宽。评估 MoE 或大规模推理时，应分别测量节点内、同超节点跨节点和跨超节点通信。

3. 软件栈：接口相近，实现不同 ​

层级NVIDIA GPU昇腾 NPU
基础框架PyTorch、JAX、TensorFlowMindSpore；PyTorch + torch_npu
运行时与编译CUDA Runtime、CUDA Graph 等CANN、GE、Runtime、AOE 等
集合通信NCCLHCCL
分布式训练Megatron-LM、DeepSpeed、FSDPMindSpeed-LLM、MindSpeed-MM、Megatron 适配路径、FSDP 等
推理引擎vLLM、TensorRT-LLM、SGLang、TritonvLLM-Ascend、MindIE、SGLang 适配路径
自定义算子CUDA、Triton、CUTLASSAscend C、TBE、Triton-Ascend
性能分析Nsight、PyTorch Profilermsprof、MindStudio 等

torch_npu 是 PyTorch 的昇腾设备后端和算子适配层，不是 CUDA Kernel 的自动转换器。[9] 标准 PyTorch 算子可以复用不少模型代码，但自定义 CUDA 扩展、特定 Attention 实现和通信优化通常需要替换或重新实现。

vLLM-Ascend 则提供了复用 vLLM 接口和部署习惯的路径。其模型页面把支持状态区分为 Supported、Experimental、Unverified、Unmaintained 和 Unsupported，并进一步列出硬件、图模式、并行和量化能力。[10] “vLLM 支持某个模型”不表示该模型在 vLLM-Ascend 上具有相同的功能和性能。

4. 训练与推理框架怎么选 ​

4.1 训练与后训练 ​

需求可选方案核对重点
快速 SFT、LoRALLaMA-Factory、ms-swift模型、训练方式、硬件和融合算子是否在支持列表中
大规模预训练Megatron-LM、MindSpeed-LLMTP/PP/DP/CP/EP 组合、通信效率和长稳训练
GRPO、PPO 等后训练verl、ms-swift、MindSpeed RL 等rollout 引擎、训练后端、精度和模型组合
多模态训练MindSpeed-MM、ms-swift模型架构、数据管线和多模态算子
自定义训练算子CUDA、Ascend C、TBE、Triton-Ascend精度、性能、维护成本和版本兼容性

LLaMA-Factory 的 NPU 文档列出了 Atlas A2/A3 和 950 系列，以及 PT、SFT、RM、DPO、Full、Freeze、LoRA、DDP、FSDP、FSDP2 和 DeepSpeed 支持情况。[11] ms-swift 提供训练、推理和部署能力，但其文档明确列出了不支持或尚未完整验证的项目，例如 QLoRA 和使用 SGLang 作为部署后端。[12] 选型应阅读当前版本的支持范围，而不是只看“支持 NPU”的概括。

verl 的昇腾文档提供 vLLM 或 SGLang 与 FSDP/Megatron 的组合方式。[13] 这类 RL 框架同时管理训练和 rollout，任何一端的模型或算子不受支持，都会影响整个流程。

4.2 推理与部署 ​

  • vLLM / vLLM-Ascend：适合评估统一的 vLLM 使用路径，先检查模型和功能支持，再做吞吐与时延测试。
  • TensorRT-LLM：适合需要 NVIDIA 深度优化、量化和图优化的场景。
  • MindIE：适合采用华为原生推理栈的部署环境。
  • SGLang 及其 NPU 适配路径：适合需要结构化生成和复杂请求处理的场景，支持情况随后端和版本而变。

推理评估至少应固定模型、权重精度、输入输出长度、并发数、批量、并行策略和 KV Cache 配置。训练关注稳定步时、有效吞吐、MFU 和扩展效率；在线推理则要同时记录 TTFT、TPOT、吞吐及 P95/P99 尾时延。

5. 从 CUDA 迁移到昇腾：按代码类型评估 ​

5.1 先分类，不先估工期 ​

代码类型迁移工作主要风险
标准 PyTorch 模型安装配套环境，调整设备与通信后端个别算子回退、精度或布局差异
使用成熟训练框架的模型核对框架支持矩阵，替换不兼容组件分布式策略和自定义扩展
自定义 CUDA Kernel用现有 NPU 算子替代，或以 Ascend C/TBE 重写数值一致性、性能退化和维护成本
复杂 MoE 通信与并行重新验证 EP、通信库、拓扑和调度All-to-All 时延、负载不均和跨节点稳定性
生产推理服务验证模型、量化、连续批处理、KV Cache 和监控尾时延、吞吐、故障恢复与版本升级

迁移成本不只是修改 API。精度对齐、性能调优、长时间测试和后续版本维护通常更耗时，因此不宜在测试前给出统一的“几周”或“几人月”估算。

5.2 推荐的迁移顺序 ​

  1. 盘点依赖：记录模型、算子、权重精度、并行策略、推理引擎和自定义扩展。
  2. 锁定兼容组合：按官方矩阵匹配驱动、固件、CANN、PyTorch、torch_npu、框架和推理引擎，避免只升级其中一个组件。
  3. 先做单设备 smoke test：检查设备可见性、内存分配、基础算子和模型前向结果。
  4. 做数值对齐：使用固定输入比较输出、损失、梯度和评估指标，定位回退算子。
  5. 再做性能优化：通过 Profiler 检查算子、数据搬运、Host 同步、通信和流水线，而不是先改模型结构。
  6. 完成系统验收：覆盖多卡、多节点、长序列、高并发、故障恢复和长时间运行。

5.3 常见误区 ​

  • 把“能够运行”当成“性能相当”。
  • 把 GPU 的支持列表当成昇腾的支持列表。
  • 只替换 torch.cuda 或 NCCL 名称，不检查自定义算子和通信路径。
  • 忽略权重精度、数据布局和量化方式的差异。
  • 用单卡峰值推算集群吞吐，或用低并发结果代表生产高峰。

6. 成本与验收：比较有效产出 ​

TCO 应包括设备或云资源、供电与散热、迁移和调优人力、测试验收、故障恢复以及后续维护。卡时价格只是其中一项。

可以使用下面的指标做同口径比较：

  • 训练：完成目标精度和 token 数所需的总成本、总时间、能耗与人力。
  • 推理：满足 TTFT、TPOT 和尾时延约束时，每百万有效输入/输出 token 的成本。
  • 集群：达到目标扩展效率和稳定运行时长所需的有效资源，而非名义卡数。

验收时保留模型版本、权重精度、软件版本、并行策略、原始日志和监控数据。没有这些信息，不同平台之间的性能和成本数字很难复现，也不适合用来决策。
