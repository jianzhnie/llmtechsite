UltraEP：在关键路径上跑实时专家均衡 —— 小红书 × 北大的 MoE 负载均衡实践 ​

摘要：UltraEP 是小红书 dots infra 团队与北京大学联合开源的专家并行（EP）负载均衡库（2026 年 7 月发布 v1.0.0，已用于小红书生产 MoE 训练）。与 EPLB 等基于历史负载的"预测式"均衡不同，UltraEP 是首个基于门控后真实负载、在每个 microbatch 的每一层实时执行均衡的系统：它用 GPU 上的 Quota-Driven 规划器联合求解"专家复制 + token 重路由"，用 Persistent Tile Streaming 与自适应中继把热点专家权重搬进高带宽 scale-up 域内的冗余 slot，并把全部开销压缩在前向约 300 µs 以内（仅占端到端 step 时间的 1–2%）。在 106B–671B 的多个 MoE 模型上，UltraEP 平均达到理想强制均衡吞吐的 94.3%，相对不均衡基线提升 1.49×，跨 rank 不均衡度从 1.30–4.01 压至 1.01–1.04。

关键词：MoE、专家并行、负载均衡、专家复制、token 重路由、Rack-Scale Node、Scale-up 域

1. 背景：预测式均衡为什么失效 ​

MoE 训推框架的工程实现常默认一个"理想假定"：路由后的专家负载已被算法侧（auxiliary loss、routing bias）抹平，每张卡接收的 token 数接近一致。但算法均衡只发生在统计意义上；落到每个 microbatch、每一层，热点专家仍然频繁更替，理想与实际吞吐之间可出现多达 2 倍的偏差：过载 rank 成为计算 straggler，拖慢整组；token all-to-all 的字节数由最热 rank 决定；过载 rank 的激活显存峰值飙升甚至 OOM。

最具代表性的系统方案是 DeepSeek 的 EPLB：根据上一个时间窗口的历史路由，周期性重排专家副本。这类预测式方法隐含前提是负载相对静态——而细粒度 MoE（几百个"小"专家，如 Qwen3-235B、Kimi K3 的 896 专家）的负载高度动态，历史信息很快过时，冷热专家预测频频失准，均衡操作甚至变成负优化。

维度预测式（EPLB / LPLB）UltraEP
负载依据历史路由统计门控后的真实负载（当前 microbatch × 当前层）
决策时机周期性离线重排，滞后于真实负载gate 之后、dispatch 之前，关键路径内
操作频率低频（窗口级）每个 microbatch × 每层

2. UltraEP 是什么 ​

  • 论文：UltraEP: Unleash MoE Training and Inference on Rack-Scale Nodes with Near-Optimal Load Balancing（arXiv:2606.04101，2026-06）
  • 技术报告：https://dots-infra.github.io/UltraEP/zh/
  • 代码：https://github.com/Dots-Infra/UltraEP（v1.0.0，2026-07-15 发布，已部署于小红书生产 MoE 训练）
  • 硬件要求：NVIDIA SM90/SM100，CUDA 12.3+（SM90）/ 12.9+（SM100），scale-up 域内 GPU 具备 NVLink/P2P 互通

UltraEP 把自己定位为一个独立的 Python/CUDA 运行时：负责冗余专家状态管理、均衡方案求解与专家传输，与 DeepEP 等 token all-to-all 通信库解耦——用官方的话说："DeepEP 优化 MoE token 的通信效率，UltraEP 实时调度专家资源"。在 Megatron-LM / SGLang 等主流框架上，只需数百行代码即可接入。

五条设计原则：自包含代码库；拓扑感知的复制（限制在 scale-up 域内）；GPU-native 内核（暴露开销 < 300 µs，约占 step 时间 1–2%）；广泛兼容（DP/PP/VPP、activation checkpointing、FP8、CUDA Graph）；显存高效（跨层复用、运行时零动态分配）。

3. 核心思想：精确负载 × 实时响应，以及 300 µs 的关键路径预算 ​

UltraEP 的方案看似激进但最直接：在 gate 结束、token dispatch 开始之前——这是唯一能拿到"当前层每个专家实际收到多少 token"的时刻——现场完成热点专家复制与 token 分流。预测式方法可以提前掩盖或平摊开销，而 UltraEP 的开销全部暴露在关键路径上、且以 microbatch 为粒度高频发生。它成立依赖一个通信前提 + 一系列控制面/数据面优化：

  • 通信前提：整个 EP group 部署在同一个高带宽 scale-up 域（NVLink 域；新兴的机柜级节点 RSN 把这一域扩大到数十张 GPU），热点专家的权重复制走机内高速互联，绝不跨机；
  • 控制面：GPU-native 在线求解器联合求解专家复制与 token 重路由；
  • 数据面：专用通信内核完成专家权重与梯度的动态传输。

实测（EP64）前向三个操作合计仅 0.30–0.43 ms，即"300 µs 预算"的由来；反向复用前向缓存的方案、不重求解，梯度归约与 router/attention 反向重叠，暴露开销接近于零。

4. 控制面：Quota-Driven 规划器 ​

拿到真实负载后，规划器要同时回答两个问题：哪些热点专家需要副本，以及每个固有实例和副本各承担多少 token。UltraEP 的答案是引入 额度（Quota）——重路由后各专家实例应接收的 token 负载——把专家复制和 token 重路由放进同一个优化过程：每一步探索既能实例化新副本，也能更新目标 quota 分布。

工程约束包括：每 rank 的冗余 slot 数量上限；同一逻辑专家禁止在同一 rank 上重复部署；新副本必须获得最低有效 quota（默认 1024 token，避免为少量 token 建收益有限的副本）。quota 确定后执行本地优先分解：token 优先使用本 rank 的实例，本地 quota 用完后按其他实例的剩余额度发往远端，在满足负载上限的同时压低跨 rank 流量。所有 rank 拿到同一份全局负载后各自独立运行相同的确定性求解，方案天然一致，无需为此增加一次全局同步。

对比"同样用精确负载、但沿用 EPLB 式求解 + Round-robin 重路由"的 EPLB+：UltraEP 将平均负载不均衡度从 1.19 降至 1.03，求解延迟降低 27.4%，平均冗余 slot 用量减少 57.9%。

5. 数据面：Persistent Tile Streaming 与中继扇出 ​

规划只是问题的一半——目标 rank 必须先拿到专家的当前权重才能接 token（训练中权重每步都在变，副本必须现拷现用）。UltraEP 的数据面由两个专用内核构成：

  1. Persistent Tile Streaming：把专家权重/梯度切成固定大小的 tile，将复制方案转换为设备端传输任务流；持久化 kernel 持续从任务流领取下一个 tile，无需为每个副本单独启动一次通信。tile 之间双缓冲流水线——一个 tile 正在写入远端时，kernel 已取下一个 tile 的任务索引并解析地址、加载数据；任务查找、动态寻址与同步等控制开销全部并入数据搬运过程。
  2. Chunk Streaming Relay（自适应中继）：当热点专家要复制到多个 rank 时，固有专家所在的源 rank 会成为一对多发送瓶颈。源 rank 按发送负载从副本 rank 中选出压力较低的作为中继，把集中式多播分摊成一棵"流式分发树"；中继以 chunk 为单位边收边转发，源端发送与中继转发之间无全局 barrier。副本数 < 4（默认 RELAY_MIN_REPLICAS）或域内 ≤ 8 卡时自动退回直连模式。

效果：EP64、256 专家端到端测试中权重同步稳定在 0.19 ms 左右，高倾斜场景下自适应中继带来最高约 1.7× 加速；通信设计比评估中的主流通信后端快 3.1–5.5×。

6. 显存设计：跨层复用的冗余 slot ​

  • 每个 EP rank 预留固定数量的冗余 slot（默认可配），存放当前层的副本权重与梯度；冗余 slot 不维护优化器状态——副本梯度在反向实时归约回固有专家，参数更新只对固有专家进行；
  • 权重/梯度 buffer 跨 MoE 层复用：前向算完当前层，同一组空间被后续层继续使用，反向再按前向缓存的方案把权重重分发进槽位。因此冗余副本的显存开销不随层数增长。以 Qwen3-235B-A22B 为例：每层独立预留需每 rank 9.9 GB，跨层复用后仅需 36 MB 权重 + 72 MB 梯度 = 108 MB（约 -98.9%）；
  • 运行时零动态显存分配；均衡生效还缩小了 DeepEP token 接收 buffer 的 worst-case 预留。

前向在每个 MoE 层插入四步（update_placement → weight_sync 异步 → reroute → 等权重就绪后 dispatch）；反向通过三个前向为恒等映射的 autograd hook 完成：RestoreReplicaWeights（专家 Dgrad 前阻塞式恢复副本权重）、StartGradReduce（专家反向后异步启动梯度归约）、JoinGradReduce（attention 反向完成后 join 事件）。反向复用前向缓存的 placement，不重求解。update_placement 返回 (physical_to_logical_map [P], logical_to_physical_map [L, EP], logical_replica_counts [L]) 三个只读 CUDA int32 视图，也支持外部方案通过 weight_sync / grad_reduce 的关键字参数注入。

9. 与 DeepEP / MoonEP / EPLB 的关系 ​

DeepEPMoonEPUltraEP
关注点token dispatch/combine 通信效率通信 + 均衡（绑定自家 buffer 体系）纯负载均衡，独立运行时
均衡依据不内置（V2.5 起提供 lb_* 原语）真实负载（规划+零拷贝）真实负载（quota 规划+中继传输）
与 token 通信库—深度耦合解耦，复用 DeepEP 等
决策频率—每层每 microbatch × 每层
关键路径开销—planning 计入通信柱前向 ~300 µs，反向 ~0

三点值得注意：其一，UltraEP 的低层通信内核实现借鉴了 DeepEP 与 HybridEP（README 致谢），与 DeepEP 是组合而非替代关系；其二，DeepEP V2.5 新增的 lb_prefetch_weights / lb_reduce_grads 与 MoonEP 的动态冗余专家、UltraEP 的实时复制同属一个技术脉络——"均衡原语"正成为 EP 基础设施的标配；其三，UltraEP 把均衡做进了关键路径：这只有在 scale-up 域足够大（RSN）、且规划与传输都被压到百微秒级时才划算，它赌的是"高带宽机内互联会持续扩大"这一硬件趋势。

10. 调优与可观测性 ​

全部行为由 ULTRA_EP_* 环境变量控制，重要项：

变量（默认）作用
ULTRA_EP_GRAD_REDUCE_NUM_SMS（42）梯度归约持久内核占用的 SM 数，按模型 profile 调到"刚好完全藏进反向计算"
ULTRA_EP_GRAD_REDUCE_DETERMINISTIC（1）确定性非原子归约，保证逐位可复现
ULTRA_EP_WEIGHT_SYNC_PLAN_MODE（adaptive）direct / adaptive / force_relay；≤8 卡域强制 direct
ULTRA_EP_QUOTA_MIN_TOKENS_PER_REPLICA（1024）新副本最低 token 配额
ULTRA_EP_QUOTA_LOCALITY_AWARE（1）本地优先的 per-rank quota 分解，压低跨 rank 流量
ULTRA_EP_QUOTA_REROUTE_INTERLEAVE（1）交织 token 顺序，避免后续 dispatch 拥塞

可观测性方面，内置负载 profiler 以极小开销记录每个 microbatch、每个专家在 reroute 前后的负载，可用自带的 HTML Load Viewer 按 EP group / 层 / microbatch 下钻，直观看到均衡前后分布（官方示例：某层某 microbatch 的 max/mean 从 1.868 降到 1.010，per-rank 堆栈由参差变为齐平）——让"均衡效果"从端到端吞吐的间接推断变成直接可视的证据。

总结 ​

UltraEP 的贡献在于把 MoE 负载均衡从"周期性、预测式、离线"升级成"逐层、逐 microbatch、在线且精确"的系统能力，并证明了这条更激进的路径在生产中的可行性：

  • 正确性来自真实负载：gate 之后决策，不存在预测偏差，数学等价性不变（重路由只改物理映射）；
  • 可行性来自 scale-up 域：专家复制限定在 NVLink/RSN 高带宽域内，把"实时"从不可能变成 300 µs；
  • 性价比来自系统设计：quota 联合求解省 slot、跨层复用省显存、tile streaming + relay 省时间、反向重叠省关键路径——最终交出 94.3% 理想吞吐、1.49× 提升的成绩单。

随着 EPLB、MoonEP、DeepEP-lb、UltraEP 等方案相继落地，"算法侧均衡保质量 + 系统侧均衡保吞吐"的双层均衡架构正在成为大规模 MoE 的事实标准，而 UltraEP 是其中把实时性做到极致的一个。
