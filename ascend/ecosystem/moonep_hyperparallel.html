MoonEP 接入 HyperParallel：910C 上的实现与性能分析 ​

MoE 训练中，每个 token 只选择少数专家计算。专家分布在不同设备上，因此每层都要先把 token 发给专家，再把结果送回来。MoonEP 优化的就是这段专家并行通信，并通过临时复制热点专家来分散负载。

把 MoonEP 接入训练框架，不能只替换一次通信调用。它还会改变 token 的落点、专家计算布局和权重获取方式。本文介绍这条链路如何在 HyperParallel 中落地，以及为什么“通信快了数倍”并不等于“训练也快了数倍”。

先看验证状态：截至原始记录最后一次更新（2026 年 10 月 30 日），接入实现已有算子、规划器和小规模梯度测试，但完整训练的跨后端数值筛查仍未通过既定阈值。本文的训练性能数据只能视为性能观察，不能称为已验证的正确训练加速。本次为文档整理，未重新运行代码或硬件测试。

配套源码见 MoonEP-Ascend-910C，910C 构建与支持范围见 适配分支 README。本文提到的 npu_patch/ 路径属于 MoonEP 适配仓库，hyper_parallel/ 路径属于 HyperParallel 仓库；实验日志路径是原始工作区中的记录，不是本站附件。

相关阅读：MoonEP 原理、910C 适配与通信验证。

2. 为什么不能只替换 all-to-all ​

2.1 接收容量固定，就必须处理超额负载 ​

设 EP 组有 R 个 rank，每个 rank 输入 S 个 token，每个 token 选择 K 个专家。全组共有 RSK 条路由，因此每 rank 的平均份额为 SK。

本文讨论的接入路径按这个平均份额设置逻辑接收容量：

NvS=S×K.

这里是 SK 条路由记录，不是 SK 个不同 token。只有路由完全按 rank 均衡时，各 rank 的原始接收量才都等于容量；一旦某 rank 超额，就需要把部分计算迁移出去。

原始验证中，四个 rank 的接收量分别为 [16, 40, 24, 48]，但各 rank 容量只有 32。普通行交换会把数据送到原定设备，MoonEP 的规划器则会调整部分路由，让其他设备使用热点专家的临时权重副本完成计算。

因此，“保持原有专家布局，只换搬运内核”不能覆盖这种路由。框架需要同时接入 plan、冗余专家权重和新的接收布局。

2.2 Plan 是整条链路共同遵守的布局约定 ​

plan 不只记录“发给谁”，还记录“放在哪里、由哪个专家处理、哪些数据可以少传一次”。

信息用途
路由目标与本地偏移确定每条路由落在哪个 rank、哪个槽位
专家分组边界告诉专家计算每段数据对应哪个专家
冗余专家列表确定需要获取哪些远端权重
去重关系同一 token 发往同一 rank 时，hidden 只传一份，接收端再展开

dst 的非负编码表示目标位置，负编码 -raw_dst-1 表示重复载荷。重复的是传输数据，不是要删除专家路由：各条路由仍需完成对应专家计算。

3. 910C 设备层改了什么 ​

验证记录使用 Ascend910_9392 设备、CANN 9.1.0 和 PyTorch / torch_npu 2.12。原始记录中的“8 卡”沿用当时运行口径；部署时仍应核对物理卡、逻辑 device 与 rank 的映射，不能仅凭设备名称推断整机配置。

在该软件环境中，910C 路径采用 主机规划器 + AscendC MTE 内核 + shmem 普通对称堆。

适配项原路径遇到的问题处理方式
构建A5 的 SIMT、UDMA 源码不能直接用于 a2 目标区分构建目标，为不支持的入口显式报错
规划器当前 910C 构建未提供设备侧 SIMT planner在 CPU 上生成 plan，再传回设备
对称内存原 VMM user-buffer 导入路径失败使用 shmem 普通堆
堆分配自建分配器可能覆盖 shmem 内部同步区域通过 aclshmem_align 分配
跨核同步当前路径缺少 SyncAll 所需配置使用 GM flag 软同步，并保留跨 rank barrier
片上暂存原配置超过目标 UB 预算缩小 dispatch 暂存块

这些是当前代码与工具链下的适配结论，不应概括为所有 910C 软件版本的永久能力限制。尤其要注意：固定接收形状不等于消除了主机同步。910C 的主机规划仍需计数汇总、设备到主机传输和结果回传。

4. 框架接入的三个关键问题 ​

4.1 缓冲区可以共享，层状态不能随意共享 ​

多层 MoE 若各建一份通信 Buffer，会快速消耗对称堆。实现按进程组和形状复用 Buffer；但每层的 plan、行布局及反向所需状态仍需保留。

共享 scratch（临时工作区）是另一项独立优化。HP_MOONEP_SHARED_SCRATCH=1 只适用于已验证的串行、完整激活检查点生命周期。后续修复还将 Buffer 命名空间、行数、device 和 dtype 纳入缓存键，避免不同配置误用同一块存储。

换句话说，“底层通信内存可复用”不意味着“所有层的中间结果都可覆盖”。启用共享前，必须确认重算与反向不会再读取旧数据。

4.2 远端专家权重必须可微，反向通信必须全组一致 ​

本接入版本没有直接使用 MoonEP 的 prefetch_weight / reduce_grad 完成训练权重管理，而是通过可微 gather 获取所需远端专家权重，让梯度返回其所有者。

这里有两个曾经出现的正确性问题：

  • 漏收专家：需要集合不能只来自预取槽位。合法 plan 中还可能有其他异地专家，应从完整布局提取 needed_remote，缺失权重时直接报错。
  • 反向集合通信失配：某 rank 没有实际用到 gather 结果时，自动微分可能不执行它的反向，而其他 rank 仍执行 reduce-scatter。实现用零值依赖 _tables_anchor 保留计算图连接，使各 rank 参与配对的反向通信。

零值依赖不改变前向结果，但维护了分布式计算图的参与关系。它解决的是通信配对，不代表所有梯度缩放和训练数值问题都已解决。

4.3 专家所有权必须与参数切分一致 ​

当前权重访问要求每个 rank 持有完整的本地专家分片。FSDP 若再次切分同一专家维度，可能破坏这一假设，因此实现会拒绝未支持的布局。

已测试的某个 EP/FSDP 组合可运行，不能推广为任意 DP、FSDP、TP、PP 与 EP 组合都兼容。需要同时检查专家维所有权、DTensor 本地视图和矩阵权重方向；例如 [in, out] 权重不能直接按 F.linear 的 [out, in] 约定使用。

5. M0–M4 优化分别解决什么 ​

这些标签是接入代码的累计实验版本，不是 MoonEP 官方版本号。M0 已使用主机规划器，后续版本依次叠加改动。

版本新增改动需要注意的边界
M0基础接入作为消融起点，不等同于 all-to-all 基线
M1缓存 plan，供相同路由或检查点重算复用全组确认命中才可跳过规划；指纹与同步本身也有成本
M2合并兼容权重表的 gather表的 dtype、每专家元素数需匹配；不满足条件时回退
M3去掉接收端不使用的路由权重传输源端加权及其梯度仍保留；不适用于专家内部需要路由权重的路径
M4输出使用 empty，并复用已有 CPU 路由副本所有有效输出必须完整覆盖；两项一起开启，不能单独归因

M2 的历史名称“零拷贝融合 gather”容易引起误解：实际仍包含索引、padding 和拼接。Qwen3 融合 gate/up 布局不满足原融合条件，因此对应实验中的 M1→M2 不能用来证明融合收益。

还有两项负面结果需要保留：

  • plan cache 的五次复验中，某配置吞吐下降中位数为 14.24%，说明缓存并不必然更快。
  • 10 月 30 日新增的不等长表 packed gather，在 mock 4k、micro batch 2、global batch 16 的五组对照中，吞吐平均下降 0.90%，reserved 峰值增加约 0.117 GiB，因此继续默认关闭。

异步权重 gather 的旁路 stream 实验也曾在反向挂起，尚不是可推荐的稳定路径。

6.4 为什么通信快几倍，训练却只快一点，甚至变慢 ​

训练总耗时不只包含 token 搬运，还包括规划、远端权重收集、专家计算、重算和框架调度。可以用下面的关系理解：

text
整步变化 ≈ 节省的通信与布局时间
         − 新增的规划、权重收集、分段计算和同步成本
1
2

这只是分析思路，不是可以直接套数值的性能公式。小形状下，固定开销不容易摊薄；大形状下，通信和显存节省可能更明显。但路由分布、专家 GEMM 效率和通信重叠都会改变结果，不能用固定 token 阈值代替实测。

还需避免两个常见误判：

  • 复制专家权重不等于重复计算所有 token。同一条路由仍应执行一次专家计算，变化主要是计算位置和分组方式；额外成本来自权重获取、分段及潜在的小矩阵效率损失。
  • 通信占整步 14%，不等于最大加速为 14%。在其他成本完全不变、该部分耗时降为零的理想条件下，整步时间下降 14%，加速比为 1/(1−0.14)≈1.163。真实接入还有新增开销，应分别测量。

8. 使用边界与后续工作 ​

当前实现更适合受控实验和问题定位。评估时建议遵循以下顺序：

  1. 固定源码提交与配置，同时记录工作区修改、CANN、torch 和 torch_npu 版本。
  2. 先验证 plan 和算子，再验证完整前反向及参数更新；数值门禁未通过时，性能结果单独标注。
  3. 两侧使用相同 grouped GEMM、损失实现、batch、精度和重算策略，避免把基线配置差异算作收益。
  4. 在同节点配对运行，排除 CPU、NPU 和通信资源干扰；分别记录预热、稳态窗口和失败退出。
  5. 按真实路由与形状选择后端。历史 auto 阈值只是某批 LIMO 实验的经验值，不是通用交叉点。

仍需独立验证的范围包括：不支持的 FSDP×EP 专家切分、跨机器 EP、共享暂存的并发生命周期，以及完整训练数值与长期稳定性。OOM、挂起、SIGSEGV/SIGBUS 和连接失败应分类保留，不填零吞吐，也不将“指标已输出但退出状态未知”记为成功。

历史补充实验使用过多个节点并行跑队列，但每台机器都是独立 EP8。其逐日队列状态、私有节点地址和容器恢复过程不影响接入原理，本文不再逐条展开。

总结 ​

MoonEP 接入 HyperParallel 的关键，是一起处理通信、布局和冗余专家权重，而不只是替换 all-to-all。910C 路径通过 MTE、shmem 普通堆和主机规划器运行，框架侧则需要维护缓冲区生命周期、专家所有权和全组一致的反向通信。

现有记录显示，通信微基准有明显收益，训练性能则取决于形状、路由和接入开销。完整训练数值筛查尚未通过，下一步应先完成梯度与参数更新定位，再判断哪些配置具备可用的训练加速价值。
