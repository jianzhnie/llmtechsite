DeepEP 与 DeepEP-Ascend：MoE 专家并行通信的 NVIDIA / 昇腾双栈实践 ​

摘要：DeepEP 是 DeepSeek 开源的、面向 MoE 模型专家并行（Expert Parallelism, EP）的高性能通信库，将 token 分发（dispatch）与结果合并（combine）的 All-to-All 通信效率推至硬件极限；DeepEP-Ascend 是同一套公开 API 在华为昇腾 NPU 上的官方移植，底层通信原语由 NVSHMEM/IBGDA 体系整体替换为 HCCL/HCOMM + UBMEM + URMA，在 Ascend 950DT 上实测 dispatch 带宽达 373–375 GB/s（EP8）。本文结合开源代码与社区技术文章，系统地梳理两者的设计动机、内核机制、API 用法与实测性能。

关键词：MoE、专家并行、All-to-All、DeepEP、DeepEP-Ascend、昇腾、通信-计算重叠

1. 背景：MoE 时代，通信成为新的瓶颈 ​

1.1 MoE 与专家并行 ​

混合专家（MoE）已成为大模型扩展的主流架构：模型拥有数百个专家前馈网络，但每个 token 仅激活其中 top-k 个。以 DeepSeek-V3 为例，共有 256 个路由专家，每个 token 激活 8 个。单张 GPU 的显存放不下全部专家权重，因此将专家切分到多张 GPU 上，这就是专家并行（EP）。

EP 的代价是：每个 token 必须根据其路由结果，被分发（Dispatch）到目标专家所在的 GPU，专家计算完成后再按路由权重合并（Combine）送回原始 GPU。由于每个 GPU 都要与所有其他 GPU 互发数据，通信模式是彻头彻尾的 All-to-All，且每次通信的字节数由动态路由结果决定，事前不可知。

传统通信库（如 NCCL 通用原语）在此场景面临三个结构性困难:

  1. 变长通信：路由结果动态决定每个 rank 的发送/接收字节数，通常需要额外一轮元数据交换；
  2. 对端重排：token 到达目标 GPU 后需按专家重新排队，涉及复杂的内存搬移与格式转换（如 BF16 ↔ FP8 及 scale 的组装）；
  3. 延迟敏感：推理 decode 阶段每个请求每步只产生几 KB 数据，但并发流极多，CPU proxy 线程逐个提交 RDMA 请求根本来不及。

知乎专栏《DeepEP 邮局》系列打了一个形象的比方：8 张 GPU 如同同城 8 家邮局分局，彼此之间有高速公路（NVLink）相连，但没有精妙的调度系统，同时互寄成千上万包裹依然会造成分拣中心的混乱。DeepEP 正是这位"邮政调度专家"——把路由、重排、类型转换和通信全部融进一个 GPU 内核，直接吃满 NVLink / RDMA 的物理带宽。

1.2 硬件带宽的不对称性 ​

EP 集群通常是多节点拓扑：节点内通过 NVLink 互联（H800 实测有效带宽约 153–158 GB/s），节点间通过 RDMA / InfiniBand 互联（400 Gb/s 网卡实测约 43–47 GB/s）。两者相差约 3–4 倍，任何把节点间当节点内处理的朴素实现，都会在网卡这一"最窄路段"上拥堵。

2. DeepEP 总览与演进时间线 ​

DeepEP（GitHub: deepseek-ai/DeepEP）于 2025 年 2 月 25 日 DeepSeek 开源周第二天正式发布，是首个面向 MoE 训练与推理的开源 EP 通信库。其演进脉络：

时间版本关键变化
2025-02V1首发。基于 NVSHMEM + IBGDA + GDRCopy，warp 级 GPU 直接发起 RDMA，CPU proxy 退出数据路径；内置高吞吐内核与低延迟内核
2025 年内V1.x低延迟内核迭代、零拷贝（Tencent 贡献）、AntGroup 优化系列（SMFree / LL-SBO / LL-Layered）、Mori-EP（ROCm/AMD）等实验分支
2025 年底V2完全重构：轻量级 NCCL Gin 后端替代 NVSHMEM，支持更大规模 scale-up / scale-out 域
2026V2.5ElasticBuffer 拆分为 EPBuffer / EngramBuffer / PPBuffer / BucketBuffer；新增 BufferAllocator、批量集合通信、专家负载均衡原语（lb_prefetch_weights / lb_reduce_grads）；完全移除 V1，NVSHMEM 不再是依赖
2026DeepEP-Ascend官方昇腾移植版发布，公开 API 与 NVIDIA 版对齐（详见第 7 节）

一点值得注意的细节：DeepEP 的 GPU 通信内核通过自带的 DeepJIT 在运行时编译（NVIDIA 版用 NVCC，昇腾版用毕昇编译器），安装时无需可见 GPU，首次使用时按当前设备现场编译——这是它能同时跨架构、紧跟新硬件特性（如 TMA、CFT）的重要原因。

3. 技术架构：软件栈与核心机制 ​

3.1 软件栈对比 ​

NVIDIA 版（V1 时代）的经典栈为：PyTorch/vLLM/Megatron → deep_ep → NVSHMEM（GDR 内部缓冲区）+ GDRCopy（CPU-GPU 快速拷贝）+ IBGDA（GPU 直接发起 RDMA）→ NVLink（机内）/ RDMA IB（机间）。V2 之后 NVSHMEM 被 NCCL Gin 取代。

昇腾版则整体映射为：PyTorch/torch_npu → deep_ep（同名包）→ DeepJIT(毕昇后端) → HCCL/HCOMM + UBMEM + URMA → UB CTP/URMA 通道 / 超节点 Clos 网络。

3.2 核心机制 ​

(1) 融合式通信内核。dispatch / combine 的全部工作——发送计数交换、token 重排、FP8 量化/反量化与 scale 组装、跨域转发、接收端写回——都在一个 GPU 内核内完成，避免多 kernel 间的同步与往返延迟，这也是它能逼近物理带宽的关键。

(2) NVLink → RDMA 非对称带宽转发。针对 DeepSeek-V3 的 group-limited 路由（top-8 专家限制在少数几个节点内），高吞吐内核让每个 GPU 先把 token 经 NVLink 转发到同组节点内的"出口 GPU"，再由后者统一走 RDMA。以 8 节点 × 8 卡为例，朴素方案的网卡流量是 7 份，转发方案只需 3 份，网卡字节节省约 57%——这是 MoE 通信设计里最大的一笔"带宽账"。

(3) SM 资源可控。通信内核占用多少个 SM 可精确指定，训练场景可以牺牲少量通信并行度换取计算资源；反过来说，EP dispatch/combine 必须占用 SM（官方明确不支持 zero-SM RDMA EP）。

(4) 延迟 epilogue（deferred epilogue）。dispatch/combine 支持 defer_epilogue=True：通信主体在通信流上异步执行，收尾工作（如 bias 相加、权重应用）延迟到调用方在计算流上 .wait() 时才做，为通信-计算重叠创造了条件。

4. 两套内核：高吞吐与低延迟的分账优化 ​

DeepEP 最富特色的设计是为训练/prefill 和 decode 各造一台"发动机"：

高吞吐内核（Normal / HT）低延迟内核（Low-Latency）
目标吃满带宽压低延迟
场景MoE 训练、推理 prefill推理 decode
传输NVLink + RDMA 混合，支持非对称转发纯 RDMA + IBGDA
SM 占用持续占用（数量可调）仅 send 阶段短暂占用
实测（H800, V1）NVLink 153–158 GB/sdispatch 延迟低至 163 µs

Hook-based 通信-计算重叠是低延迟内核的灵魂。它将 dispatch 拆为两个阶段：

  • SEND_PHASE：warp 写完网卡工作队列（WQE）、敲完 doorbell 后 kernel 立即退出，此后数据在网络上自主传输，不占用任何 SM；
  • RECV_PHASE：等框架真正需要结果时，通过 hook() 触发接收内核完成收尾。

于是 GPU 的时间线变成：batch A 的 dispatch 数据在飞 → SM 全部让给 batch B 的 attention → 需要 A 的结果时调 hook 收数。多个 micro-batch 以此方式流水起来，通信被完全藏进计算背后。

5. 代码实践：EPBuffer API 详解 ​

以下示例基于当前 V2.5 API（NVIDIA 版与 Ascend 版公开接口一致）。

5.1 初始化 Buffer ​

每个 EP 组创建一个 EPBuffer 并长期复用；所有 rank 必须就 num_max_tokens_per_rank 达成一致：

python
import torch
import torch.distributed as dist
from deep_ep import EPBuffer

# 初始化 EP 组（昇腾版用 backend='hccl'，并 import torch_npu）
ep_group = dist.group.WORLD

buffer = EPBuffer(
    ep_group,
    num_max_tokens_per_rank=4096,   # 每 rank token 容量（覆盖训练/prefill/decode 各 batch）
    hidden=7168,
    num_topk=8,
    use_fp8_dispatch=True,          # 预留 FP8 dispatch 存储
    explicitly_destroy=True,
)

5.2 前向：Dispatch → 专家计算 → Combine ​

python
# ---- Dispatch：token 按路由分发到各专家所在 rank ----
pending = buffer.dispatch(
    x,                              # BF16 tensor，或 FP8 的 (data, scales) 元组
    topk_idx=topk_idx,              # 每 token 的 top-k 专家 id
    topk_weights=topk_weights,      # 路由权重
    num_experts=256,
    num_max_tokens_per_rank=4096,
    expert_alignment=128,           # 与分组 GEMM（如 DeepGEMM）的 token 对齐一致
    do_expand=True,                 # 输出按专家分组的 expanded 布局
    do_zero_padding=True,
    defer_epilogue=True,            # 延迟收尾
    async_with_compute_stream=True,
)

# ★ 通信在飞：先干别的活（如 shared expert）★
shared_output = shared_experts(x)

# 需要结果时 .wait()，拿到 expanded 布局与路由句柄
recv_x, _, recv_weights, handle = pending.wait()

# ---- 专家计算（分组 GEMM，权重在 combine 前应用）----
expert_output = local_experts_forward(recv_x)

# ---- Combine：加权合并 + bias（如 shared expert 输出），送回原始 rank ----
pending = buffer.combine(
    expert_output,
    handle=handle,
    bias=shared_output,
    defer_epilogue=True,
    async_with_compute_stream=True,
)
output, _ = pending.wait()

5.3 反向传播：几何对称，免费获得 ​

反向传播利用 dispatch/combine 的几何对称性自动成立，训练时只需保存前向 handle：

python
# dispatch 的 backward 就是 combine（梯度"回家"）
grad_x, grad_w, ev = buffer.combine(
    grad_recv_x, handle=handle, topk_weights=grad_recv_weights,
    async_with_compute_stream=True)

# combine 的 backward 就是 dispatch（梯度"出门"，复用 handle）
grad_out, _, _, _, ev = buffer.dispatch(
    grad_combined_x, handle=handle,
    do_expand=True, do_zero_padding=True,
    async_with_compute_stream=True)

5.4 推理 decode 的低延迟用法 ​

decode 时用 GPU 侧接收计数（do_cpu_sync=False），避免 CPU 同步开销；输出按容量分配，专家 GEMM 需用 handle.psum_num_recv_tokens_per_expert 判定有效范围。框架集成方面，vLLM 通过 --all2all-backend deepep_high_throughput / deepep_low_latency 切换两套内核，Megatron-LM 的 MoEFlexTokenDispatcher（_DeepepManager）与 SGLang 也已内置支持。

5.5 专家负载均衡（V2.5 新原语） ​

面向 MoonEP / UltraEP 式的动态冗余专家，EPBuffer 暴露两个 NVLink 域内集合操作：

python
# 专家计算前：把热门专家的权重预取到冗余槽位
ready = buffer.lb_prefetch_weights(
    redundant_weights, expert_weights, redundancy_mapping)

# 反向：把冗余槽位的 FP32 梯度累加回原专家
ready = buffer.lb_reduce_grads(
    redundant_grads, expert_grads, redundancy_mapping)

7. DeepEP-Ascend：换芯不换 API ​

DeepEP-Ascend（GitHub: deepseek-ai/DeepEP-Ascend）是面向华为昇腾 NPU 的官方移植版，2026 年随 Ascend 950 系列推出。其公开 README 声明："同一 API、完整性能"（Same API and full performance on HUAWEI Ascend 950 NPUs）。

7.1 移植策略 ​

  • 上层完全不动：Python 包名仍是 deep_ep，EPBuffer 等公开类名、方法签名与 NVIDIA 版逐一对齐，训练脚本基本零修改；
  • 内核换芯：Ascend C 内核通过 DeepJIT（毕昇编译器后端）运行时编译；通信底座由 NVSHMEM/IBGDA 换成 HCCL/HCOMM（对等通信）、UBMEM（机内共享内存，对标 NVLink 域）、URMA（远程内存访问，对标 RDMA）；
  • 拓扑对应：机内走 UBMEM + UB CTP 通道，机间走 URMA + 超节点 Clos 网络。

7.2 环境要求 ​

  • Ascend 950（A5）NPU，具备 UBMEM 连通性与 UBC_CTP/URMA 通道；参与通信的 rank 数为偶数；
  • CANN 9.2.0（含 Ascend C、毕昇编译器、HCCL/HCOMM），Python ≥ 3.10，PyTorch 2.13 + torch_npu 2.13；
  • 验证栈：Ascend 950DT + CANN 9.2.0；华为 Q3 商用 HDK（Atlas 850E，计划 2026 年 10 月中旬公开）为推荐部署基线。

9. DeepEP vs DeepEP-Ascend 对比总结 ​

维度DeepEPDeepEP-Ascend
定位MoE EP 通信库（NVIDIA GPU）同一 API 的昇腾 NPU 官方版
硬件Hopper（H800/H100）及更新Ascend 950（A5）
机内互联NVLinkUBMEM + UB CTP
机间互联RDMA / InfiniBandURMA + 超节点 Clos
通信原语NCCL Gin（V2）；NVSHMEM+IBGDA（V1）HCCL / HCOMM + UBMEM + URMA
JIT 编译DeepJIT + NVCCDeepJIT + 毕昇
实测水平NVLink ~158 GB/s；dispatch 163 µsEP8 dispatch ~374 GB/s（物理上限 90–95%）

结语：DeepEP 的贡献不止于一个"更快的 All-to-All"——它证明了 EP 通信可以像计算算子一样被极致工程化（融合内核、GPU 发起传输、分场景双内核、通信-计算重叠）。DeepEP-Ascend 则把这套工程范式完整平移到昇腾生态：换的是芯，不换的是 API 与方法论。对于 MoE 训练/推理集群的选型者而言，两者共同构成了跨 NVIDIA 与国产算力的统一 EP 通信底座。
