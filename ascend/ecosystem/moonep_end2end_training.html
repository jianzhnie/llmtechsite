MoonEP 与 HyperParallel：集成方案与端到端训练效果 ​

MoonEP 是 Moonshot AI（月之暗面）开源的专家并行通信库，采用 MIT 协议。它面向 MoE 训练中的 token 分发与结果合并，通过通信布局优化和动态冗余专家，把热点设备上的部分计算分散到其他设备。

本文基于本地 moonep/ 中的介绍、适配说明、集成文档、实验记录和演示稿，围绕四个问题展开：MoonEP 如何工作、如何集成到 HyperParallel、端到端训练表现如何、相对 all-to-all 有哪些收益和代价。

关注点已有结果
集成方案在 HyperParallel 中替换路由专家的完整计算链，接入 plan、dispatch/combine、冗余专家权重及梯度回传
自然路由训练性能所选三次配对配置中，mock 16k 吞吐 +17.55%；LIMO 16k +5.92%、32k +9.45%；LIMO 12k、micro=4 时 +22.88%
不适合的形状LIMO 4k、micro=1 时吞吐 −10.60%，存在固定规划与权重收集开销
显存LIMO 32k、micro/global=1/8 的 allocated 峰值均值从 45.99 降至 40.84 GiB
通信微基准指定形状下 dispatch 延迟比约 4.10–4.47×，combine 约 5.33–6.09×；不包含主机规划

1. MoonEP 介绍 ​

1.1 为什么 MoE 需要专门的专家并行通信 ​

MoE 的 router 为每个 token 选择 top-k 个专家。专家分布在 EP 组的多个 rank 上，训练时需要先 dispatch 输入，执行专家网络，再 combine 返回结果。普通 all-to-all 主要负责数据交换，专家归属和前后重排由框架处理；当热点专家集中在少数 rank 时，最忙的 rank 会拖慢整层。

MoonEP 将规划、数据搬运和专家布局共同设计：保留 token 的逻辑专家选择，改变一部分路由的物理执行位置，并为执行端准备原专家的临时权重副本。每条路由仍执行一次对应专家计算，副本梯度最终回到原始权重 owner。

1.2 接收容量固定，就必须处理超额负载 ​

设 EP 组有 R 个 rank，每个 rank 输入 S 个 token，每个 token 选择 K 个专家。全组共有 RSK 条路由，因此每 rank 的平均份额为 SK。

本文讨论的接入路径按这个平均份额设置逻辑接收容量：

NvS=S×K.

这里是 SK 条路由记录，不是 SK 个不同 token。只有路由完全按 rank 均衡时，各 rank 的原始接收量才都等于容量；一旦某 rank 超额，就需要把部分计算迁移出去。

因此，“保持原有专家布局，只换搬运内核”不能覆盖这种路由。框架需要同时接入 plan、冗余专家权重和新的接收布局。

1.3 Plan 是整条链路共同遵守的布局约定 ​

plan 不只记录“发给谁”，还记录“放在哪里、由哪个专家处理、哪些数据可以少传一次”。

信息用途
路由目标与本地偏移确定每条路由落在哪个 rank、哪个槽位
专家分组边界告诉专家计算每段数据对应哪个专家
冗余专家列表确定需要获取哪些远端权重
去重关系同一 token 发往同一 rank 时，hidden 只传一份，接收端再展开

dst 的非负编码表示目标位置，负编码 -raw_dst-1 表示重复载荷。重复的是传输数据，不是要删除专家路由：各条路由仍需完成对应专家计算。

2.2 Ascend 910C 上的设备实现 ​

验证记录使用 Ascend910_9392 设备、CANN 9.1.0 和 PyTorch / torch_npu 2.12。

在该软件环境中，910C 路径采用 主机规划器 + AscendC MTE 内核 + shmem 普通对称堆。

适配项原路径遇到的问题处理方式

规划器当前 910C 构建未提供设备侧 SIMT planner在 CPU 上生成 plan，再传回设备

2.3 前向与反向如何串起来 ​

实现说明中有两条入口：生产模型由 build_ep_compute 进入 moonep_routed_forward，独立模型验证使用 MoonEPMoE。两者共用规划与传输，但对路由权重的需求可能不同。

步骤主要工作关键模块
路由与规划统计本地专家计数，汇总全组信息，生成目标位置和分段布局moonep_plan.py
权重准备找出全部异地专家，紧凑收集所需权重moonep_forward.py
数据分发保存 plan，执行 dispatch，并建立反向连接moonep_ep.py
专家计算本地专家使用 grouped GEMM，远端专家段走分段计算moonep_forward.py、experts.py
结果合并combine 回收行结果，再按原 token 和路由权重聚合moonep_forward.py
反向回传通信的转置操作回传行梯度，可微 gather 回传专家权重梯度moonep_ep.py 与自动微分图

这些文件位于 hyper_parallel/distributed/expert_parallel/。此处描述数学与数据流关系，不表示权重收集、dispatch 和专家计算已经实现完全并行。

生产入口在 combine 后加权，因此可以省去接收端不用的路由权重；独立 MoonEPMoE 入口可能在专家计算前使用权重。对非线性专家网络，一般有 f(wx)≠wf(x)，不能为了省通信随意移动乘权重的位置。10 月 30 日修复记录通过 requires_route_weights=True 显式声明独立入口的需求，避免全局开关破坏接口语义。

2.4 权重、缓冲区与参数布局 ​

接入中最关键的工程约束集中在以下几处：

集成问题当前处理方式边界
冗余专家权重从完整 plan 提取所需异地专家，使用可微紧凑 gather仍有 padding 和向非消费 rank 广播权重的成本；未接入原生 prefetch/reduce-grad
反向 collective 配对_tables_anchor 保留不消费远端权重的 rank 的图依赖不能因零值依赖不影响前向而删除，否则可能反向挂起
通信 Buffer按进程组和形状复用，避免多层各建一份耗尽对称堆plan 和反向状态仍需按调用保存
共享 scratch已验证的串行、完整激活检查点生命周期下复用不代表任意并发、交错调度都安全，需检查缓存隔离与覆盖时机
FSDP / DTensor校验本地专家所有权、参数可读生命周期及权重投影方向已测组合不代表任意 FSDP×EP、TP、PP 组合均兼容

专家计算采用本地 grouped GEMM 与远端分段计算的混合路径。远端段的小矩阵效率、FP32 转换和逐段 Python 调用仍可能抵消部分通信收益。

2.5 从基础接入到 M4 ​

M0–M4 是累计实验配置，不是 MoonEP 官方版本号，也不是不同仓库提交的简单回退。

版本累计增加的优化实验解释
M0主机规划、通信与冗余专家基础接入MoonEP 消融起点，区别于 all-to-all 基线
M1plan 缓存与检查点重算复用需全 EP 组一致命中；指纹与同步仍有固定成本
M2兼容权重表的融合 gatherQwen3 融合 gate/up 布局不满足原条件，不能据此证明融合收益
M3去掉接收端不消费的 route-weight 传输生产入口仍在源端加权并回传路由权重梯度
M4输出取消清零、复用 CPU 路由副本两项同时启用，收益不能单独归因

后端通过 HP_MOONEP_EP=0/1/auto 选择；910C 使用 ASCEND_MOONEP_HEAP=shmem。训练矩阵还固定 grouped GEMM、同步权重 gather、num_sms=32 及受控生命周期下的共享 scratch。复现实验需要保存 YAML、全部开关、源码提交及未提交 diff，不能只设置后端开关。

历史 auto 阈值 HP_MOONEP_MIN_ROWS=98304 按路由行数判断，K=8 时对应每 rank 12288 个输入 token，不是通用序列长度交叉点。异步 gather 曾在完整模型反向挂起；缓存也曾在 mock12k、micro4/global32 五次复验中使吞吐下降中位数 14.24%，因此优化开关需逐形状配对测量。

3. MoonEP 的端到端训练效果 ​

3.1 实验设置与统计口径 ​

后续矩阵采用 Qwen3-30B-A3B 架构、随机初始化权重，在多台机器上分别执行单机 EP8，不是跨机 EP 训练。对照统一使用 grouped GEMM、BF16、完整激活检查点和 chunked loss；同配置的不同后端及重复固定在同一节点。

以下选取本地实验总报告及配套 CSV 中的完整配对配置，统一使用算术均值口径。每组都有同节点三次成功配对；先在节点内平均，再对节点均值等权平均，所列配置实际各只有一个节点，不能称为多节点独立复验。吞吐是单节点 EP8 整体 tokens/s，变化列先逐对计算再平均。

通常先预热 10 步，再计时 50 步；窗口耗时取全 rank 最大值，吞吐由累计全局 data/step_tokens 除以窗口耗时得到，不再乘 rank 数。它是否完全等于参与 loss 的非 padding token 数，还需核对数据字段。以下 allocated 是每次窗口全 rank 峰值的平均值，不是显存容量安全上限。

以上百分比和差值基于表内已舍入数据；显存减少不能直接解释成可支持更大 batch，仍需单独验证目标形状是否 OOM。不同配置的 step time 也不直接横比，因为每步 token 数不同。

审查报告还记录：本地 grouped 分支主要使用 BF16，远端分段计算会转为 FP32 后再写回 BF16，可能形成不同算术路径。它是应优先验证的线索，尚未证明是唯一根因。不能仅以“BF16 有误差”为由豁免筛查，也不宜在定位前直接删掉类型转换。

当前应优先沿 路由 → 分发 → 专家输出 → 加权合并 → 输入与参数梯度 → optimizer 更新 逐段定位，尤其检查专家梯度缩放、参数所有权、DTensor 布局和检查点重算。loss 接近或进程正常退出，都不足以单独证明梯度正确。

MaxVio 定义为全组专家负载的 max/mean−1，数值越大，负载越集中。在这组测试里，dispatch 的延迟比约为 4.10–4.47 倍，combine 约为 5.33–6.09 倍（根据表内已舍入数据计算）。

这个结论有明确边界：MoonEP dispatch 包含权重预取，但 plan 在计时区间外生成；基线是该脚本的 eager all-to-all 与布局处理路径，不等同于训练框架中可异步重叠的完整路径。记录中的逻辑带宽按 S×K×H×2/t 计算，也不是链路实际传输带宽。

4.2 负载重平衡的收益 ​

本地可视化说明区分了三种负载：

指标统计什么适合回答的问题
专家需求各专家获得的 token-expert 路由条目数哪些专家最热门？
原始 owner 需求将专家需求按权重原始所属 rank 求和不迁移计算时，工作集中在哪些 rank？
实际执行负载按 MoonEP 接收布局统计各 rank 执行的有效行数规划是否把工作重新分散？

通信微基准中的 MaxVio 为 max/mean−1。下面补充实验的“偏斜”使用 max/mean，因此均匀负载对应 1，两种数值不要混用。使用 mock (随机生成)数据集， sequence length 16k、micro/global batch 为 1/8 的受控实验中，按实验总报告的配对均值口径：

4.4 为什么通信收益没有等比例转化为训练收益 ​

训练总耗时不只包含 token 搬运，还包括规划、远端权重收集、专家计算、重算和框架调度。可以用下面的关系理解：

text
可节省的整步时间 ≈ 节省的通信与布局时间
         − 新增的规划、权重收集、分段计算和同步成本
1
2

这只是分析思路，不是可以直接套数值的性能公式。小形状下，固定开销不容易摊薄；大形状下，通信和显存节省可能更明显。但路由分布、专家 GEMM 效率和通信重叠都会改变结果，不能用固定 token 阈值代替实测。

还需避免两个常见误判：

  • 复制专家权重不等于重复计算所有 token。同一条路由仍应执行一次专家计算，变化主要是计算位置和分组方式；额外成本来自权重获取、分段及潜在的小矩阵效率损失。
  • 通信占整步 14%，不等于最大加速为 14%。在其他成本完全不变、该部分耗时降为零的理想条件下，整步时间下降 14%，加速比为 1/(1−0.14)≈1.163。真实接入还有新增开销，应分别测量。

4.5 主机规划的实际成本 ​

910C 当前采用主机 planner。C++ 实现缩短了规划计算时间，但仍需将输入从设备传到主机（D2H），再将规划结果传回设备（H2D）。集成记录 §6.3 的 PyTorch / torch_npu 2.12 复测采用预热 20 次、计时 100 次，以下报告 p50：

按包含传输的口径，C++ 相对 Python 的耗时比改善约为 3.91–4.81 倍。计算本体与含传输耗时之间的差距也说明：优化 CPU 规划算法后，主机与设备之间的往返成本仍然存在，固定接收形状并不意味着消除了主机同步。

表中“行数”指 S×K 条 token-expert 路由记录，不是输入 token 数；在 K=8、每 rank 一条序列的测试配置下，分别对应约 1k、4k、16k 输入 token。这是 planner 的独立测量，未覆盖完整训练中的全部路由计数汇总、缓存指纹与全组命中判定、框架调度等成本。梯度累积和激活检查点重算还会改变每步调用次数，因此不能直接将表内耗时乘模型层数作为完整 step 的规划开销。

4.6 如何选择后端 ​

现有性能证据更支持在热点集中到少数 owner、每次调用工作量较大、或接收激活占用较高的场景评估 MoonEP。短序列、小 micro batch、owner 需求接近均匀时，all-to-all 可能更合适。判断依据应是同配置的完整 step 吞吐、allocated/reserved 峰值及正确性结果，而不是专家偏斜或单项内核速度。

吞吐提升与 step 耗时下降也应分开：固定 token 数时，吞吐提升比例为 T_a2a/T_moonEP−1，耗时下降比例为 1−T_moonEP/T_a2a，两者数值不同。主表的变化列先逐对计算再平均，不能用已舍入均值重新计算后要求逐位相同。
