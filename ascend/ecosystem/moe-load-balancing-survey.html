MoE 负载均衡：训练与推理加速方案综述 ​

MoE 通过稀疏激活专家，在扩大模型容量的同时控制每个 token 的计算量。但在分布式执行时，计算量少并不意味着设备利用率高：如果大量 token 被路由到少数设备，其他设备就会等待，训练 step 或推理批次的耗时最终由最忙的设备决定。

负载均衡要回答的核心问题是：在保留模型能力的同时，如何让专家需求、设备计算和通信成本相互匹配？ 辅助损失、专家重排、热点复制和 token 重路由，分别从不同层次处理这个问题。

本文围绕三个问题展开：热点从哪里来，均衡策略改变什么，以及为均衡付出的成本是否值得。 阅读时可以先把四类方案理解为：EPLB 调整专家布局，LPLB 优化已有副本之间的流量，MoonEP 围绕固定接收容量组织计算，UltraEP 根据当前微批次联合决定副本与配额。后文逐一解释这些选择背后的原理与取舍。

1. 先分清：需要均衡的究竟是什么 ​

1.1 专家热门，不一定意味着设备失衡 ​

路由器（router）为每个 token 选择 top-k 个逻辑专家，专家并行（Expert Parallel，EP）再将这些专家分布到不同设备上。模型决定“需要哪些专家”，执行系统决定“去哪个实例计算”，两层映射共同决定最终负载。

逻辑专家是一组模型参数，物理实例是这组参数在设备上的存储或副本。原始实例所在的 rank 称为 owner；rank 是参与分布式执行的进程，本文示例按每个 rank 对应一个设备理解。

图 1：逻辑专家与物理实例的关系。分支表示可选执行位置；对同一条专家路由，只选择一个实例执行，不同时计算两份。

同一个逻辑专家可以拥有多个物理实例，但对一条已选定的专家路由，只需由其中一个实例完成计算。这样可以保持逻辑专家选择，同时把工作分散到不同设备。

观察对象需要回答的问题常见误判
专家需求哪些逻辑专家收到的路由最多？热专家多，就一定存在热点设备
设备执行负载各设备实际执行多少条专家路由？行数相等，设备耗时就一定相等
通信与等待输入、权重和梯度在哪里传输，谁在等待？通信内核快几倍，整步也会快几倍

例如，四个热门专家分别位于四张设备上，设备之间可能仍然均衡；若四个热门专家集中在同一张设备上，就容易形成瓶颈。因此，专家级偏斜与设备级偏斜需要分开测量。

另外，token 选择 K 个专家会产生 K 条 token-expert 路由记录。负载统计中的“行数”通常指这些路由记录，而不是唯一 token 数。

1.2 三个层次的均衡方法 ​

层次主要改变什么典型方法主要代价
路由选择token 选择哪些逻辑专家辅助均衡损失、专家偏置、均衡分配需要权衡专家分工与均衡目标
专家放置专家及其副本位于哪些设备EPLB、专家迁移参数搬迁、额外显存与布局切换
运行时调度当前路由由哪个物理实例执行LPLB、MoonEP、UltraEP当前负载统计、在线规划与副本通信

这些方法可以组合使用。训练中的均衡损失降低长期路由偏斜，周期性专家放置适应较慢的分布变化，运行时调度再处理当前批次的波动。后两类方法通常保留逻辑专家选择，但要让结果在训练中成立，还需保证副本权重一致、梯度归还正确，以及数值误差符合验收标准。

1.3 均衡的目标是缩短关键路径 ​

一次 MoE 调用通常包含负载统计、调度、token 分发、专家计算和结果合并；使用副本后，还会增加权重准备，训练时则需要处理副本梯度。这些阶段可能重叠，实际耗时取决于最长的依赖链，也就是关键路径。

因此，比起分别追求最均匀的行数或最快的调度器，更有用的判断是：

ΔT=Tbaseline−Tbalanced.

只有在相同工作量与正确性要求下，计入全部新增成本后的 ΔT>0，均衡方案才带来净收益。不能把多个有重叠的阶段耗时直接相加，也不能从路由行数变化直接推导加速比。

这也解释了为什么“行数完全均衡”不等于“性能最优”：专家批量大小、分组矩阵乘效率、网络拓扑和数据类型都会影响实际耗时。行数是重要代理指标，最终仍应以完整训练 step 或推理请求延迟为准。

2. 从路由约束到专家副本 ​

2.1 路由侧均衡：减少热点的形成 ​

训练阶段可以在路由器中加入均衡约束，让专家获得更接近的使用频率。常见方式包括辅助均衡损失，以及根据历史使用量调整专家选择偏置。Megatron-LM 等训练框架提供了多种此类策略。

这类方法直接作用于逻辑专家选择，有助于避免专家长期闲置或过载，但需要兼顾模型质量与专家专门化。即使长期平均使用率接近，单个批次仍可能偏斜；专家使用率均匀，也不保证给定设备布局下的通信和计算最优。

容量限制和 token 丢弃也能限制最坏负载，但会改变哪些路由实际参与计算。本文重点讨论保留所选专家计算、通过放置与调度改善执行效率的方案。

2.2 专家迁移与临时复制：两种不同代价 ​

专家迁移改变参数的长期存放位置。对于训练，迁移通常还涉及梯度与优化器状态；它适合负载偏好持续较长时间、迁移收益能够摊销的情况。

临时复制保留原始专家位置，将权重放到空闲设备的副本槽位，再分担当前任务。训练时，副本梯度需要归约回原始专家，通常由原始专家统一维护优化器状态。推理时权重不随 step 更新，副本可以长期驻留，主要成本转为显存和布局调整。

下面用两个等速设备说明临时副本如何分担热点。假设 E0 有 80 条路由，E1 有 20 条路由；设备 1 有一个空闲副本槽位，可以执行 E0 的部分任务。

图 2：临时复制的示意数据。E0 的总需求仍为 80 行，E1 仍为 20 行，只改变执行位置。虚线表示新增权重通信；图中未计入复制、调度和计算效率差异，因此不代表实测加速比。训练时还需将副本梯度归还原始专家。

图中的最忙设备从 80 行降到 50 行。若假设计算时间严格正比于行数，并忽略全部新增成本，计算部分的理想加速比为 80/50=1.6。实际收益通常还要扣除权重复制和调度成本；这个例子解释了均衡为何有潜力，也说明行数改善并不直接等于整步加速。

副本数量受显存与通信预算约束。复制更多热门专家可能降低计算等待，也会增加权重存储和同步压力。当额外实例承担的任务太少时，复制成本甚至可能高于节省的计算时间。

2.3 负载变化速度决定调度节奏 ​

负载倾斜有不同的时间尺度。某个专家可能在很长时间内持续热门，也可能只在一批请求中突然繁忙；同一个训练 step 内，不同层、不同微批次的热点也可能不同。微批次（microbatch）是一次前向处理的数据批次，它与通过梯度累积形成的一次优化器更新需要区分。

变化尺度典型现象对调度的要求
长期偏好某些专家持续承担更多任务用历史统计调整布局，摊销搬迁成本
批次波动相邻批次的热点强度不同根据当前需求调整已有实例的流量
逐层、逐微批次变化热点位置与强度快速切换更及时地决定副本或配额，同时压低在线开销

历史统计覆盖的窗口越长，估计通常越平滑，但对新热点的响应越慢；决策越频繁，适应性越强，但统计、求解和搬运成本也越难忽略。四类代表方案的差异，正是在这些时间尺度与成本之间做选择。

3. 四类代表方案的方法原理 ​

3.1 EPLB：用历史负载优化专家布局 ​

EPLB 的核心是根据历史负载，为热门专家分配更多物理实例，再将这些实例尽量均匀地放到设备上。其基本流程是：

  1. 在一个统计窗口内收集各专家的需求。
  2. 在固定副本预算内，为预计最繁忙的专家增加副本。
  3. 根据估计工作量分配物理实例，兼顾设备容量和节点局部性。
  4. 搬运权重并更新逻辑专家到物理实例的映射。

副本分配可以理解为不断拆分最重的任务：某专家预计承担 100 份工作，有两个实例时理想上每份承担 50；若仍然过重，再考虑增加一个实例。放置时则优先处理较重实例，将其分给尚有容量的轻载设备，形成近似均衡的布局。

分层放置进一步考虑网络拓扑：先安排节点之间的专家组，再安排节点内实例，以减少跨节点通信。这里追求的不是单纯“每卡专家数一样”，而是估计工作量均衡且通信局部性较好。

EPLB 适合负载具有一定稳定性的场景。它的局限是历史统计可能滞后：布局刚调整好，下一批请求就可能转向其他专家。EPLB 的布局决策本身也不负责精细优化当前批次在已有副本间的流量，运行时分流仍由框架或其他调度方法完成。布局切换是否阻塞服务，则取决于具体框架的搬迁与切换机制。

3.2 LPLB：在既定副本拓扑上优化当前流量 ​

EPLB 解决了“副本放在哪里”，但布局不变时，当前批次仍可能失衡。LPLB 进一步将较慢的副本布局调整与较快的 token 分流分开。历史负载决定哪些专家拥有副本、实例之间如何连接；当前批次到来后，再依据实际需求优化原始实例和副本各自承担的工作量。

它把设备视为图中的节点，把可供分担工作的副本关系视为连接。在固定拓扑约束下，求解一个线性规划问题：

minmaxrLr,

其中 Lr 是重分配后设备 r 的路由负载。约束要求每个逻辑专家的总需求得到满足，工作只能分给它已经拥有的物理实例，且分配量非负。

与周期性重排相比，LPLB 能更快响应批次间的负载波动，也避免每个批次都重新构建完整副本布局。不过，已有拓扑限制了可用选择：如果当前最热专家没有足够副本，流量优化无法凭空增加执行位置。本文所依据的开源设计中，每个被复制专家最多增加一个副本，这也是极端热点下的重要限制。

线性规划本身还有求解成本。小批次计算时间较短时，调度开销可能难以摊薄；即使路由数更均衡，若未建模矩阵乘的非线性效率，也不一定得到最短设备耗时。

3.3 MoonEP：围绕固定接收容量联合规划 ​

与在既有副本拓扑上分流相比，MoonEP 进一步把负载规划、接收布局与专家并行通信共同设计。设每个 rank 输入 S 个 token，每个 token 选择 K 个专家，在各 rank 输入规模相同的配置下，全组平均每 rank 有 SK 条路由记录。MoonEP 围绕这个平均份额设置固定逻辑接收容量：

CAP=S×K.

规划器读取当前路由需求，识别过载与空闲 rank，将过载专家的部分任务转移出去，并为执行端准备临时专家权重。逻辑专家选择不变，物理执行位置发生变化。规划目标同时约束每个专家的需求守恒，以及各 rank 的接收容量。

固定容量有利于预分配缓冲区、稳定执行形状，并将重排与通信协同优化。代价是当前规划、远端权重获取和副本计算组织都带来额外成本。它力求降低执行行数对原始路由偏斜的敏感性，不意味着训练延迟完全不受偏斜影响，也不保证任意配置都更快。

MoonEP 的方法原理还应与具体平台实现分开。原生设计中的设备规划、载荷去重等能力，不能直接视为所有后端都已启用。本地 Ascend 910C 与 HyperParallel 适配采用主机规划和框架侧可微权重收集，端到端收益随形状变化，完整模型数值筛查仍待通过。具体结果见 MoonEP 集成与训练效果。

3.4 UltraEP：基于当前微批次联合决定副本与配额 ​

MoonEP 与 UltraEP 都使用当前路由器输出后的实际负载，也都涉及动态副本。UltraEP 的侧重点是围绕专家实例配额组织实时决策，并将副本放置、权重分发和训练生命周期一起纳入设计。在每层、每个微批次中，它联合决定哪些专家需要副本，以及每个实例应承担多少工作量。

这里的配额（quota）表示专家实例接收的目标路由数量。方法围绕可行的负载阈值搜索，在副本槽位与通信局部性约束下，使最忙设备的负载下降。相比“先根据历史定布局，再分流当前 token”，它把布局与分流更紧密地结合起来。

要让逐微批次决策值得做，还需控制三个成本：

  • 复制范围：优先在高带宽 scale-up 互联域（通过高速互联紧密连接的一组设备）内准备副本，避免权重复制跨越慢链路。
  • 复制粒度：少量任务未必值得触发一次权重传输，需要权衡分担计算与复制成本。
  • 副本生命周期：跨层复用有限缓冲，训练时将副本梯度归还原始专家，避免为每个临时副本长期维护完整训练状态。

当一个热点专家需要多个副本时，源设备的权重发送也可能成为新瓶颈。UltraEP 使用中继分发等方式分摊发送压力，其意义是避免“计算热点被消除，通信热点却留在原处”。

UltraEP 对历史预测的依赖较少，但当前负载统计、规划和权重同步进入了执行流程，对互联带宽及调度开销提出更高要求。流水线训练还需要确保不同微批次在前向、重算和反向时使用正确的副本状态；实际重叠程度和数值一致性需要由具体集成验证。

4.2 比较时最重要的三个取舍 ​

第一，历史预测还是当前观测。 历史负载可将决策移出高频路径，但对分布漂移有滞后；当前观测减少预测误差，却需要在执行过程中完成统计与决策。LPLB 结合两者：布局较慢地更新，流量较快地调整。

第二，已有副本之间分流，还是同时改变执行位置。 固定副本拓扑缩小了决策空间，也减少了布局变化；动态副本扩大了可调度范围，但会引入权重传输和更复杂的状态管理。若最热门专家没有可用副本，单纯调整流量无法解决它的瓶颈。

第三，优化行数还是优化实际耗时。 路由数量容易统计和约束，但专家矩阵乘效率不一定随行数线性变化。相同总行数拆成许多小段，可能比集中成较大的计算块更慢。复制范围若跨越慢链路，也可能把计算收益消耗在通信上。

这些取舍比笼统讨论“哪个算法更先进”更有助于选型。尤其是 MoonEP 与 UltraEP，二者都属于当前负载驱动的联合设计，差异需要结合容量目标、配额约束、互联局部性和实际集成来理解。

4.3 与 DeepEP 等通信库是什么关系 ​

DeepEP 主要提供 token 分发、结果合并及相关数据搬运能力。专家复制路线还需要权重准备和训练梯度归约，但有这些通信能力，不等于已经有负载均衡策略：复制谁、放在哪里、当前流量如何拆分，仍需要规划方法决定。

可以将整个系统分成三层：

层次负责的问题代表角色
策略层调整路由、布局、副本和配额路由均衡策略、EPLB、LPLB 等
通信与执行层搬运输入、权重、输出和梯度，执行专家计算DeepEP 等通信库；MoonEP 等联合设计方案
框架层管理参数、批次、调度、检查点及服务状态Megatron-LM、vLLM、SGLang、MindSpeed、HyperParallel

部分项目横跨多个层次，不能仅凭“通信库”或“均衡库”的名称推断完整能力。方案对接是否可用，还取决于目标版本、参数布局和训练或推理后端。

5. 训练与推理应如何选择 ​

5.1 训练：兼顾模型质量与完整反向 ​

训练中的权重持续更新，临时副本必须使用对应前向所需的权重，副本梯度也必须正确回到原始专家。梯度累积、激活检查点和流水线并行会进一步延长状态生命周期。

因此，训练评估需要同时观察三件事：路由侧均衡是否影响模型质量，执行侧均衡是否真正缩短 step，以及副本方案是否保持完整梯度与优化器更新正确。首步 loss 接近或进程正常退出，都不足以完成验收。

如果负载偏好变化较慢，可以先评估专家布局调整；如果每层、每微批次波动明显，可以进一步评估在线分流或动态副本。前提始终是新增统计、复制和调度开销能被减少的等待时间覆盖。

5.2 推理：区分 prefill、decode 与请求分布漂移 ​

推理权重通常固定，常驻副本更容易复用，因此历史窗口驱动的 EPLB 有较自然的应用条件。vLLM、SGLang 等框架将负载记录、布局决策和权重搬迁组织进服务流程，但不同版本、模型和后端的支持范围需要分别核对。

Prefill（提示词预填充）一次处理较多 token，更可能摊薄在线规划成本；decode（逐 token 解码）每个活跃请求每步通常只产生一个新 token，批次规模较小时，统计与求解开销占比可能更高。不过连续批处理、请求规模和硬件互联都会改变结果，不能将这个趋势当成固定结论。

推理还要关注平均吞吐之外的尾延迟（例如 P99 请求延迟）。布局调整即使提高长期吞吐，也可能带来短时搬迁干扰；请求域切换较快时，长统计窗口又可能反应迟缓。窗口大小、更新频率与异步切换策略需要一起评估。

6. 昇腾生态：区分算法可迁移与后端已验证 ​

EPLB 的布局思路和 LPLB 的优化模型不天然绑定某一种芯片，但负载统计、求解、权重传输及专家计算仍需要后端支持。算法能复用，不等于某个现成实现可以直接运行。

方向生态中的对应实践应如何理解支持范围
专家并行通信DeepEP-Ascend、CANN / torch_npu 相关能力及框架专用路径同名或兼容接口不代表设备、版本和复制能力一致
推理专家布局vLLM-Ascend、SGLang 的 EPLB 相关集成需分别核对芯片、模型、量化格式、冗余专家及通信后端

MoonEP 适配本地 Ascend 910C 适配与 HyperParallel 实验已有设备通信和训练性能记录，完整训练数值验收仍有待完成

评估昇腾上的可用性时，应具体说明实现分支、设备型号、模型与训练或推理配方，并区分算子验证、性能测量和质量验收。平台能力与项目版本持续变化，部署应以目标版本的支持矩阵和实际测试为准。

7. 如何做可信的效果对比 ​

不同项目公开的吞吐提升、理想效率和通信加速比，通常采用不同模型、拓扑和基线，不能直接据此排名。更可靠的对照应同时覆盖以下维度：

维度应记录的内容目的
路由需求相同输入、逻辑专家选择、专家与 owner 偏斜区分负载变化与调度收益
执行负载重分配前后行数、实际计算时间验证工作是否分散，以及行数能否解释耗时
附加成本规划、权重与梯度字节、副本显存、布局切换避免只报告均衡收益而省略代价
完整性能训练 step、推理吞吐与尾延迟判断关键路径是否缩短
正确性与质量输出、完整梯度、优化器更新或任务质量区分性能观察与可用加速
重复与失败同节点配对、重复范围、OOM 和环境失败避免选择成功样本后形成过度结论

基线的专家计算、精度和重算策略也应一致。例如，只给候选方案开启 grouped GEMM，会把专家计算优化误算为均衡收益。人工热点适合检验机制，但最终仍需自然路由、真实模型权重及目标业务负载下的验证。

总结 ​

MoE 负载均衡包含三个相互关联的选择：是否改变逻辑路由，是否调整专家布局，以及是否根据当前负载重分配执行位置。EPLB 依靠历史统计优化布局，LPLB 在既有副本拓扑上优化当前流量，MoonEP 围绕固定容量联合设计规划与通信，UltraEP 则强调逐微批次的实时副本和配额决策。

选型时，应先判断瓶颈属于长期专家偏好、短期流量波动还是通信与执行布局，再比较对应方案的规划、显存和同步成本。能够让任务更均匀只是第一步，完整关键路径更短、正确性和质量可接受，才是最终的加速收益。
