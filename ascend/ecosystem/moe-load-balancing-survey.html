MoE 负载均衡：训练与推理加速方案综述 ​

摘要 ​

  • 负载均衡已经从「训练时用辅助 loss 让路由更均匀」，演进为运行时专家复制与再放置 （冗余专家 / 专家迁移），并出现了事实上的公共接口：权重预取 + 梯度归约原语。
  • Ascend 侧不是空白：DeepEP 有官方 Ascend 分支，vLLM-Ascend 与 SGLang 都有可用的 EPLB， MindSpeed 提供了训练侧的两条负载均衡路线。

1. 开源生态方案 ​

1.1 总览 ​

1.2 EP 通信库与 dispatcher 集成 ​

定位：DeepEP 只解决 EP 的 dispatch / combine 通信，并把冗余专家的权重预取与梯度归约做成原语； 它不做负载均衡决策——复制谁、复制到哪、token 怎么重路由，全部由调用方给出。

DeepEP V2.5 做了较大重构：移除 NVSHMEM 依赖、改用 NCCL Gin 后端，通信内核通过 DeepJIT 在运行时编译，dispatch / combine 统一进 EPBuffer。 与负载均衡最相关的是新增的两个原语：

  • EPBuffer.lb_prefetch_weights(redundant_expert_weights, expert_weights, redundancy_mapping)： 在专家计算前把原专家权重（可含量化 scale）推到冗余槽位；
  • EPBuffer.lb_reduce_grads(redundant_expert_grads, expert_grads, redundancy_mapping)： 在反向把冗余专家的 FP32 梯度跨 NVLink 累加回原专家梯度。

调用方提供 [num_nvlink_ranks, num_redundant_experts] 的 int32 副本映射，并负责把 token 重路由到 被选中的专家实例。README 说明这两个原语是为支持 MoonEP / UltraEP 的专家复制路线而暴露的—— 三家因此收敛到同一套接口语义（前向把主专家权重推到副本、反向把副本梯度归约回主专家； UltraEP 明确说明副本不维护优化器状态），对应的实现见 3.2.3、3.3.4 与 3.4.5。

框架侧的 dispatcher 生态已相当统一：Megatron-LM 的 FlexDispatcher 支持 deepep / deepepv2 / hybridep 三个后端；vLLM 已落地 MoonEP 后端 （vllm/model_executor/layers/fused_moe/experts/moonep_experts.py， 但其 _supports_current_device() 断言 current_platform.is_cuda()，即 CUDA-only）。

1.3 负载均衡控制面 ​

EPLB（DeepSeek 开源）：核心是 eplb.rebalance_experts(weight, num_replicas, num_groups, num_nodes, num_gpus)， 按「节点数能否整除专家组数」在分层与全局两种策略间切换，只输出 phy2log / log2phy 映射， 与硬件无关，因此 Ascend 侧框架可直接复用该算法。算法步骤与工程约束见 3.1。

LPLB（DeepSeek 开源，EPLB 的续作）：在 EPLB 给出的冗余拓扑之上逐 batch 解线性规划重分配 token， 补上 EPLB 无法应对的 batch 内抖动；每个被选中的专家最多复制一份。模型、拓扑与限制见 3.2。

vLLM：核心是把 EPLB 拆成三层——控制面（EplbState + policy 决定布局与何时换）、 数据面（fused MoE 把逻辑专家查表映射到本卡物理专家并记录实际执行的专家）、 搬运面（后台 worker 搬迁量化专家权重），从而在服务过程中不停机换布局。 开关为 --enable-eplb --eplb-config '{...}'，配置含 window_size / step_interval / num_redundant_experts / use_async / policy / communicator， 其中 communicator 可选 torch_nccl / torch_gloo / pynccl / nixl。 实现位于 vllm/distributed/eplb/（state + communicator + migration_scheduler + async_worker + rebalance_execute）。

SGLang：把 EPLB 做成多算法可选的统一入口，并把 LPLB 作为其中一条求解路径集成进来。 python/sglang/srt/eplb/ 下同时提供多条算法路径： eplb_algorithms/{deepseek,deepseek_vec,elasticity_aware}.py、lplb_solver.py、waterfill.py 以及 expert distribution recorder 与 simulator。其中 lplb_solver.py 即对上述 LPLB 的集成 （各 rank all-reduce 全局计数后各自独立求解同一个 LP，不需要广播映射）； 但源码注释指出该路径只在 DeepSeek-v2 系列上安全（其它家族的 empty-rank 路径会死锁）。

MindSpeed（Ascend 训练）：把负载均衡拆成两条可独立启用的路线——搬参数（专家迁移） 与搬 token（动态热专家广播），前者改变专家位置、后者改变 token 落点：

  • 专家迁移（mindspeed/core/transformer/moe/expert_placement/）： EMA 预测专家负载（θ=0.9）→ DP 域 all-reduce 对齐 → 贪心 / DP / 混合打包 → 迁移专家参数与优化器一/二阶动量；细粒度控制器以变异系数至少下降 0.08 为门槛决定 每层是否迁移，默认 expert_placement_freq=50。支持分布式优化器、参数副本复用与 tp_extend_ep。
  • 动态热专家广播（balanced_moe，文档称「数参互寻」）： 识别热专家子集后跨 EP 节点广播其参数，把原本发往远端热专家的 token 改为本地计算， 并按 microbatch 精细调度以掩盖通信。限制较强：必须同时开启 --moe-fb-overlap 与 --moe-grouped-gemm，仅支持 alltoall 分发器与 Dropless 模式， 且源码明确说明不保证二进制对齐（DeepSeek-V3 减层 4 机 A3 场景 loss 误差 < 1%）。

Megatron-LM：思路是从损失函数侧抑制不均衡，并把 token dispatcher 做成可替换后端， 是训练侧路由均衡的基准。提供 aux_loss / seq_aux_loss / global_aux_loss / sinkhorn / aux-loss-free(expert bias) / none 六种策略，并配合 MoE parallel folding（解除 EP ≤ DP 限制）、FP8 训练与分布式检查点。

2.1 EPLB：130 行定义清楚问题边界 ​

核心思想：不做 token 层面的干预，只用历史负载统计周期性地重新摆放专家——热点专家复制多份， 再用 LPT 装箱把副本尽量均匀地铺到各 GPU（节点内优先，以利用 group-limited routing）。 由于只改「逻辑专家 → 物理专家」的落点，路由与计算语义完全不变；代价是布局决策依赖负载平稳性， 且重排通常需要停世界。它解决的是静态不均衡。

整个仓库只有一个 eplb.py，对外只导出 rebalance_experts，内部由三个函数构成。

2.1.1 三个核心函数 ​

balanced_packing(weight, num_packs)：LPT 贪心装箱。 输入 [X, n]（X 层、n 个对象）， 要求每个 pack 恰好装 n/m 个对象，目标是最小化各 pack 的权重极差。 实现是标准 Longest-Processing-Time：按权重降序排，每个对象丢给「还有名额且当前最轻」的 pack。 两点实现细节：

  • 有硬约束 assert num_groups % num_packs == 0，必须整除；
  • groups_per_pack == 1 时直接退化为恒等映射（省掉排序与循环）。

replicate_experts(weight, num_phy)：逐个加副本。 从 logcnt=1 出发， 循环 num_phy - num_log 次，每次取 (weight / logcnt).max() 的专家作为下一个冗余专家的宿主， 并令该专家 logcnt += 1。即「当前平均负载最高的专家优先再复制一份」，朴素但对负载估计不敏感。

rebalance_experts_hierarchical(...)：三步走。

  1. 把专家组按负载装箱到节点（balanced_packing(tokens_per_group, num_nodes)）；
  2. 在节点内做 replicate_experts（目标份额为 num_physical_experts // num_nodes）；
  3. 把物理专家 LPT 装箱到 GPU（balanced_packing(tokens_per_phy, num_gpus // num_nodes)）。

动机是 group-limited routing：同组专家尽量落在同节点，跨节点流量最小。

2.1.2 一个实现上的小聪明 ​

所谓「全局策略」并没有另写一套实现，而是在 rebalance_experts 里判断 num_groups % num_nodes == 0：成立走分层策略；不成立则把整机当成一个组一个节点 （num_groups=1, num_nodes=1）再调一次同一个函数，分层逻辑自动退化为全局装箱。

2.1.3 工程约束（README 未提及） ​

约束影响
全流程在 CPU 上跑（weight.float().cpu()），一次性计算所有层适合离线 / 周期性调用，不适合热路径
复杂度约 O(L·(E log E + 冗余数·E))（按代码估算）256 专家量级可忽略
多重整除断言（专家数/组数/节点数/GPU 数）不满足拓扑时直接 assert 失败，需调用方保证
只输出映射（phy2log、log2phy 带 -1 填充、logcnt）完全不碰 token：改的是逻辑→物理落点，无法应对同一专家在 batch 内忽冷忽热

最后一点正是 LPLB 要补的洞。

2.2 LPLB：把静态布局变成每 batch 的 LP 重路由 ​

核心思想：把 EPLB 的一步拆成两步——复制谁仍由 EPLB 按历史负载决定（静态、周期性）， 每个被复制专家分到多少 token 则由当前 batch 的负载解一个线性规划（动态、逐 batch）。 冗余专家与其原专家之间的连接被抽象成「边」，边容量即分给该副本的 token 数， 于是「均衡」变成「在边容量约束下最小化 EP 组内最大负载」。 它补的是 EPLB 的短板：batch 内抖动。

deepseek-ai/LPLB 是 EPLB 的续作，也是 SGLang lplb_solver.py 的来源。

2.2.1 图模型 ​

  • 边：冗余专家 ↔ 其原专家（由拓扑矩阵 r2o 决定）；
  • 边容量：本 batch 分给该冗余专家的 token 数，即该边允许的最大 token 流；
  • 求解目标：在边容量约束下重分配 token，最小化 EP 组内最大负载。

2.2.2 两段式分工 ​

谁被复制由 EPLB 决定（使用「只 reorder、不 replication」的变体），复制后的每 batch token 去向由 LP 决定。 Planner.update_redundancy_mapping 的顺序很能说明问题：

  1. 先用 rebalance_experts（num_replicas == 逻辑专家数，即不做复制）得到基础布局；
  2. 按 workload 历史在每 device 内对专家降序排序；
  3. 每 device 取前 combined_redundant_experts * num_redundants 个专家作为「待复制」集合；
  4. 按拓扑矩阵 r2o 把副本挂到对端 rank，构建 log2phy 时保证原始专家排在副本之前；
  5. 最后 assert max_logcnt == 2 —— 每个被选中的专家只复制一份。

拓扑 r2o 的形状是 [group_size, num_redundants]，并要求：每 rank 冗余专家数相同； 第 i 个冗余专家必须是另一个 rank 上第 i 个专家的副本——这让每个冗余专家恰好被两个 rank 共享。 仓库预置三类拓扑：

拓扑要求适用
Cube每卡 ≥ 2 专家，保留对角边8 卡 EP 子组内均衡，不牺牲跨节点通信
Hypercube16 卡，去掉对角边跨 16 卡专家并行
Torus每卡 ≥ 2 专家，编内 + 编外各一邻居全局均衡，但跨节点效率低于 Cube

自定义拓扑即修改 r2o 矩阵。

2.2.3 实现与集成 ​

  • 求解器是单 SM 的 Interior Point Method，线性代数走 NVIDIA 的 cuSolverDx / cuBLASDx （需先执行 download-mathdx.sh）；示例中按 N_SMS = 100（SM 数，与上文「约 100 µs」的 求解延迟无关）调用。
  • 实时负载统计可来自 torch.distributed，也可直接复用 DeepEP buffer 的内部通信器 （用 NVLINK + NVSHMEM 替代 allreduce）。
  • 对外接口：count_workload(idx, n_sms) → solve_probs(workload, avail_counter) → run(indices, avail_counter, N_SMS) 返回重定向后的物理专家索引；init_from_deep_ep(buffer) 可初始化。

2.2.4 作者自陈的限制（比宣传更有参考价值） ​

  1. 只均衡 token 总数，不考虑 grouped GEMM 耗时对 token 数的非线性，可能次优；
  2. 求解约 100 µs（跨节点更久），小 batch 下不可忽略；
  3. 极端全局不均衡时可能不如 EPLB——因为 LPLB 避免把多个副本给同一原专家，而 EPLB 会；
  4. 仍是早期研究阶段，性能收益「尚在评估」。

2.3 MoonEP：用「完美均衡」换掉负载敏感性 ​

核心思想：不去追赶负载，而是消除负载的不确定性——让每个 rank 在每层恒定收到 S×K 个 token， 与路由偏斜完全无关。做法是在线规划出若干冗余专家实例：把热点专家的 token 直接写到目的 rank 的 专家分组位置上（零拷贝），并把该专家的权重预取过去；反向再把副本梯度归约回主专家。

这样通信与迭代时间对 maxvio = max_e(T_e/T̄) − 1 基本不敏感，代价是额外的规划与权重预取内核。

2.3.1 规划算法 ​

规划逻辑在 56 KB 的 CuTe DSL 内核里，但仓库提供了等价的 Torch 参考实现 （tests/planning_reference.py），读它更高效。步骤：

  1. all-gather 各 rank 的 tokens_per_expert → tpe[R, E]，得到全局每专家 token 数 expert_count；
  2. 按 home group（每 rank 一段连续的 epn = E/R 个专家）求和得 group_tokens[h]；
  3. 计算 balance = group_tokens − CAP，CAP = S×K 是每 rank 的接收容量； 因总量守恒 sum(balance) == 0，正值表示该 home group 过载、负值表示该 rank 有余量；
  4. 贪心迁移：反复取 h = balance.argmax()、u = balance.argmin()，迁移 -balance[u] 个 token， 直到没有 group 过载（策略总是把接收方填满）；
  5. 把 quota 落到具体专家：「最大远端 quota × 剩余 token 最多的本地专家」逐轮取 take = min(rem, quota)，得到 alloc[e, d]（专家 e 有多少 token 落到目的 rank d）；
  6. 断言两条不变量：alloc.sum(dim=1) == expert_count（逐专家守恒）、 alloc.sum(dim=0) <= CAP（每 rank 不超容量）。

2.3.2 物理布局与关键不变量 ​

目的 rank d 上的 token 排布是：

  • [0, epn)：本 rank 自己的本地专家（local_start = d * epn）；
  • [epn, 2*epn)：远端专家的 prefetch 槽位（由 experts_to_copy[d, b] 指定）。

由此得到 MoonEP 最关键的约束：每个目的 rank 最多接收一个远端 home group 的专家 （参考实现里有 len(remote_experts) > epn 的断言）。这让每 rank 每投影的 prefetch 池大小刚好等于 epn， 且该池是进程级、跨层共享的——额外物理成本是总共 epn 个专家权重，而不是每层一份。

另外：cu_seqlens 按 token_padding（benchmark 用 128）对齐，padding 行由 dispatch 的 zero warp 清零 （zero_fill_ranges）；dst 把目的 rank 与段内偏移打包进一个 int32 （dst[i] = dest * NvS + base_off + seg_pos），重复项用负数编码，并生成 dup_groups / dup_loffs / dup_counts 三张去重表。

2.3.3 内核与内存 ​

  • 规划是一次 cooperative grid launch 的 CuTe DSL 内核：num_sms 个 block 在一次启动里跑完 Phase A/B/C/D；块间用软件 grid barrier，跨 rank 用 NVLink meta_buf 上的系统级原子自复位屏障； 大量使用 warp 级 argmax / scan 原语。
  • 打包编码位宽是常量而非推导：RANK_BITS = 7、KIDX_BITS = 7，注释写明「2^7 = 128 足够覆盖当前主流 EP 设置」； 去重构建用 DEDUP_BUILDER_WARPS = 4（注释解释了单 warp 是延迟受限、4 warp 是收益拐点）。
  • 内存走 CUDA VMM（nvl_dist_alloc / nvl_dist_map），跨 rank 共享可用 fabric handle 或 POSIX fd （MOONEP_MEM_HANDLE_TYPE=auto|fabric|fd），并使用 NVLink multicast（nvl_multicast_*）。 zero_copy=True 时 dispatch 直接返回通信缓冲的 view，专家 FFN 原地读写，没有边界拷贝。
  • 去重表的顺序由 builder 的 atomicAdd 决定、不保证稳定，参考实现明确要求测试比对 「组的集合」而不是元素顺序——这是个容易踩的坑。

2.3.4 训练侧的四条路径 ​

方向调用说明

2.3.5 Benchmark 方法学（值得借鉴） ​

benchmarks/bench_vs_deepep.py 的对齐做得很克制：

  • 两库使用完全相同的路由矩阵（共享 seed 1234）、相同输入张量与生成器 seed；
  • 相同 SM 预算（32）、相同 expert_alignment / token_padding（128）；
  • 相同计时框架（eager CUDA event、back-to-back、warmup 20 / iters 50、跨 rank 取均值）；
  • 只对齐 DeepEP v2 的 do_expand=True 路径，并说明 DeepEP v1 因不做融合 permute 而不参与比较；
  • grad_reduce 不计入（可被后续计算掩盖、不在 MoE 关键路径）；
  • 带宽口径统一为 S*K*H*2 / t（逻辑 payload 字节）。

局限：README 的性能结论是图示 + 定性（通信时间随 maxvio 基本持平、DeepEP v2 随最热 rank 退化）， 没有给绝对数字，引用时需注意；benchmark 仅单节点（ep == world size）； 设备仅列 NVIDIA GPU（Zhenwu PPU 标注待定）；强依赖 NVLink multicast 与 fabric handle。

2.4 UltraEP：把「精确负载 + 实时」做成生产系统 ​

核心思想：赌「算得起」——在每个 microbatch 的每一层，用精确的 post-gating 负载实时决定 复制哪些专家、token 如何重路由，完全不依赖历史预测。为此它不分别求解「布局」与「重路由」， 而是直接求解重路由后每个专家实例收到的负载（quota），并把复制流量限制在 scale-up 域内、 用跨层复用的副本缓冲把显存成本摊薄。

论文（arXiv 2606.04101）给出的理由是：预测式方法（EPLB/LPLB）的有效性取决于专家负载的平稳性， 而今天的细粒度 MoE 负载往往高度动态，预测误差会直接变成 straggler。

2.4.1 专家状态布局与内存 ​

  • 每 EP rank 在主专家（main / master experts）之外预留固定数量的冗余专家槽位；
  • 冗余专家不维护优化器状态：它们的梯度在反向实时归约回主专家，优化器只更新主专家；
  • 冗余专家的权重与梯度缓冲跨层复用——这是可行性的关键。Qwen3-235B 上， 每 rank 单个冗余槽的额外显存从 9.9 GB 降到 108 MB；
  • 运行期不做动态显存分配，声称不改变 MoE 的数学等价性。

2.4.2 控制面：quota-driven 求解 ​

它不做「先定布局、再定重路由」的两段式，而是直接求解重路由后每个专家实例收到的负载（quota）， 把两个阶段耦合起来。内核 quota_placement_solve_kernel 的骨架是「对最优全局负载阈值做二分」， 并且先做一次快速线性探测（fast_step）再二分收窄；do_binary_search 的触发条件是 「本 rank 有冗余专家且 NVL 域内多于一个 rank」。

可调参数集中在 UltraEPTuning（均有环境变量，括号内为默认值）：

参数作用
ULTRA_EP_BALANCE_THRESHOLD（1.0）均衡阈值下界
ULTRA_EP_QUOTA_MIN_TOKENS_PER_REPLICA（1024）避免为几十个 token 触发一次昂贵的权重复制
ULTRA_EP_QUOTA_LOCALITY_AWARE（True）复制时考虑局部性
ULTRA_EP_QUOTA_ALLOW_ZERO_MASTER_QUOTA（False）是否允许主专家 quota 归零
ULTRA_EP_QUOTA_ORACLE_EPS（0.01）/ ULTRA_EP_QUOTA_KERNEL_STAGE（1）求解精度与内核阶段
ULTRA_EP_GRAD_REDUCE_NUM_SMS（42，须为偶数）/ ..._DETERMINISTIC（True）归约的 SM 占用与确定性
ULTRA_EP_WEIGHT_SYNC_PLAN_MODE（adaptive）权重分发模式：direct / adaptive / force_relay

2.4.3 放置规则与确定性 ​

默认（非 legacy）放置算法：

  1. 主专家位置固定不动；
  2. 在每个 NVL 域内贪心复制最热的专家；
  3. 用 LPT 装箱把副本分配到 GPU 槽位，副本绝不与它的主专家同卡。

测试把它固化为不变量：l2p[:, 0] 必须是主专家、副本不得跨越 NVL 域 （违例直接断言 "replica crosses NVL domain"）。且所有 rank 各自算出相同结果，不需要广播—— 与 SGLang 的 LPLB 设计一致。

重路由语义是确定性轮转：逻辑专家 l 的第 k 个 token 分派到 l2p[l, k % C_l]（C_l 为该逻辑专家的物理实例数）。

2.4.4 数据面 ​

  • persistent kernel + 共享内存双缓冲：把专家权重/梯度切成 tile，用 memory semantics + TMA 做设备间异步搬运；
  • chunk streaming relay：热专家副本多、冷专家无需副本，于是热专家所在 rank 的出向组播会成为新瓶颈。 方案是按实时流量分布构建两级中继树，让低流量 rank 帮忙转发；并按 chunk 流式转发， 避免全局 barrier 与通信气泡。相关旋钮：weight_sync_relay_min_replicas / max_relays / min_fanout_gain；
  • 确定性梯度归约：用保序累加替代 atomicAdd，保证 FP32 归约可复现；
  • 通过环境变量控制通信 kernel 的 SM 占用与共享内存足迹，让通信与计算 CTA 能调度到同一 SM 上共存。

2.4.5 生命周期 ​

前向三步（update_placement → weight_sync → reroute）：规划与权重复制在关键路径上， 重路由较轻、基本能被权重复制掩盖。

反向两步：在 MoE Dgrad 之前用 RestoreReplicaWeights（autograd 恒等前向 + 反向触发权重重分发） 恢复对应 microbatch 的副本布局；在 Wgrad 之前 grad_reduce 把副本梯度归约回主专家， 该通信可藏在 router 与 attention 的反向之后。

PP/VPP 支持：给每个 (真实层, microbatch slot) 分配虚层 ID （num_alloc_layers = real_num_alloc_layers * max_microbatches，且 real_num_alloc_layers = num_layers + 3 为 1-based 层号做 padding），避免布局表与重路由缓冲在 microbatch 间串扰。

官方注脚同时承认：在开源的 Megatron patch 里，权重复制被放在 MoE Wgrad 之前 （因为与 fused grouped-GEMM 重叠需要在 kernel 内插入同步，过于侵入）， 所以反向的权重分发并没有被完全掩盖。

2.4.6 对外接口 ​

Manager 构造参数包含 num_layers、num_local_master_experts、num_local_redundant_experts、 expert_fc1_numel / expert_fc2_numel（含 FP8 的 scale numel）、is_train、max_microbatches、 legacy_placement、权重/scale 的 dtype；梯度 dtype 目前只支持 FP32（否则直接 ValueError）。

主要方法：construct_local_master_ptr_pool（逐层注册主专家权重/梯度指针）、 update_placement / update_placement_sparse、reroute / reroute_sparse、 weight_sync、grad_reduce、set_weight_sync_plan_mode、set_grad_reduce_deterministic、 allocate_microbatch_slot、get_comm_stream、destroy。

2.4.8 局限 ​

  1. NVIDIA-only（NVSHMEM），且以 RSN（rack-scale node） 为大前提——复制限定在 scale-up 域内；
  2. 依赖 HybridEP 分支与源码补丁，DeepEP V2 路径尚未验证；
  3. 反向的权重分发在开源 patch 中未被掩盖（见 3.4.5 注脚）；
  4. profiler 不兼容 CUDA Graph；ULTRA_EP_LOAD_PROFILING 与 legacy_placement 互斥（构造时断言）；
  5. 官方自陈：UltraEP 解决的是「跨 rank 不均衡」，与理想上限的残余差距来自单个专家内部负载不均 与冗余专家带来的控制开销，而不是残余失衡或关键路径开销。

2.5 横向取舍 ​

把四者放在一起，取舍其实只有三个维度：

① 预测还是精确。 EPLB 押「负载平稳」，代价是分布漂移时失效；UltraEP 押「每条关键路径都算得起」， 代价是必须把求解压到约 100 µs 并把复制限定在高带宽域；MoonEP 落在中间——逐层精确， 但用固定 S×K 的形状换掉了所有动态形状问题。

② 动布局还是动 token。 EPLB 只动布局，所以重排是「停世界」的（vLLM / vllm-ascend 需要额外的异步 worker 正源于此）；LPLB / MoonEP / UltraEP 都动 token，因此可以在 microbatch 粒度做， 但必须处理重路由的反向传播与梯度归约。

③ 副本预算。 EPLB 无上限（num_replicas 自由），极端不均衡下表现最好； LPLB 每专家恰好 1 个副本（max_logcnt == 2），结构最简单、权重复制最好做； MoonEP / UltraEP 的副本数由每 rank 预留 slot 数决定，内存与通信可控，但必须靠跨层复用缓冲摊薄成本。

一句话总结演进逻辑：EPLB 是「算得准就能省」，LPLB 是「算得勤就能省」， MoonEP 是「让负载不影响延迟」，UltraEP 是「让精确计算便宜到可以每层都做」。
