Dist-MoE 调研：融合专家通信、计算与激活内存管理 ​

混合专家模型（Mixture of Experts，MoE）只为每个 token 激活少量专家，可以扩大模型容量，但计算成本之外还存在两类开销：token 要在设备间往返，训练中间结果要一直保留到反向传播。路由分布变化后，通信量、专家矩阵规模和激活内存需求又会随之变化。只优化矩阵乘法，往往不能缩短整个 MoE 层的关键路径。

Meta Dist-MoE 将专家并行的数据搬运、分组矩阵乘法和激活内存规划放进同一套执行体系：GPU 根据实际路由生成地址与偏移，内核按数据就绪情况推进计算，保存空间不足时在反向阶段重算。它适合研究 Blackwell 上的高吞吐专家层，但不是包含 router、数据流水线和优化器的完整训练框架。

调研范围与版本：资料核对日期为 2026 年 11 月 9 日。代码依据 Meta Dist-MoE 提交 285763b；机制与性能依据官方交互式说明及其公开 CSV。性能图由这些数据重新绘制，机制图为本文示意，未在本地 GPU 上复测。用户提供的 arXiv:2608.09907v1 是另一项同名研究，第 1 节单独辨析，不将其结果归于 Meta 实现。

1. 先区分两种 DistMoE ​

1.1 三份资料并不属于同一项工作 ​

资料研究对象主要问题证据类型
arXiv:2608.09907DISTMOE：Private-data Rehearsal-free Routing in Mixture-of-Experts for Distributed Instruction Tuning私有视觉语言数据分布在不同客户端时，如何独立训练、校准并组合专家模型方法、任务精度、消融实验
Meta 交互式说明Dist-MoE 分布式专家执行库如何协同通信、GEMM、激活保存与重计算机制演示、实现说明、独立基准
meta-pytorch/dist_moeBlackwell 专家层内核与运行时如何在稳定地址与容量约束下执行专家前反向代码、API 契约、测试与使用文档

论文作者为 Mainak Singha、Niccolò Biondi、Elisa Ricci 和 Subhankar Roy，其代码链接为 mainaksingha01/DistMoE，不是 Meta 仓库。论文中的“distributed”主要描述客户端数据与专家训练的分布；Meta 库中的“distributed”主要描述专家并行执行时跨 GPU 的数据运动。

因此，不能用该论文的多模态任务精度证明 Meta 内核的训练效果，也不能把 Meta 的吞吐结果当成该论文方法的系统评测。

1.2 论文方法可以怎样理解 ​

论文将专家知识获取与专家组合分为两个阶段。

阶段 I 用公共 FFN 初始化私有专家，冻结公共专家与注意力层，只更新私有专家和对应路由参数。阶段 II 冻结专家，更新 router 与私有专家输出上的线性适配器，让独立训练的专家具有更可比较的输出尺度。

设公共专家输出为 hpub，客户端 m 经适配后的输出为 h~m，残差为 Δm=h~m−hpub。论文以随机方向投影和 Epps–Pulley 差异约束，使这些残差向共同的各向同性高斯目标校准；训练目标同时包含下一 token 预测损失。路由权重非负且归一化时，组合输出可写为：

o=hpub+∑mαmΔm.

这说明专家的影响不仅取决于路由权重，还取决于残差幅度。阶段 II 的目的就是缓解“分数接近，但某个专家因输出尺度过大而主导组合”的问题。

论文的 rehearsal-free 指不使用其他客户端的私有数据做联合回放，并非不再使用本客户端私有数据，也不等同于形式化的差分隐私保证。论文在 COCO、GQA、OCRVQA、TextVQA、Visual Genome 五个客户端域，以及 Qwen-1.8B、Phi-2.7B、StableLM-1.6B 等骨干上研究任务表现；这些实验不衡量 Blackwell 内核的通信吞吐。

两项工作在概念上可以处于不同层次：前者决定专家与路由如何学出来，后者执行已经给定的路由。但论文的公共专家、输出适配器和门控形式是否满足 Meta 内核接口，仍需单独适配，三份资料没有给出二者已集成的证据。

2. Meta Dist-MoE 的定位与数学边界 ​

2.1 谁负责什么 ​

调用方提供输入 token、选中的专家 ID、路由分数与本 rank 的专家权重。Dist-MoE 管理对称通信缓冲区、GPU 路由元数据、激活槽和临时空间，并执行专家前反向。

组件调用方负责Dist-MoE 负责
Routerlogits、Top-K 选择、分数与路由策略消费给定 ID 与分数，生成执行所需的计数和地址表
专家权重参数分配、FSDP 协作、更新和低精度权重刷新以支持的布局执行专家计算，返回或累积梯度
并行调度EP 进程组、流水线动作与激活槽归属按选定槽保存状态并执行当前调用
生命周期保证动作顺序、等待使用结束后关闭 context预分配、维护内部状态与释放自有资源

Dist-MoE 中的 routing kernel 是“根据已有路由生成执行元数据”，不是训练或选择专家的 router。它也不会自动添加共享专家、改变专家放置或通过借用专家消除路由不均衡。

2.2 专家层的计算 ​

设每个 rank 有 T 个物理输入行，隐藏维度为 D，专家中间维度为 F，每个 token 最多选 K 个专家，全局专家数为 E，专家并行度为 P。采用列向量写法，普通 SwiGLU 专家的计算为：

h1,e=W13,ex=[ge;ue],h2,e=SiLU(ge)⊙ue,h3,e=W2,eh2,e,yt=∑k∈Vtst,kh3,et,k(xt).

其中 W13,e∈R2F×D 拼接 gate/up 投影，W2,e∈RD×F 为下投影；Vt 是有效路由槽集合，st,k 为调用方给出的分数。这里不假定库会替调用方归一化分数。输入与输出公开形状均为 [T, D]。

若全部路由有效，均衡接收量为 R―=TK。负载倾斜可用 ρ=maxrRr/R― 表示，Rr 是 rank r 接收的专家行数。关闭部分路由后，应以实际有效路由数计算均值。

3. 对称内存与指针驱动的数据流 ​

3.1 Token 所有者与专家所有者 ​

每个 GPU 同时拥有本地输入 token 和一部分专家。一个 token 选中远端专家后，输入仍由原 rank 发布，远端专家根据地址表读取它；专家输出再写回 token 所有者的返回槽。

图中箭头表示逻辑数据依赖，不表示所有阶段只有一次内核启动。

创建 context 时，库分配对称 routing、dispatch 和 combine 缓冲区，并交换各 rank 的基址。各 rank 可以持有不同的虚拟基址；通过 peer-base 表才能定位对端内存，不能把“对称”理解为所有进程中的地址数值必然相同。

对于 token 所有者 r、行号 t 和 Top-K 槽号 k，BF16 行宽为 σ=2D 字节时，前向读取和写回的逻辑地址为：

输入地址=dispatch_base[r]+tσ,结果地址=combine_base[r]+(tK+k)σ.

一个输入行只需发布一次，多条专家路由可引用同一源地址；这不意味着网络只传输一份数据，多个远端消费者仍可能分别读取它。

3.2 一次前向如何推进 ​

  1. 本地 kernel 发布输入和专家 ID，路由分数留在 token 所有者。
  2. GPU 间 barrier 确认发布完成；GPU 读取各 rank 路由，统计本地专家行数，构造 gather/scatter 指针表。
  3. 设备端 planner 根据实际接收量和选定激活槽生成内存偏移，决定保存还是重算。
  4. 专家 kernel 按指针读取本地或远端行，执行 W13、SwiGLU、W2，并将结果写入对端 combine 槽。
  5. 返回写入经 barrier 排序后，token 所有者用本地分数加权并对 K 条路径求和。

关键是路由计数与内存偏移不需要回传 CPU 再决定分配。但 GPU 间发布 barrier、tile 就绪计数和片上流水同步依然存在。项目所强调的 SyncFree 不能解释为“系统没有任何同步”。

3.3 两个 GPU 的最小例子 ​

Token 所有者Token选中专家
rank 0AE0、E2
rank 0BE3、E1
rank 1CE2、E0
rank 1DE1、E3

rank 0 拥有 E0/E1，因此本地专家计算顺序可组织为 E0[A,C]、E1[B,D]；rank 1 对 E2/E3 做相同组织。结果必须按原 token 和原 Top-K 槽写回，而不能按专家顺序直接输出，否则分数与结果会错位。

训练时反向沿相反方向流动：token 所有者发布路由输出梯度，专家 rank 计算输入梯度（DGRAD）与权重梯度（WGRAD），再将每条路由的输入梯度写回，最后由 token 所有者归约。

4. 计算内核：从分块就绪到 Staged/Mega ​

4.1 融合发生在数据就绪边界 ​

分组矩阵乘法（Grouped GEMM）将本地多个专家合并进同一启动。持久化调度器把工作映射为“专家、token 行块、输出列块”，各角色协作推进：

执行角色或存储职责
Gather/量化生产者读取路由行，生成本地操作数，发布块就绪信号
TMA使用 Tensor Memory Accelerator 将操作数块搬入片上共享内存 SMEM
MMA使用 Blackwell Tensor Core 执行矩阵乘加，累积到 FP32 TMEM
Epilogue转换输出格式、计算可融合操作，并写入本地或 peer HBM

某个输入块已收集完成，其对应 GEMM 就可以推进，而不必等所有专家的行全部收集完。生产者与消费者通过计数器和 full/empty barrier 保护缓冲区复用。通信因此被嵌入计算流水，而不是先完成一个独立的大规模搬运阶段，再开始全部专家计算。

这里的融合不会消除 HBM 中间结果，也不意味着所有 token 都能直接从远端进入寄存器。官方 BF16 路径明确将 gather 行写入本地激活缓冲区，再交给 TMA/MMA 消费。

4.2 Staged 与 Mega 的差别 ​

路径前向主要计算组织取舍
BF16 Standard分布式 W13 与 W2；满足条件时融合 SwiGLU，否则单独执行精度路径较直接，仍需容量和布局约束
MXFP8 Staged分布式 W13；随后 SwiGLU/量化/W2/回传两个有序计算启动，部分操作数临时空间可在边界复用
MXFP8 Mega在一个分块前向计算网格内交错 W13、SwiGLU/量化与 W2/回传块就绪即可推进下投影，但 x-row 与 h2-row 生命周期重叠，需要独立区域

图中长度仅表示依赖与交错关系，不是实测时间，也不表示三个阶段使用互不竞争的硬件资源。Mega 仍有路由、规划、barrier 和最终归约；“一个前向计算 kernel”不是“整个 MoE 调用只有一个 kernel”。

Mega 的反向也不是全部合为一个 kernel：主要先运行 W2 的 DGRAD/WGRAD 融合 kernel，再运行 SwiGLU 反向与 W13 的 DGRAD/WGRAD 融合 kernel，最后归约输入梯度。

Mega 不保证始终更快。公开宽度扫描中，EP64、MXFP8 训练、F=6144 的更快路径是 Staged；应在目标形状与内存预算下比较两者。

5. 低精度：算术格式不等于通信格式 ​

5.1 当前支持矩阵 ​

精度执行路径训练推理
BF16Standard支持支持
MXFP8 E4M3Staged / Mega支持支持
NVFP4Staged / Mega不支持支持，要求预处理权重

MXFP8 用 E4M3 存值，每 32 个逻辑元素共享一个 E8M0 的二次幂缩放因子。NVFP4 用 E2M1 存值，每字节打包两个数，并配合 E4M3 块缩放与全局缩放。矩阵乘法的操作数精度、FP32 累积精度和最终存储精度需要分别讨论。

当前 MXFP8 训练路径发布的是 BF16 源输入，专家端 gather 后才量化，专家结果也以 BF16 写回。README 明确将通信量化列为不支持项。因此，不能将“FP8 GEMM”直接理解为“跨 GPU 通信流量减半”。

5.2 为什么训练保存不止一份量化表示 ​

前向或输入梯度计算需要沿收缩维度量化的行布局；计算权重梯度时，激活作为转置操作数，又需要沿另一轴量化的列布局。量化缩放因子依赖分组方向，不能简单转置字节和 strides 就得到数值相同的另一表示。

训练权重采用 32×32 分组量化，供前向与 DGRAD 共享 qdata，并为不同消费方向准备缩放布局。激活则可能具有 row/column bundles。MXFP8/NVFP4 还会将每个本地专家的工作行独立补齐到 128 的倍数；BF16 路径不做这种逐专家行补齐。

这些额外表示、缩放因子和 padding 解释了一个容易误判的现象：FP8 算术更便宜，不代表训练激活或总显存一定比 BF16 更小。小专家批量尤其需要关注补齐比例和准备开销。

6. 激活内存：跨层打包与动态重计算 ​

6.1 三类存储要分开预算 ​

存储可见范围保存内容与释放时机
对称通信缓冲区EP peer 可访问的 GPU HBM输入、路由结果、梯度与信号；context 生命周期内复用
Activation slot（激活槽）rank 本地 GPU HBM保留到匹配反向的前向状态
Scratch（临时空间）本地 HBM，可选主机 VMM 扩展当前调用的临时激活、重算与梯度，动作间复用

多个层可以把实际保存状态连续打包进同一个激活槽。这样，当某层接收行数多、另一层接收少时，二者可以共享总预算，而不是为每层都按峰值固定预留。

BF16 的 full-save 保存 gathered x、h1 与路由输出 h3，h2 仍可由 h1 重建；触发重算时，只保留原始本地输入 x。MXFP8 full-save 还涉及 WGRAD 所需的列量化 bundles。这里的“完整保存”指 planner 选择保留的必要状态，不是保存全部中间张量。

6.2 软预算与硬容量不同 ​

激活槽空间不足时，可以通过重算减少保存量；但 scratch 必须容纳实际执行的临时工作，超过总容量会失败。三个控制项不能混为一谈：

控制项作用超出后果
activation_slot_capacity_factor / 显式槽字节数控制保存到反向的激活预算，两种配置互斥在满足必需输入预算的前提下选择重算
device_scratch_capacity_factor控制热 HBM 临时空间无 VMM 时超出为执行错误；有 VMM 时可进入主机溢出区域
VmmConfig.total_scratch_capacity_factor控制 HBM + 主机临时空间总容量超出总界限会触发设备错误

激活容量因子不是简单的“接收行数倍数”。官方定义为：

Bslot=Bmin+ca(Bbalanced full−save−Bmin),

其中 Bmin 保留同槽各层重放所需的输入。实际字节还受对齐、精度和专家 padding 影响，应使用 plan_memory()，而不是自己以 T × K × D 推算全部内存。

这些 capacity factor 是内存预留参数，不会修改 router、不截断 token，也不会自动重分配热点专家。

6.3 动态选择为什么仍可兼容 CUDA Graph ​

CUDA Graph 需要稳定的执行结构与地址。Dist-MoE 在创建 context 时预留存储，实际 offsets 和 need_recompute 由 GPU planner 写入设备张量。主机始终发出固定序列，重算 kernel 根据设备谓词决定是否工作，不在 Python 端读取标志并分支。

这意味着路由变化可以改变缓冲区内部的偏移和工作量，而不必导致主机重新分配或重新组织调用图。但更换精度、静态模式或输入形状仍可能改变图；不能理解为一次捕获覆盖任意配置。

6.4 VMM 是容量兜底，不是免费扩容 ​

CUDA Virtual Memory Management（VMM）将同一稳定虚拟地址区间显式映射到 GPU 与 pinned host memory。它不是 CUDA managed memory，不依赖执行时自动迁页。训练布局可概括为：

已保存激活始终在 HBM，对称通信缓冲区也是独立的设备内存。只有 scratch 超出热区时才触及主机 backing，代价取决于 GPU–CPU 链路。它有助于容纳少见的接收峰值，但不会消除峰值对应的计算、通信和主机访存成本。

7. 流水线集成与运行约束 ​

7.1 槽分配取决于状态存活区间 ​

流水线框架根据最终调度计算哪些 (stage, microbatch) 的前向状态同时存活，再为不重叠区间复用物理槽。Dist-MoE 接收槽编号，不负责生成流水线调度。

比较策略时要看“同时存活的槽数 × 每槽容纳层数 × 每层预算”，不能只数槽。按 stage–microbatch 分配时，即使槽数更多，每槽只保存一个 stage 的层，也可能比整个 microbatch 共用大槽更省内存。拆分反向时，状态要保留到权重梯度完成，不能在输入梯度完成后提前释放。

每次前向保存其物理 slot ID 的不可变快照，后续更换当前槽不能改变该前向对应反向的地址归属。

7.2 使用接口前要满足的契约 ​

  • 目标为 NVIDIA SM100 及更新 GPU，没有 CPU fallback；首次发布验证环境是 Linux ARM64、Blackwell、Python 3.12、PyTorch 2.14.0+cu130、CUDA Toolkit 13.0.3.0、NCCL 2.30.7，以及 README 列出的 Triton/CUTLASS DSL 工具链。这是验证组合，不是所有兼容平台的穷举。
  • 一次调用中各 EP rank 必须有相同的物理输入行数 T。不同调用可以使用不同 T，但不能超过 context 预留上限；图捕获是否需要分桶或重新捕获应另行处理。
  • 专家 ID 范围为 [-1, E)；-1 表示关闭该路由且分数必须为零。同一 token 的有效专家 ID 不能重复。全关闭行返回精确零行。
  • Context 要在所有 EP rank 以匹配顺序 collective 创建；可顺序复用，不可重入。正常训练不应随意 reset()；关闭前要确保 eager、trace 与 CUDA Graph 使用均已结束。
  • 支持 CUDA Graph、激活检查点和 non-strict make_fx；当前不支持完整 torch.compile、strict export 或 NVFP4 训练。不能由注册了 PyTorch op 推出完整编译兼容。

行数不匹配或总 scratch 溢出可能触发 device trap，使 CUDA context 无法继续使用；不能当作普通 Python 参数错误捕获后继续训练。容量规划应先于规模扩展。

8. 性能证据：局部执行收益有多大 ​

8.1 先区分两套公开基准 ​

8.4 测量口径与尚未回答的问题 ​

公开说明采用 10 次预热、5 个计时窗口、每窗口 30 次迭代。CUDA events 得到窗口时间后先按 rank 取最大值，再对五个窗口取中位数；图中的窗口范围不是置信区间。standalone 套件记录了数值检查和输入变化、地址稳定的图回放检查，但这些不能代替长时间训练收敛验收。

有效前向 GEMM 工作量的每卡平均值为：

FLOPsfwd=6TKDF,FLOPsbwd≈2FLOPsfwd.

计数约定为一次乘加计 2 FLOPs，覆盖 gate/up/down 三个投影；忽略 padding 与 replay 的额外算术，但这些开销仍留在计时中。这里得到的是整个 routed layer 的有效算率，不是 Tensor Core 指令利用率。

  • NVLink TX/RX 是另一次至少一秒重复运行中采集的 NVML GPM 硬件计数，不能由字节率更高直接推导系统更快。
  • HBM 指标是逻辑字节数 / 时间的模型值，不是 DRAM 计数器，不宜称为实测 HBM 利用率。
  • EP 扫描固定每 rank 输入量，增加 EP 会增加全局 token，不能直接称为固定全局批量的强扩展。
  • standalone 的 EP32/EP64 训练位于不同站点，部分分配共享互连 fabric；资料不支持“全程无外部竞争”的结论。
  • standalone 训练设置激活与 scratch 因子为 8、VMM 关闭且未触发容量重算，不能据此证明 VMM 溢出或强重算情况下性能相同。

9. 与其他 MoE 优化的关系 ​

比较维度Dist-MoE 的重点不能直接替代的工作
Router 设计执行给定路由路由训练、辅助损失、专家语义与模型精度设计
通信库将 gather/scatter 与专家 GEMM 协同任意通信拓扑与跨节点后端的通用适配
专家负载均衡容纳变化的接收量并按预算重算热点专家复制、借用或重新放置
训练框架提供专家操作与内存/槽接口全局训练循环、流水线调度、优化器及检查点
跨硬件迁移体现分块依赖与生命周期管理方法Blackwell TMA/TMEM、低精度指令及对称访存的直接移植

DeepEP 更侧重专家分发与回传，组合计算后才形成完整专家层；Dist-MoE 把计算与通信作为更大的优化边界。MoonEP 等工作中的动态冗余专家解决热点分布，不能用 Dist-MoE 的容量因子替代。HyperParallel-MoE 同样重视细粒度通信计算交错，但针对的是昇腾 AIC/AIV 等不同执行资源。

官方交互说明还比较了 MoK、Comet/Flux 与 Mega MoE 的公开能力，但该表是 2026 年 10 月 14 日的源码审阅快照，并非对所有后续版本的永久结论。“没有内置 planner”也不等于外部训练框架无法管理状态。性能对比只覆盖实际测量的实现与工作负载。

10. 工程选型与复现建议 ​

适合优先评估的场景是：已有可用的 Blackwell 专家并行环境，MoE 层占比较高，跨层路由造成的激活波动明显，而且训练框架能保证调用顺序与槽生命周期。普通 BF16 可先作为数值基线，再逐项加入 MXFP8、Mega、激活打包和重算。

建议按下面的顺序验证，每次只引入一个主要变量：

  1. 固定代码提交、驱动、PyTorch、CUDA Toolkit、NCCL 和内核工具链，执行官方两卡 BF16 示例与测试。
  2. 记录真实模型的每专家接收分布及跨层峰值，用 plan_memory(...).explain() 分别核对保存预算、scratch、通信缓冲区与总显存。
  3. 在相同路由、共享专家、精度及计时范围下比较 baseline 与 Dist-MoE；分别报告单层、若干层和完整训练步。
  4. 使用真实激活重叠与流水线动作测试槽回收，验证图回放时输入、路由改变后的结果与梯度。
  5. 再评估低精度、Staged/Mega 和容量因子；将长期数值稳定、收敛和异常恢复与短期吞吐分别验收。

若主要问题是极端热点专家，优先考虑路由与专家放置；若目标是 NPU 或其他 GPU 架构，先评估后端实现成本；若是小批量 decode，需单独测量路由、量化与 padding 占比，不能外推 2,048 tokens/rank 的吞吐结果。

Dist-MoE 值得借鉴的系统设计，是将动态数据需求留在 GPU、用固定存储承载动态偏移、按真实生命周期复用激活、按块依赖推进通信计算。实际收益取决于这些机制是否击中了目标模型的关键路径。
