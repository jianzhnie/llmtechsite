流水线并行中的 Micro-batch：概念与 128 卡配置计算 ​

流水线并行（Pipeline Parallelism，PP）中的 micro-batch（微批次）有两个容易混淆的量：每个微批次包含多少样本，以及一次参数更新需要处理多少个微批次。前者决定任务的数据规模，后者决定调度器需要安排多少组前反向任务。

本文以 16 节点、每节点 8 卡，micro_batch_size=1、global_batch_size=128、PP=4、EP=32、FSDP Shard=32 为例。在 TP=1、CP=1，且批大小按样本数定义的前提下，HyperParallel 的拓扑解析得到数据并行规模 DP=32，因此每个 DP 数据分片每次参数更新处理 4 个微批次，每个微批次 1 个样本。

这个结果是数据计数与拓扑推导，不代表该配置已经完成训练验证，也不表示所有 PP 调度器都能在相同条件下直接运行。下文的实现依据固定为 HyperParallel 提交 12c5f7c6d417f24890680e09a38e678c00fe77e0。[1]

1. 三个计数量各自表示什么 ​

概念常见配置或变量含义本例
全局批大小global_batch_size一次参数更新覆盖的全局样本数128
微批大小micro_batch_size一个 DP 数据分片单次前向处理的样本数1
每步微批次数num_micro_batches、scheduler 的 micro_batch_num一个 DP 数据分片在一次参数更新中处理的微批次数4

这里的“DP 数据分片”指独立的数据输入流，后文也沿用常见说法称为“DP 副本”。它不等于一份物理上完整复制的模型权重：FSDP 可以在这些进程间切分参数，MoE 专家也可以采用不同的并行布局。

1.1 一个微批次会经过所有模型阶段 ​

一个微批次先经过模型首段，再依次经过后续阶段；反向传播按相反方向返回。不同阶段负责同一组样本的不同模型层，不是各自消费一组独立样本。

图 1：GPipe 原论文 Figure 2（PDF 第 3 页，原图裁切）。左侧展示阶段间的前反向依赖，右下展示多个微批次流经同一组阶段；同一微批次在不同阶段出现，不应重复计入全局样本数。该图解释 PP 语义，不是本文 HyperParallel 配置的运行记录。来源：GPipe。

在一次参数更新内，不同微批次可以位于不同阶段。具体何时执行前向、反向以及通信，由调度器决定；改变任务顺序不会自动增加数据量。

1.2 微批次数与梯度累积 ​

在本文的常见同步训练语义下，多个微批次的梯度共同用于一次参数更新，因此微批次数也对应每个 DP 数据分片的梯度累积规模。这个关系不能推广为“所有框架的 gradient_accumulation_steps 都与 PP 微批次数同义”：框架可能另设外层累积、token 预算或批处理策略，需要核对实际实现。

2. 从全局批大小计算微批次数 ​

2.1 基本公式与适用前提 ​

令 G 为全局批大小，b 为微批大小，D 为数据并行规模，m 为每个 DP 数据分片的微批次数，则：

G=Dbm,m=GDb.

公式来自数据量守恒：每个 DP 数据分片一次更新处理 bm 个样本，D 个分片合计处理 Dbm 个样本。它要求：

  • G 按同一种样本单位计数，所有 DP 数据分片均分数据。
  • 每个微批次大小固定，G 能被 Db 整除。
  • 没有另行覆盖该关系的外层累积或不完整尾批处理。

样本打包、动态 token batch 和变长输入需要额外确认“样本”到底是一条原始记录、一个打包序列，还是配置中的其他计数单位。微批次数相同，也不代表有效 token 数和计算量相同。

2.2 一个简单例子 ​

设 G=512、b=8、D=4：

GD=128 个样本/数据分片,m=5124×8=16.

每个数据分片需要处理 16 个微批次，每个微批次 8 个样本。这 16 个任务都要经过所在流水线的全部阶段；不能再因经过两个或四个 PP 阶段，就把样本数乘以阶段数。

3. 128 卡配置：先解析拓扑，再代入数据公式 ​

3.1 已知参数与待确认前提 ​

项目数值或条件用途
物理资源16 节点 × 8 卡，共 128 个训练进程world_size=128，假定每卡一个进程
PP4模型流水线方向的物理进程数
TP、CP均为 1本文推导的配置前提；分别指张量并行与上下文并行
FSDP Shard32参数分片规模；不能单独据此认定数据并行规模
EP32每个专家并行组的进程数
全局批大小 G128一次参数更新的样本数
微批大小 b1每个数据分片单次前向的样本数

节点数与每节点卡数只决定总进程数；它们没有说明每个通信组具体跨哪些节点。物理 rank 映射、网络和显存可用性仍需单独检查。

3.2 从 World Size 解析 DP ​

固定提交中的 resolve_parallel_layout() 先计算非 DP 维度，再解析 DP 规模：[1]

WorldSize=D×CP×TP×PP.

代入 TP=1、CP=1、PP=4：

D=1281×1×4=32.

这表示全局样本沿 32 条 DP 数据输入流分配，每条流经过 4 个 PP 阶段。此处“32 个 DP 副本”描述数据划分，不要求每条流水线独立持有全部专家权重。

3.3 FSDP Shard=32 是一致性校验 ​

同一实现还要求：

DPreplicate×DPshard=D×CP.

本例中 D=32、CP=1、FSDP Shard=32，因此解析出的 FSDP replicate 规模为：

DPreplicate=32×132=1.

因此，FSDP Shard 与 DP 恰好都为 32 是这组配置下的结果，不能当作通用等式。若存在 CP 或额外参数复制维度，应重新解析。

3.4 EP=32 使用同一组进程的另一种布局 ​

该提交将一个 PP 阶段内的稠密计算进程域定义为：

Ndense=D×CP×TP.

EP 则在这个进程域内组织专家并行，并要求 Ndense 能被 EP 整除。本例中：

Ndense=32,EDP=NdenseEP=3232=1.

这里 EDP 指专家数据并行规模。代码还检查专家数据并行的分片配置 edp_shard_size，本例要求其与 EDP=1 相容，即为 1；该参数未在输入条件中给出，实际配置时需要确认。[1]

EP 不是再额外乘到 World Size 或全局样本数上的独立维度。 在这份实现中，稠密部分的 DP/FSDP 布局与专家部分的 EP/EDP 布局复用了进程资源。同一条输入数据在 MoE 层按路由访问专家，不因此新增 32 份样本。

这个结论依赖本文引用的 Mesh 定义；不能脱离框架，将“DP×EP 一定不能相乘”作为所有并行系统的通则。

3.5 最后计算微批次数 ​

数据并行规模确定后，代入第 2 节公式：

m=GDb=12832×1=4.
统计范围本次参数更新的数据量
单个 DP 数据分片4 个微批次 × 1 个样本 = 4 个样本
全部 DP 数据分片32 × 4 = 128 个样本
同一数据流的每个 PP 阶段各自处理这 4 个微批次对应的模型分段，不能重复计为新样本

不能使用 128/(1×32×4)，因为其中的 32 已经是按 PP=4 解析出的 DP 规模，再除以 PP 会重复计算。也不能再除以 EP=32，因为它未增加独立的数据输入流。

4. 调度方式改变任务顺序，不改变批大小关系 ​

4.1 四种路径分别改变什么 ​

路径改变的内容对微批次数 m 的影响
GPipe前向与反向分阶段安排不自动改变 m；激活保留量随微批次数增长
同步 1F1B预热后交替执行前向与完整反向不自动改变 m；可更早回收激活
Interleaved 1F1B / VPP每个物理 rank 持有多个模型 chunk，交错执行逻辑阶段变多，但样本与微批次不因此增加
HyperParallel MPipe将部分预处理工作按微批次分配到不同 PP rank，再与主干流水线衔接输入仍是同一步的微批次集合；额外的 owner 与传输约束需要核对实现

本例始终是每个数据分片的 MB0～MB3。VPP 增加的是它们经过的模型分块，不能把 4 个微批次当作 8 个独立微批次，再用于全局批大小计算。具体调度图和论文原图见调度综述。

4.2 m=4、p=4 能运行，不等于高效率 ​

普通 GPipe/同步 1F1B 的均衡、无通信简化模型给出：

ρelapsed=p−1m+p−1=37≈42.86%.

这只是该理想模型下的气泡比例示例，不是本例 HyperParallel 配置的实测空闲率。实际结果还取决于各阶段耗时、通信、重计算、专家负载与优化器同步。

此外，批大小整除条件与调度器约束是两层检查。Megatron-LM 论文中的交错实现要求 m 是物理 PP 规模的整数倍，但本文引用的 HyperParallel ScheduleInterleaved1F1B 在 _init_round_layout() 中处理不足一轮和非整除的微批次数，不能照搬该旧约束。这个代码能力仍不等于任意模型分块、通信重叠和 MPipe 配置均已通过运行验收。

4.3 固定全局批大小时，增大微批大小会减少任务数 ​

固定 G=128、D=32：

微批大小 b每个 DP 数据分片的样本数微批次数 m
144
242
441

增大 b 可能提高单次计算效率，也可能增加激活显存，同时减少可用于填充流水线的微批次。总吞吐是否改善需要实测。若为了增加 m 而改变 G 或 D，还会改变数据量、优化语义或并行布局，不能只调 scheduler 的任务数量。

5. HyperParallel 代码如何传递这个数量 ​

以下路径均来自同一固定提交，核对范围为批数计算、拓扑解析与任务数量传递；本文没有执行该模型的分布式训练。

环节实现依据相关行为

计算微批次数build_dataloader.pycalculate_num_micro_batches() 检查整除，再计算 global_batch_size // (micro_batch_size * dp_world_size)
配置与消费输入text_trainer.py、vlm_trainer.py用 mesh.dp_size 计算 num_micro_batches，PP 分支将输入迭代器与该数量传给 pipeline_forward_backward()

6. 配置前的检查顺序 ​

  1. 确认数据单位：全局批大小与微批大小是否都按相同样本单位定义，是否存在 packing、动态 token 预算或外层累积。
  2. 解析数据并行规模：依据框架的 World Size 公式计算 DP，不凭 FSDP Shard 或 EP 的数值直接猜测。
  3. 核对参数与专家布局：本例除 FSDP Shard=32 外，还需检查与 EDP=1 相容的专家分片配置。
  4. 检查两类整除约束：既检查 G/(Db)，也检查所选 PP/VPP/MPipe 调度器对微批次和模型分段的限制。
  5. 验证实际运行：再检查阶段划分、rank 映射、显存、通信、梯度同步与一次参数更新的数值结果。

总结 ​

微批大小 b 表示任务中有多少样本，微批次数 m 表示一次参数更新中每个 DP 数据分片处理多少个任务，二者通过 G=Dbm 关联。

在本文指定的 HyperParallel 布局与前提下，128 卡、PP=4 解析出 DP=32，再由 128/(32×1) 得到 m=4。PP、VPP 和 EP 影响模型部署及任务执行方式，不能在已经解析出的数据并行规模之外再次重复计入样本数。
